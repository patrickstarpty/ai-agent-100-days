## Day38 - 路由、并行与子图

> 编排：工作流与受控循环 ｜ 建议用时 1 小时

> **一句话**：条件边让状态决定下一步去哪，并行让互不依赖的步骤同时跑、由 reducer 合并结果，子图把一段能力封成接口固定、失败时返回状态的组件。
>
> **放在全局看**：这是 Day35 里“路由”和“并行”两种工作流模式在 LangGraph 里的落地，用到 Day37 的 reducer；子图是 Day77~80 多 agent 契约的前身。

### 学习目标

- 写出由状态驱动的条件边，分清规则路由和模型路由各自的位置。
- 搭一个并行分支，说清结果怎样合并、某一支失败时会怎样。
- 把一段独立能力做成子图，输入输出类型化，失败时返回带状态的结果。

### 核心概念

**打个比方**：像医院看病：分诊台按症状和规定把你分到科室（路由）；抽血和拍片可以同时去做，结果汇总到医生那里（并行）；检验科是个独立科室，只收化验单、只出报告，内部怎么做你不用管（子图）。

**条件边：状态说了算**

条件边的路由函数读状态、返回下一个节点的名字。决定走向的依据要事先写进状态：任务类型、检索结果是否为空、校验是否通过、已用步数。

路由的依据有两种来源：

| 路由方式 | 做法 | 适合 |
| --- | --- | --- |
| 规则路由 | 按字段、权限、关键词、表达式判断 | 依据明确的场合：权限、风险等级、预算、格式校验结果 |
| 模型路由 | 让模型按 Day04 的结构化输出给出分类 | 依据是自然语言、规则写不全的场合：用户意图、问题类型 |

两者经常一起用：模型给出分类，规则做最后裁决。模型的分类是一条输入，权限不够、动作有风险、分类不在已知范围内时，由确定性的规则改走别的路。

```python
from typing import Literal

KNOWN = {"faq", "order_query", "unsubscribe"}
NEEDS_APPROVAL = {"unsubscribe"}            # 有写操作的意图

def route(state) -> Literal["answer", "order_tools", "approval", "fallback"]:
    intent = state["intent"]                # 上一个节点让模型给出的分类
    if intent not in KNOWN:
        return "fallback"                   # 模型给了没见过的类别，不猜
    if intent in NEEDS_APPROVAL:
        return "approval"                   # 规则强制走人工确认（Day41）
    return "order_tools" if intent == "order_query" else "answer"
```

路由函数里只有确定性代码，所以它可以单独写单元测试：每个分支一条用例。

**并行：同一步里跑，用 reducer 合并**

一个节点有多条出边时，所有目标节点在同一个超步里并行执行；汇合节点等它们都结束后才运行。几个分支写同一个字段，就靠 Day37 的 reducer 合并。

```python
import operator
from typing import Annotated
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END

class State(TypedDict):
    question: str
    evidence: Annotated[list[dict], operator.add]   # 各分支的结果追加进来

def search_docs(state: State) -> dict:
    try:
        return {"evidence": [{"source": "docs", "status": "ok", "items": docs_search(state["question"])}]}
    except Exception as e:
        return {"evidence": [{"source": "docs", "status": "failed", "error": type(e).__name__}]}

# search_code 写法相同，source 为 "code"

builder = StateGraph(State)
builder.add_node("prepare", prepare)
builder.add_node("search_docs", search_docs)
builder.add_node("search_code", search_code)
builder.add_node("answer", answer)
builder.add_edge(START, "prepare")
builder.add_edge("prepare", "search_docs")      # 两条出边：并行
builder.add_edge("prepare", "search_code")
builder.add_edge("search_docs", "answer")       # 两支都结束后才进入 answer
builder.add_edge("search_code", "answer")
builder.add_edge("answer", END)
graph = builder.compile()
```

三点要注意：

- **顺序不保证。** 文档说明同一超步里并行分支的更新顺序不一定一致。需要稳定顺序时，按 `source` 这类字段排序后再用。
- **一支抛异常，整步作废。** 同一超步是事务性的，任何一支抛出异常，这一步所有分支的更新都不生效。如果“部分结果也能用”，就像上面那样在节点里捕获异常，返回带 `status` 的结果，由汇合节点决定怎么处理。
- **数量不固定时用 `Send`。** 分支数量取决于运行时数据（例如每个子问题各检索一次），可以从条件边返回一组 `Send(节点名, 该分支的输入)`。并发数可以用调用配置里的 `max_concurrency` 限制。

**子图：自成一体的组件**

子图是被当作节点使用的另一张图。父图和子图状态结构不同时，在一个节点函数里调用子图，手动做输入和输出的转换。这个包装节点正好是写契约的地方：

```python
from typing import Literal
from typing_extensions import TypedDict

class RetrievalResult(TypedDict):
    status: Literal["ok", "empty", "failed"]
    chunks: list[dict]
    error: str

retrieval = retrieval_builder.compile()     # 子图：改写查询、检索、按权限过滤、重排

def retrieve(state) -> dict:
    try:
        out = retrieval.invoke({"query": state["question"], "user_id": state["user_id"]})
        result = RetrievalResult(status="ok" if out["chunks"] else "empty",
                                 chunks=out["chunks"], error="")
    except Exception as e:
        result = RetrievalResult(status="failed", chunks=[], error=type(e).__name__)
    return {"retrieval": result}
```

父图只看 `retrieval["status"]`，用条件边分别走向生成、弃答（Day17）或报错，不需要知道子图内部有几个节点。好处有三个：子图可以单独测试和评估；内部改动不影响父图；失败有统一的表达方式，父图不会被一个未捕获的异常中断。父子图状态字段相同的情况下，也可以把编译好的子图直接传给 `add_node`，但那样就少了这层显式的契约。
