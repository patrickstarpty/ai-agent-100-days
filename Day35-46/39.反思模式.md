## Day39 - 反思模式

> 编排：工作流与受控循环 ｜ 建议用时 1 小时

> **一句话**：让模型先写一版，再对照标准检查并改一版，用多一次调用换更好的结果。
>
> **放在全局看**：反思是成本最低的质量提升手段之一，也是 Day35 里“评估者与优化者”工作流的最小形式。它和评估（Day23~34）是一对：评估告诉你反思值不值。

### 学习目标

- 说清反思模式的基本结构，以及它在什么条件下有效。
- 能区分“自我反思”和“带外部反馈的反思”，并知道后者为什么更可靠。
- 会用评估集判断加一轮反思是否值得。

### 核心概念

**打个比方**：像写完作文自己再读一遍、改一遍。如果有老师的批注（外部反馈），改得会准得多；只靠自己读，常常看不出问题。

**基本结构**

反思由三步组成：生成一版结果，对照标准检查这版结果，根据检查意见改写。检查和改写可以重复，直到通过或达到轮数上限。

```python
from llm import chat   # Day02 写的薄封装

def reflect(task: str, check, max_rounds: int = 2) -> str:
    draft = chat([{"role": "user", "content": task}]).choices[0].message.content
    for _ in range(max_rounds):
        problems = check(draft)              # 返回问题列表；空列表表示通过
        if not problems:
            return draft
        feedback = "\n".join(f"- {p}" for p in problems)
        draft = chat([
            {"role": "user", "content": task},
            {"role": "assistant", "content": draft},
            {"role": "user", "content": f"上面的结果有这些问题，请修改后给出完整的新版本：\n{feedback}"},
        ]).choices[0].message.content
    return draft                              # 调用方应知道这是“达到上限”的结果
```

关键在 `check` 用什么来做。

**两种反馈来源**

| 反馈来源 | 做法 | 可靠程度 |
| --- | --- | --- |
| 自我反思 | 让模型（同一个或另一个）按评审标准批评这版结果 | 一般。模型容易认可自己的输出，或者提出无关紧要的修改 |
| 外部反馈 | 把结果交给一个确定的检查手段：运行代码看报错、校验结构、核对引用是否存在、跑测试 | 高。反馈是事实，模型据此修改的方向明确 |

能拿到外部反馈时优先用外部反馈。写代码的任务把报错信息喂回去，带引用的回答把“第 2 条引用指向的片段不存在”喂回去，效果通常比让模型“再检查一遍”好得多。

**什么时候有效**

- 有明确的、可以检查的标准：格式、约束条件、测试、引用。
- 第一版的常见错误是模型自己能改对的那一类。

标准模糊时，反思常常只是把文字改得不一样，甚至把原本正确的内容改错。

**用评估证明它值得**

反思让每次请求至少多一到两次模型调用。加不加，由评估集说了算：在同一批用例上比较“直接生成”和“加一轮反思”的通过率、成本和延迟。通过率没有明显提高，就不要加。

**上限与停止**

反思轮数必须有上限（Day45）。达到上限仍未通过时，要把“未通过”的状态如实带给调用方，不能把最后一版当作合格结果返回。

**在编排图里的样子**

放进 LangGraph，就是“生成”和“检查”两个节点，加一条条件边：检查通过走向结束，不通过回到生成，状态里记录已经进行的轮数。

1. 给主线项目“带引用的回答”加一轮带外部反馈的反思：引用校验失败时，把失败的具体原因反馈给模型重写。写出 `check` 函数会返回哪几类问题。
2. 设计对比实验：用哪批用例、比较哪三个数字、通过率提高多少才算值得。
