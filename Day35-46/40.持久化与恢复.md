## Day40 - 持久化与恢复

> 编排：工作流与受控循环 ｜ 建议用时 1 小时

> **一句话**：任务随时可能中断，系统要能从上次的存档接着跑，并且不把做过的事再做一遍。
>
> **放在全局看**：Day41 的人工确认靠检查点暂停和恢复，Day42 的事件回放也要读检查点里的状态；后面 Day72 的后台任务同样建立在它之上。

### 学习目标

- 理解检查点让长任务“可暂停、可恢复”的机制。
- 用 `thread_id` 和检查点跑通一次“中断再接上”的最小例子。
- 找出自己系统里恢复时可能重复执行的副作用。

### 核心概念

**打个比方**：像游戏存档：读档后从存档点重新开始。所以存档点之后做过的事（比如已经付的款）要能被认出来，不能再付一次；读档也撤不回已经发出去的付款和邮件，这类外部副作用不会因为你回到存档点就消失。

**两种持久化**

- 检查点（checkpointer）：按线程保存图状态的快照。它支撑对话连续性、人工确认、回放和故障恢复。
- 存储（store）：保存跨线程的长期数据，如用户偏好和共享知识。

生产环境必须用持久化的检查点后端，内存实现重启即丢。检查点会随对话变长而累积，需要保留策略。

**最小例子：带检查点编译，两次 invoke 看状态延续**

沿用 Day36 的 `State`（`messages` 字段用“追加”的 reducer）。编译时传入检查点，调用时在 `config` 里带上 `thread_id`，两次 `invoke` 用同一个 `thread_id`，第二次能看到第一次留下的消息：

```python
from langgraph.checkpoint.memory import InMemorySaver

checkpointer = InMemorySaver()           # 内存实现，仅用于本地演示
graph = builder.compile(checkpointer=checkpointer)   # builder 同 Day36

config = {"configurable": {"thread_id": "demo-1"}}

graph.invoke(
    {"messages": [{"role": "user", "content": "订单 A1001 多少钱？"}], "steps": 0, "stop_reason": ""},
    config=config,
)
graph.invoke(
    {"messages": [{"role": "user", "content": "再加上 A1002 呢？"}], "steps": 0, "stop_reason": ""},
    config=config,
)

snapshot = graph.get_state(config)
print(len(snapshot.values["messages"]))  # 两轮的消息都在，数量比单轮明显多
print(snapshot.next)                     # 空元组表示图已跑完，没有停在中途
```

第二次 `invoke` 传入的 `messages` 只有这一轮的新消息，因为 `messages` 字段的 reducer 是追加：框架会把它接到检查点里已经保存的消息后面，不需要调用方自己把历史消息重新传一遍。`get_state(config)` 返回的 `StateSnapshot` 里，`values` 是这个检查点的状态内容，`next` 是接下来要跑的节点名，空元组表示图没有停在等待中。生产环境要换成持久化的检查点实现，`InMemorySaver` 只用于本地演示，进程重启就丢。

**恢复的代价：节点可能重跑**

从检查点恢复时，中断的节点会从头再执行一次。节点里如果有外部副作用（发消息、写数据库、提交代码、触发构建），就可能做两次。应对方式：

1. **幂等键。** 每个副作用带一个由任务 ID 和步骤决定的键，下游据此去重。
2. **先记后做。** 在同一个事务里写下“准备执行”和状态变更，执行后再标记完成；恢复时先查这条记录。
3. **副作用单独成节点。** 把纯计算和副作用分开，副作用节点尽量小，重跑范围就小。

**等待时释放资源**

等待人工或外部结果时，任务应把状态存下来并释放 worker。恢复前检查两件事：租约是否仍然有效，发起人的权限是否仍然成立。

**至少一次投递**

用消息队列唤醒 worker 时，按“至少投递一次”设计：同一条唤醒消息可能来两次，处理方必须能安全地重复执行。
