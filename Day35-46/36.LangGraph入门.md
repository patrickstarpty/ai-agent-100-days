### 学习目标

- 说清 LangGraph 里状态、节点、边各自的职责。

### 核心概念

**打个比方**：像把口头交接的工作改成一张流转单：单子上写着当前进度（状态），每个岗位（节点）处理完在单子上填一栏，单子背面的规则（边）决定下一站送去哪里。

**图 = 状态 + 节点 + 边**

- **状态**：一份类型化的共享数据，图里所有节点读它、更新它。每个字段可以指定 reducer，决定更新怎样合并（Day37 细讲）。
- **节点**：普通的 Python 函数，接收当前状态，返回对状态的局部更新，不必返回完整状态。
- **边**：决定下一个节点。普通边固定走向；条件边调用一个路由函数，按状态选择去处，也可以选择结束。

图定义好后要先 `compile()` 才能运行。编译时会检查结构（例如有没有孤立的节点），检查点等运行参数也在这里传入。

**第一张图：把 Day06 的循环搬进来**

下面沿用 Day06 的 `SYSTEM`、`TOOLS` 和 `run_tool`，只把循环的骨架换成图。

```python
import operator
from typing import Annotated, Literal
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END

from llm import chat
from agent import SYSTEM, TOOLS, run_tool   # Day06

MAX_STEPS = 8

class State(TypedDict):
    messages: Annotated[list, operator.add]   # 追加，而不是覆盖
    steps: int
    stop_reason: str

def call_model(state: State) -> dict:
    msg = chat(state["messages"], tools=TOOLS).choices[0].message
    update = {"messages": [msg], "steps": state["steps"] + 1}
    if not msg.tool_calls:
        update["stop_reason"] = "done"
    return update

def call_tools(state: State) -> dict:
    calls = state["messages"][-1].tool_calls
    return {"messages": [
        {"role": "tool", "tool_call_id": c.id, "content": run_tool(c)} for c in calls
    ]}

def hit_limit(state: State) -> dict:
    return {"stop_reason": "max_steps"}

def route(state: State) -> Literal["tools", "hit_limit", END]:
    if state["stop_reason"] == "done":
        return END
    if state["steps"] >= MAX_STEPS:
        return "hit_limit"
    return "tools"

builder = StateGraph(State)
builder.add_node("model", call_model)
builder.add_node("tools", call_tools)
builder.add_node("hit_limit", hit_limit)
builder.add_edge(START, "model")
builder.add_conditional_edges("model", route)
builder.add_edge("tools", "model")
builder.add_edge("hit_limit", END)
graph = builder.compile()

result = graph.invoke({
    "messages": [{"role": "system", "content": SYSTEM},
                 {"role": "user", "content": "订单 A1001 和 A1002 的金额加起来是多少？"}],
    "steps": 0, "stop_reason": "",
})
print(result["stop_reason"], result["messages"][-1])
```

为了和 Day06 逐行对照，这里把模型返回的消息对象直接放进了状态。没有检查点时这样可以运行；接上检查点（Day40）以后，状态要能被序列化，应改成普通的 dict。

**与手写循环的对应关系**

| Day06 的写法 | 图里的位置 |
| --- | --- |
| `messages` 列表，每步 `append` | 状态字段 `messages`，reducer 为追加 |
| `for step in range(...)` | `tools → model` 这条边形成的环 |
| `if not msg.tool_calls: return` | 路由函数返回 `END` |
| `max_steps` 和抛出的异常 | 状态里的 `steps`，加上 `hit_limit` 节点记录停止原因 |
| 循环体里调模型、调工具 | `model`、`tools` 两个节点 |
| `print` 每一步 | 流式输出每个节点的更新（Day42） |

循环没有消失，只是从一段 `for` 代码变成了一张能画出来的图。用 `graph.get_graph().draw_mermaid()` 可以打印出它的 Mermaid 图。

**框架多给了什么**

| 能力 | 做法 | 在哪课展开 |
| --- | --- | --- |
| 持久化 | 编译时传入检查点，按 `thread_id` 保存每一步的状态 | Day40 |
| 中断 | 节点里调用 `interrupt()` 暂停，之后用 `Command(resume=...)` 继续 | Day41 |
| 流式 | 运行时按节点产出状态更新、模型 token 和自定义事件 | Day42 |
| 并行与子图 | 一个节点的多条出边在同一步并行执行；一张图可以作为另一张图的节点 | Day38 |

这些能力手写也能做，但要自己处理序列化、恢复位置和事件分发，框架把这部分工作标准化了。

**它不替你决定什么**

LangGraph 的文档明确说它不抽象提示词和架构。具体到工程上，下面几件事仍然归你：

- **业务上限。** 图有一个递归上限 `recursion_limit`，按超步计数，超过时抛出 `GraphRecursionError`；文档写明自 1.0.6 起默认值是 1000。它只是防止死循环的最后一道保护，步数、token、时间这些上限（Day45）要写在状态里，由路由函数裁决，并留下停止原因。
- **权限。** 哪个工具能被调用、以谁的身份执行，框架不管（Day41、Day59）。
- **副作用的幂等。** 恢复时节点会从头重跑（Day40），重跑安不安全取决于你的节点怎么写。
- **路由规则本身。** 条件边里写的是你的代码，模型只是提供输入。
