## Day44 - 规划模式

> 编排：工作流与受控循环 ｜ 建议用时 1 小时

> **一句话**：让模型先把步骤列出来再执行；计划要看得见、查得了、改得动。
>
> **放在全局看**：规划是自主程度最高、也最难预测的模式。它必须和 Day45 的上限、Day41 的人工确认配合使用。

### 学习目标

- 说清“先计划后执行”和“边做边定”两种做法的差别。
- 能定义一份结构化的计划，并写出执行前的校验规则。
- 知道什么情况下不该用规划。

### 核心概念

**打个比方**：像出门旅行前先列行程。有了行程才知道要订哪些票；路上遇到变化可以调整，但预算和返程日期不变。

**两种做法**

| 做法 | 过程 | 特点 |
| --- | --- | --- |
| 边做边定 | 每一步由模型根据上一步的结果决定下一步。Day06 的循环就是这种 | 灵活，能随时适应新情况；整体走向事先看不到 |
| 先计划后执行 | 模型先输出一份完整的步骤清单，再由代码逐步执行，必要时重新计划 | 计划可以展示、审批和检查；计划可能在执行中过时 |

步骤能事先写死的任务用工作流（Day35），不需要规划。规划用在步骤要看具体任务才能定的场合。

**把计划做成数据**

计划应该是结构化的输出（Day04），不能只是一段话：

```json
{
  "goal": "给订单导出接口增加按日期过滤",
  "steps": [
    {"id": 1, "action": "search_code", "input": "订单导出接口的定义位置", "expects": "找到接口文件和函数"},
    {"id": 2, "action": "read_file", "input": "步骤 1 找到的文件", "expects": "了解现有参数"},
    {"id": 3, "action": "edit_code", "input": "增加 start_date、end_date 参数和过滤逻辑", "expects": "代码修改完成"},
    {"id": 4, "action": "run_tests", "input": "订单导出相关测试", "expects": "测试通过"}
  ]
}
```

做成数据之后，四件事才成为可能：

- **给人看。** 用户或审批人在执行前看到 agent 打算做什么。
- **执行前校验。** 代码检查计划里的每个动作是否在工具白名单里、步数是否超限、有没有需要人工确认的动作。
- **跟踪进度。** 每一步的状态可以记录、可以恢复（Day40）。
- **评估。** 可以评“计划合不合理”，不必等到最后看结果。

**重新计划**

某一步的结果和 `expects` 不符时，把已完成的步骤和实际结果交给模型，让它修订余下的计划。重新计划的次数同样要有上限。

**用代码表达计划**

另一种做法是让模型写一段代码来串起多个步骤，在沙箱里执行。它适合数据处理这类步骤多、逻辑细的任务，一段代码能表达循环和条件，比一长串工具调用紧凑。代价是必须有可靠的隔离环境（Day60）。

**风险与控制**

| 风险 | 控制 |
| --- | --- |
| 计划很长，前面的小错在后面被放大 | 限制步数；关键节点设检查，结果不符就重新计划 |
| 计划里出现不该用的工具 | 执行前用白名单校验，不通过就拒绝执行 |
| 计划包含不可逆的动作 | 这类动作标记为需要人工确认 |
| 计划看起来合理但目标理解错了 | 执行前把计划展示给用户 |

模型负责提出计划，是否执行由代码和人决定。

### 动手练习

**20 分钟必做**

1. 为案例 B 的“编码”任务定义计划的结构：每一步有哪些字段，哪些动作是允许的。
2. 写出代码在执行计划前要做的三条校验规则，以及每条不通过时的处理方式。

**课后选做**

3. 回答：需求工单到合并请求这条流程里，哪一段适合规划，哪一段应该是固定工作流？

### 自检

1. 计划做成结构化数据，相比一段自然语言，多出了哪些控制手段？
2. 执行到第 3 步时发现第 1 步找错了文件，系统应该怎么办？
