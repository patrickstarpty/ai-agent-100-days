## Day42 - 流式与进度事件

> 编排：工作流与受控循环 ｜ 建议用时 1 小时

> **一句话**：图每走一步就产出一条事件，事件先存下来再推给浏览器，断线能续、刷新能重放，运行真正结束之前界面不说“完成”。
>
> **放在全局看**：这是 Day08 的进度事件在编排框架里的版本。事件流同时是界面、审计（Day62）和追踪（Day67）的原始材料。

### 学习目标

- 说出 LangGraph 运行时能流出哪几类数据，各自适合什么用途。
- 设计一条“图 → 事件表 → SSE → 浏览器”的进度链路，支持断线续传和刷新重放。
- 让界面上的状态只由终止事件决定，杜绝“连接断了就显示完成”。

### 核心概念

**打个比方**：像快递的物流轨迹：每到一站就记一条，记录存在快递公司的系统里。你什么时候打开查询都能看到完整轨迹，网断了重新打开也不会丢；只有出现“已签收”那一条，订单才算完成。

**图运行时能流出什么**

调用 `graph.stream(...)` 时用 `stream_mode` 选择要什么，可以同时选多种：

| 模式 | 内容 | 用途 |
| --- | --- | --- |
| `updates` | 每个节点执行后返回的状态更新 | 生成“检索完成”“校验通过”这类步骤事件 |
| `values` | 每一步之后的完整状态 | 调试；状态大时不适合推给前端 |
| `messages` | 模型输出的 token 和元数据 | 逐字显示回答；要求模型通过 LangChain 的集成调用 |
| `custom` | 节点里用 `get_stream_writer()` 写出的任意数据 | 自定义进度；也可以用来转发任何模型客户端的流 |
| `checkpoints`、`tasks`、`debug` | 检查点、任务开始结束等底层事件 | 排查问题，需要检查点 |

传入 `version="v2"` 后，每个分片都是 `{"type", "ns", "data"}` 的统一形状，按 `type` 分支即可（撰写时，文档注明需要 LangGraph 1.1 及以上，以官方文档为准）。文档还为新应用推荐了一套基于类型化投影的事件流接口；本课用的是更底层的 stream mode，原理相同。

Day02 的 `chat` 走的是 litellm，不经过 LangChain 的模型类，`messages` 模式拿不到它的 token。做法是在节点里自己消费流，再用 `custom` 写出去：

```python
from langgraph.config import get_stream_writer
from llm import chat

def answer(state) -> dict:
    writer = get_stream_writer()
    writer({"kind": "progress", "text": "正在生成回答"})
    parts = []
    for chunk in chat(state["messages"], stream=True):
        delta = chunk.choices[0].delta.content if chunk.choices else None
        if delta:
            parts.append(delta)
            writer({"kind": "token", "text": delta})
    return {"answer": "".join(parts)}
```

**先存事件，再推送**

运行放在后台 worker 里（Day72），HTTP 连接只负责读事件。这样浏览器关掉，任务照样跑完；连接断开再连回来，也能接着看。

事件表至少包含：`run_id`、`seq`（同一次运行内单调递增）、`type`、`payload`、`created_at`。worker 把图的输出翻译成事件写进去：

```python
def run_and_record(run_id: str, inputs: dict, config: dict) -> None:
    record(run_id, "run_started", {})
    try:
        for part in graph.stream(inputs, config=config, stream_mode=["updates", "custom"], version="v2"):
            if part["type"] == "custom":
                if part["data"]["kind"] != "token":          # token 只推送，不入库
                    record(run_id, "progress", part["data"])
            else:
                for node in part["data"]:
                    if not node.startswith("__"):           # 跳过框架内部的键
                        record(run_id, "step_done", {"node": node})
    except Exception as e:
        record(run_id, "run_failed", {"error": type(e).__name__})
        return
    snap = graph.get_state(config)                           # 需要检查点
    if snap.next:                                            # 还有待执行的节点：停在了人工确认
        record(run_id, "waiting", {"at": list(snap.next)})
    else:
        record(run_id, "run_finished", {"stop_reason": snap.values["stop_reason"]})
```

token 数量大、单个价值低，通常只实时推送、不逐个入库；入库的是步骤事件和最终结果。刷新后的重放看到的是完整步骤和最终回答，不再逐字播放。token 的推送需要一条进程内或消息队列的实时通道，下面的示例只演示入库事件这一条线。

**进阶：用 SSE 送到浏览器**

这一节讲怎样把事件表里的记录送到浏览器，属于前端接入细节，第一次学可以先跳过，回头用到时再看。SSE（Server-Sent Events）是一种单向的 HTTP 流，响应类型为 `text/event-stream`，每条消息由 `id:`、`event:`、`data:` 几行加一个空行组成。浏览器的 `EventSource` 断线后会自动重连，并在重连请求里带上 `Last-Event-ID` 头，值是它收到的最后一条 `id`。

```python
import json
import time

STREAM_END = {"run_finished", "run_failed", "waiting", "cancelled"}

def sse_events(run_id: str, last_event_id: str | None):
    after = int(last_event_id or 0)
    idle = 0
    while True:
        events = load_events(run_id, after_seq=after)     # 从事件表按 seq 读取
        for ev in events:
            after = ev["seq"]
            payload = json.dumps(ev["payload"], ensure_ascii=False)
            yield f"id: {ev['seq']}\nevent: {ev['type']}\ndata: {payload}\n\n"
            if ev["type"] in STREAM_END:
                return
        idle = 0 if events else idle + 1
        if idle and idle % 15 == 0:
            yield ": ping\n\n"                             # 注释行保活，防止中间代理断开空闲连接
        time.sleep(1)
```

把这个生成器交给你所用 Web 框架的流式响应即可。断线续传靠 `Last-Event-ID` 自动完成；刷新页面时新建的 `EventSource` 不带这个头，于是从头重放，界面能还原到当前进度。事件表里的 `run_id` 要做权限校验，只有发起人或有权限的人能读。

**没结束就不说“完成”**

界面的状态只由事件决定，并且只有终止事件能改变“是否结束”：

| 界面看到的情况 | 应显示 |
| --- | --- |
| 连接断开、正在重连 | “连接中断，正在重连”，进度保持原样 |
| 收到 `waiting` | “等待审批”，并给出审批入口（Day41） |
| 收到 `run_finished` | 按 `stop_reason` 区分“已完成”和“已达到步数上限”（Day45） |
| 收到 `run_failed` 或 `cancelled` | 明确的失败或已取消，以及已经执行过的步骤 |

HTTP 流结束、最后一个 token 到达，都不等于运行结束。回答文本流完之后可能还有引用校验节点，校验失败会改写结果；在 `run_finished` 到来之前，界面上的回答只能标成“生成中”。
