## Day45 - 有界循环：预算与停止条件

> 编排：工作流与受控循环 ｜ 建议用时 1 小时

> **一句话**：agent 可以自己决定怎么做，但做多少步、花多少钱、用多久，由你的代码说了算。
>
> **放在全局看**：上限是 agent 能上生产的前提，也是成本可预测的来源。

### 学习目标

- 为 agent 循环定出明确的上限。
- 设计一套用户和排查人员都能看到的停止原因。

### 核心概念

**打个比方**：像给出差的同事定预算和返程日期：行程他自己安排，超了预算或到了日期就得回来汇报。

**四个上限**

一个可上线的 agent 循环至少有这四个上限：

| 上限 | 说明 |
| --- | --- |
| 步数 | 最多多少次“思考 → 调用工具 → 观察” |
| token | 一次任务累计可用的 token |
| 时间 | 在线任务的延迟预算，超出后转为后台任务或停止 |
| 工具调用 | 每类工具的调用次数上限，高风险工具更低 |

上限写在状态里（Day37），每一步检查，由代码裁决。模型可以建议“还需要再查一次”，是否允许由预算决定。

**停止原因要显式记录**

建议用一个枚举：完成、达到步数上限、预算耗尽、等待人工、权限变更、工具失败、被取消。停止原因写进任务记录和追踪，界面上也要显示。达到上限时如实告知“已达到步数上限，以下是目前的结果”，不能把截断的结果当作完成。

**控制流属于你的代码**

《12-Factor Agents》里有三条与此直接相关：

- 掌握自己的控制流：循环、重试、暂停由你的代码决定，不交给框架的黑盒。
- 小而专注的 agent：范围小，上下文就短，行为就稳定。
- 把 agent 做成无状态的归约函数：给定当前状态和一个事件，返回新状态。状态在外部持久化，agent 本身可以随时重启。

**数值怎么定**

先从追踪数据里看真实任务用了多少步和多少 token，把上限定在覆盖绝大多数正常任务的位置，再留一点余量。上限定得过宽等于没有，过窄会让正常任务频繁被截断。定好之后，每个上限都要有一条测试证明它确实生效。
