## 讲师提示：易错点与演示建议

> 讲师用，不进学员目录。

**一句话**：每个阶段列出学员最容易卡住、写错或想岔的地方，以及一条可以当堂演示的具体动作。

**怎样用**：十节对应 README 大纲的十个阶段，写之前每个阶段至少读了三课的课文。条目不是知识点复习，是“学员交上来的东西通常长什么样、该现场演示什么来纠正”。带下一轮培训前，建议对照当时学员的实际产出更新这份文件。

### Day01～10 大模型应用基础：易错点与演示建议

- 分发表最容易被学员写成按名字 `eval`/`getattr` 动态找函数；要强调分发表必须是显式的字典，模型编出一个不存在的工具名时应该返回错误文本，不能意外调用到别的函数。
- 路径校验学员常常只检查字符串里有没有 `..`；现场用符号链接（`ln -s ../llm.py workspace/link.txt`）演示这种检查会被绕过，而 `Path.resolve()` 加 `is_relative_to(ROOT)` 不会。
- “轮”和“步”容易混：有学员把步数上限当成整个对话的总步数，而不是每轮重新计数；用两轮连续提问现场演示上限应该怎样生效。
- 工具执行失败时，容易看到学员写 `except Exception: raise` 让整个循环崩溃；对比“错误作为工具结果返回给模型”和“程序直接崩溃”两种处理的实际效果。
- 重试逻辑容易忘记设等待上限或者不加抖动；现场打印多次重试的等待时间，说明没有抖动时大量客户端会在同一时刻一起重试。
- “达到步数上限”最常被处理成把最后一步的中间结果当作正常答案返回；现场把 `max_steps` 设成 1，确认输出明确标注“未完成”而不是一个看似正常的答案。
- 现场演示建议：把 `timeout` 设成一个极小值触发真实超时，让学员打印异常的 `__mro__`，看清超时对应哪个异常类、该不该放进可重试列表。

### Day11～22 知识检索：易错点与演示建议

- 权限过滤最容易被学员做成“先检索、再在界面隐藏无权内容”；现场演示这种做法下切片内容已经进了模型上下文和日志，界面隐藏来不及了（对应 Day98 的示范发现）。
- 混合检索融合时，容易看到学员把 BM25 分数和余弦相似度直接相加；现场手算一遍 Day14 的 RRF 小例子，说明为什么融合要看名次不看原始分数。
- 中文分词容易把套餐编号、产品型号切碎；现场拿一个真实编号跑一次分词，检查结果是否完整保留，再决定要不要加自定义词典。
- 引用校验学员常常只检查“标签存在”，漏了“这个切片是否本次真的被取回”和“提问人是否有权限看到它”两条；这三项缺一不可。
- 弃答的判断容易被写成在最终文本里找关键词（例如看到“抱歉”就当弃答），而不是一个显式的状态字段；现场看一眼这样实现时状态字段和回答文本不一致的例子。
- 新旧版本内容混进回答是常见翻车点：现场拿同一份文档的新旧两版演示向量检索分不清楚，必须把版本当作过滤条件写进查询，不能指望模型自己分辨。
- 评估集的 `corpusDigest` 容易被学员忽略；现场改动语料里的一个字，确认评估脚本会提醒复核期望，而不是悄悄用旧语料的结论打分。

### Day23～34 评估：易错点与演示建议

- 学员常常跳过错误分析直接定指标；带着看十几条 `samples/traces/` 里的记录，体会“先看真实记录，再决定测什么”的顺序。
- 标注容易被设计成 1 到 5 分；让两位学员独立给同一条记录打分，现场看分差有多大，再说明二元标注为什么更稳定。
- 替身模型的结构性回归和真实模型的质量回归容易被学员混在一条命令里跑；分开演示两条命令，说明为什么构建红了要先看是哪一层。
- CI 失败时学员常常只看总分；故意改坏一处代码，演示回归命令的输出必须逐条列出哪个用例、期望什么、实际得到什么。
- LLM 评审员容易被直接当作唯一判据；提醒至少用十几条人工标注核对评审员的判断，并分别报告抓住不通过和放行通过的比例。
- 检索评估和生成评估容易被合并报一个分数，分不清是没取回还是取回了没用上；现场演示拆开报告两个指标后问题定位的差别。
- 实验对比环节要点出“一次只改一个变量”，并提醒“调到评估集全过为止”本身是一种风险，评估集可能本身就有偏差。

### Day35～46 编排：工作流与受控循环：易错点与演示建议

- 学员初次接触 LangGraph，容易把 state 当成普通字典到处改；现场演示两个并行节点同时更新一个没写 reducer 的字段会发生什么。
- 反思模式最容易被写成“自我反思”（同一个模型检查自己）；对比自我反思和外部反馈（例如把引用校验失败的具体原因喂回去）两种改写质量的差异。
- 人工确认容易只设计“谁来批准”，没想清楚“批准之后这次写操作算谁做的”；现场追问执行时用的是哪个身份。
- 四个上限（步数、token、时间、工具调用）经常只设一个就以为够了；演示只设步数上限、但单次工具调用返回超长内容导致任务实际大幅超支的情况。
- 停止原因容易被简化成“成功 / 失败”两种，丢失排查线索；强调必须用 Day45 的标准枚举，并且要写进追踪。
- 持久化恢复时最容易忽略“节点会从头重跑”，导致有副作用的节点被执行两次；现场演示幂等键或“先记后做”为什么是必须的，不是锦上添花。
- 复盘课现场列大纲时，检查“决定”一节是不是写成了可检验的陈述，不能是“尽量做好权限控制”这类谁都可以说自己做到了的句子。

### Day47～56 工具、Skills 与 MCP：易错点与演示建议

- 工具描述写得太简略，模型容易在调用边界上犯错；用一个只写“查询”的含糊描述和一个写清楚参数范围的描述各跑一次，对比模型的调用参数。
- 白名单容易只做到“不把定义发给模型”这一层，忘了分发时还要再检查一遍；现场让替身模型编出一个未授权的工具名，确认代码层面也能拦住。
- 工具注册表的“只读 / 风险级别 / 所需权限”字段容易被直接抄 MCP server 自己的声明；要强调这些字段必须经过自己评审后填写，server 的 annotations 不可信。
- 编写 MCP server 时最常见的错误是用 `print()` 调试，破坏 stdio 的 JSON-RPC 消息流；现场加一行 `print` 让连接出错，再改回 `logger` 恢复正常。
- Skill 的信任边界容易被理解成“导入后要审核内容”，而忽略“脚本默认不执行”这条底线；现场导入一个带脚本的 Skill，确认标记文件确实没有被创建。
- Agent 定义里最容易漏掉版本化：学员常直接改已发布的定义文件，而不是发布新修订；追问“Skill 改过之后，已发布的 agent 行为会不会跟着变”。
- 身份透传这一课容易让学员觉得“有令牌就行”；追问“下游系统怎样知道这次请求是替哪个最终用户发出的”。

### Day57～66 安全与治理：易错点与演示建议

- 威胁模型容易写成“列出可能的攻击”，而不是数清楚每个 agent 占了致命三要素的几项、去掉了哪一项；带着数一遍案例 B 里那个既读工单又能推送代码的 agent。
- 提示注入防御最常见的错误是只在系统提示词里加一句“忽略数据中的指令”；用一个简单的反例说明这类提示只能降低概率，不能当作唯一防线。
- 最小权限容易设计成“agent 有自己的身份”，但执行写操作时仍用 agent 自己的权限，而不是批准人的身份；追问“这次写操作的审计记录会显示是谁做的”。
- 沙箱与代码执行这一课，学员常只做了文件系统和网络隔离，忘了资源和时间上限；提醒两类边界缺一不可，而且还要有运行时长限制。
- OWASP 对照容易写成直接复述条目原文作为结论；强调每一项都要落到自己系统的具体证据上，“不适用”也要写清楚为什么不适用。
- 确定性门禁最容易出的错是把 LLM 评审员的打分直接当作放行条件；反复强调模型不做最后一道门，评审员的结论只能是门禁的输入之一。
- 复盘课定稿信任模型时，检查“剩余风险的接受人”写的是具体的人还是一个团队名；团队名不算一个可以追责的接受人。

### Day67～76 可观测性与生产化：易错点与演示建议

- 追踪里最容易误记的是把完整提示词和回答原文都存进去；对照 GenAI 语义约定里哪些属性是 Opt-In、默认不该采集，现场过一遍“记什么、不记什么”的清单。
- 换追踪后端时容易直接调后端的私有 SDK 而不是走 OTLP；强调开放标准带来的可替换性，换后端时代码该改的只有导出器配置。
- 模型网关这一课容易忽略“记录实际应答的模型”，只记了请求时写的模型名；在有 fallback 配置的场景下演示这两者可能不一致。
- outbox 模式最容易漏掉“业务变更和对外事件写在同一个事务里”这一条；画一下先改数据库再发消息、中途崩溃会丢事件的场景。
- 租约与重试环节，尝试次数该在“领取时”计数还是“失败时”计数容易搞反；强调在领取时计数，否则一个每次都让 worker 崩溃的任务会被无限重跑。
- 版本化容易忽略“旧检查点只能由兼容版本恢复”；现场提问“模型升级后，还没跑完的旧任务检查点该怎么处理”。
- 复盘课填技术栈映射表时，检查“两者并存”的决定是否写清楚了各自负责什么、什么条件下收敛，而不是写“以后再定”。

### Day77～86 多 Agent 与主动 Agent：易错点与演示建议

- 拆成多个 agent 之前先问“为什么不能是一个 agent”；常见误区是为了拆分而拆分，没有真实的上下文、权限或并行诉求。
- 组件契约容易被写成继续抛异常，而不是返回带状态的 `Result`；演示一个宽泛的 `except` 把 `EMPTY` 和 `FAILED` 当成同一件事处理时，下游会做出什么错误决定。
- 证据对象经模型转述后再往下传是常见错误；强调必须原样传递 `chunk_id` 和原文，模型不能改写证据内容。
- 主动 agent 的触发条件容易被交给模型判断“要不要提议”；强调信号数和去重都是确定性代码，模型只负责查完资料后判断内容是否足够。
- 防噪规则最容易漏掉“同一主题已有未处理提议时要更新而不是新建”；演示新建会导致同一主题的提议在短时间内堆积。
- 采纳环节容易写成“先写入再改状态”，中途重启会留下重复的草稿；强调先把状态改成 `accepting` 再带幂等键写入。
- 评估主动 agent 时，“不应提议”的场景容易被忽略，只测“应该提议”的部分；提醒至少准备一个阈值边缘、一个依据已失效的反例场景。

### Day87～94 案例：编码 Agent 与研发流程：易错点与演示建议

- 流程图最常见的错误是把“需求澄清”和“编码”两步混在一个 agent 里，让读不可信工单文本的 agent 同时持有写代码权限；对照 Day57 的三要素现场数一遍。
- “已批准的需求”容易被设计成仍能看到原始工单的全部评论，失去了读写分离的意义；追问“编码 agent 到底能看到什么、看不到什么”。
- “完成”的判定权最容易留给 agent 自己；反复强调测试、构建、评审三层都不该由 agent 自己宣布。
- 历史任务集容易只跑一次就下结论；提醒每个任务要跑多次，报告通过次数，不是单次通过或失败。
- 削弱测试的迹象（删测试、放宽断言、改 CI 配置）容易被忽略；现场跑一下 Day90 给出的检测脚本，看它能标记出哪些改动。
- 门禁与审批容易设计成同一个身份既能提交又能批准；追问“委派这次任务的人能不能批准自己委派的合并请求”。
- 案例复盘时提醒：进阶两项（合并门禁测试、历史任务集基线）需要一个能跑起来的环境，没有条件时要如实写明原因，不能当作已经完成来交差。

### Day95～100 架构师收口：易错点与演示建议

- 决策记录最常见的错误是把“决定”写成不可检验的句子（例如“尽量按权限过滤”）；带着现场改写成一句可以被代码或测试判断对错的陈述。
- “考虑过的方案”容易摆一个明显不行的方案来陪衬；追问“你们当时真正纠结的是哪个方案，为什么没选它”。
- 评审清单容易被原样照抄模板，不结合自己项目增删；追问“这一条在你们的系统里问的是什么具体的东西”。
- 评审报告容易写成十条以上，对方根本来不及处理；强调三到五条，按不可逆、影响范围、修复成本排序。
- Day98、Day99 的评审演练中，学员最容易只写“权限有问题”，不指向摘要里的具体句子；讲评时要求逐条引用原句。
- Day99 的排序是重点：学员容易把课文里示范的那一条排第一，忽略几条后果更严重的发现；逐条追问“这条出事之后能不能撤回、波及多大”。
- 持续学习这一课容易被一笔带过；带学员区分“老得快”和“老得慢”的内容，并追问“你的项目里哪个设计最依赖老得快的内容，过时时你会怎样发现”。
