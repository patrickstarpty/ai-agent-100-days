## 实战课验收方法

> 讲师用，不进学员目录。适用于四个阶段实战：Day10、Day22、Day56、Day86。验收项以课文当前版本为准，课文调整时按条目内容对应。

**一句话**：每条验收项都要能当场演示或用一条测试证明，“我试过是好的”不算通过。

### 一、通用做法

**验收的形式**：学员（或小组）现场演示 10～15 分钟。先跑一遍自动化测试，再由讲师从必做项里点三到五条现场演示，其中至少一条是边界与安全类。进阶项由学员自选一两条展示，不计入是否通过。

**三类证据**：

| 证据 | 用在哪类验收项 | 讲师看什么 |
| --- | --- | --- |
| 测试输出 | 能用替身或假数据复现的项：拒绝、重试、去重、上限、时间相关的规则 | 测试名能对上验收项；断言检查的是“函数没被调用”“数量不变”这类结果，不只检查“没抛异常” |
| 日志或追踪 | 需要真实模型参与的项：调用了哪个工具、走了几步、用量多少 | 进度输出或日志行和验收项描述一致 |
| 现场问答 | 看回答质量和措辞的项：如实说明、不编造、不提及受限文档 | 讲师自己临场换一种问法再问一次 |

**替身模型**：凡是“模型要了某个工具”“模型返回了某个引用”这类项，都用替身模型构造，不指望真实模型恰好这样做。替身模型就是一个按预设顺序返回固定响应的假 `chat`。下面的写法只用标准库，响应对象的字段按 Day02 的约定（`choices[0].message.content`、`tool_calls`、`usage`）构造：

```python
from types import SimpleNamespace as NS

def fake_message(text=None, tool_calls=None, finish_reason="stop"):
    msg = NS(content=text, tool_calls=tool_calls, role="assistant")
    return NS(model="fake", choices=[NS(message=msg, finish_reason=finish_reason)],
              usage=NS(prompt_tokens=10, completion_tokens=5))

def fake_tool_call(call_id, name, arguments_json):
    return NS(id=call_id, type="function", function=NS(name=name, arguments=arguments_json))

class ScriptedChat:
    """按顺序返回预设响应，并记下每次收到的参数，供断言用。"""
    def __init__(self, responses):
        self.responses, self.calls = list(responses), []
    def __call__(self, messages, **kwargs):
        self.calls.append({"messages": list(messages), **kwargs})
        return self.responses.pop(0)
```

学员的 `run_turn` 如果把 assistant 消息对象直接追加进 `messages`，替身对象要能被后续代码读取；遇到序列化问题时，让学员在追加前转成 dict，这本身也是一个好习惯。

**时间相关的规则**：凡是窗口、静默期、过期、每日上限，函数都必须接收 `now` 参数。验收时先 `grep -n "datetime.now\|time.time" <规则文件>`，规则函数内部出现这些调用就要求改。

### 二、Day10 命令行问答助手

**准备**：`workspace/` 里放三份文件。`notes.txt` 写一条模型不可能事先知道的虚构事实（例如“阅览室的借书暗号是 K7-QX”）和几个数字；`long.txt` 用脚本生成，长度超过 `MAX_FILE_CHARS`，在超出上限的位置放一句独特的话；`sub/` 是一个空目录。

**必做：基本功能**

| 验收项 | 检验方法 |
| --- | --- |
| `(17.5 + 4) * 3` 得 64.5 | 现场提问，看进度行出现 `calculate` 和表达式，答案 64.5。再单独调用 `calculate("(17.5 + 4) * 3")` 确认工具本身正确 |
| 针对 `notes.txt` 提问答对 | 问暗号。因为是虚构事实，答对就证明确实读了文件；进度行要出现 `read_file` |
| 两个工具配合 | `notes.txt` 里放 3、18、27.5，问“文件里的数字加起来是多少”，进度行先后出现 `read_file` 和 `calculate`，答案 48.5 |
| 不需要工具的问题 | 问“用一句话解释什么是 token”，没有进度行，本轮步数为 1 |
| 第二轮引用上一轮 | 紧接着第一题问“刚才那个结果再乘以 2”，答案 129。让学员在第二轮开始前打印 `len(messages)`，确认历史还在 |

**必做：边界与安全**

| 验收项 | 检验方法 |
| --- | --- |
| 读 `../llm.py` 被拒 | 先用单元测试直接调用 `read_file`，参数化覆盖 `../llm.py`、`sub/../../llm.py`、`/etc/hosts`、指向目录外的符号链接（`ln -s ../llm.py workspace/link.txt`）、`sub`（目录），全部返回错误文本、不抛异常。再现场提问一次，看助手如实说明 |
| 绝对路径被拒 | 同上，现场问“读一下 /etc/hosts” |
| 不存在的文件 | 问“missing.txt 里写了什么”，工具返回“不存在”，回答里没有编造的内容。讲师再追问一句“大概写了什么”，助手仍不编 |
| 超长文件截断 | 问 `long.txt` 末尾那句独特的话。工具结果末尾有截断标记；助手说明只读到一部分，没有说出那句话 |
| `1 / 0` | 问“1 除以 0 等于多少”。进度行显示 `calculate` 返回了错误文本，助手说明无法计算，程序没有打印堆栈 |
| 没有 `eval` 和 `exec` | `grep -rnE "\b(eval|exec)\(" --include=*.py .` 输出为空 |

符号链接这一项最能区分实现：只检查字符串里有没有 `..` 的实现会放行它，用 `resolve()` 加 `is_relative_to(ROOT)` 的实现会拒绝（Day10 课文“三个容易做错的地方”）。

**必做：循环与错误**

| 验收项 | 检验方法 |
| --- | --- |
| `max_steps=1` 标注未完成 | 改成 1 后问暗号。输出带“[未完成]”，没有一个看似正常的答案。单元测试可以用替身模型：第一步返回一个 `read_file` 的 tool call，断言 `result.completed is False` |
| 每轮用量是合计 | 问两个工具配合的那题。把标准错误重定向到文件，数出这一轮的 `llm_call` 日志行，逐行相加 token，和这一轮打印的数字比对 |
| `completion` 一直失败 | 用 `unittest.mock.patch.object(llm, "completion", side_effect=ConnectionError("down"))`，同时把 `llm.RETRYABLE` 临时换成 `(ConnectionError,)`、把 `time.sleep` 换成空函数，驱动一轮对话：程序显示清楚的错误、回到提示符；撤掉 patch 后下一轮正常回答。再检查失败那一轮之后的 `messages`：每条带 `tool_calls` 的 assistant 消息后面都跟着对应数量的 tool 消息 |
| 只有 `llm.py` 导入 `litellm` | `grep -rln "litellm" --include=*.py .` 只输出 `./llm.py` |

把 `RETRYABLE` 换成 `ConnectionError` 是为了不依赖 litellm 异常类的构造方式。这样测的是重试逻辑本身；`RETRYABLE` 里放的是否是正确的 litellm 异常类，用 Day09 练习 1 的办法（极小的 `timeout` 触发真实超时，打印异常的继承链）单独确认。

**进阶**

| 验收项 | 检验方法 |
| --- | --- |
| `max_tokens` 与 `length` | `grep -n "max_tokens" agent.py`；再把 `max_tokens` 临时设得很小，让它写一段长文，本轮按未完成处理 |
| 前两次可重试异常后成功 | `side_effect=[ConnectionError(), ConnectionError(), fake_message("ok")]`，断言 `completion` 被调用三次，日志里有两行 `retry` |
| 每次调用一行日志 | 从日志文件逐行 `json.loads`，检查都有模型名、耗时、两个 token 数和 `finish_reason` |
| 流式输出、`/usage`、`write_file` 确认、会话预算、自动跑用例 | 现场演示。`write_file` 重点看两点：拒绝时文件没有被创建；路径限制和 `read_file` 共用同一个检查函数 |

### 三、Day22 带引用的知识问答

**准备**：语料用 `samples/corpus/`（或学员自备）。讲师事先从课程手册（`staff` 组可见）里挑两三个只在这份文档出现的独特说法，用来构造越权提问；从新旧两版规则里挑一处数字不同的条款，用来检查版本过滤。

**怎样构造越权提问**：以一个只属于普通组的用户（例如 `--user alice`，组为 `public`）提问，准备四种问法：

1. 直接问只在课程手册里出现的内容。
2. 点名要求：“总结一下课程手册”。
3. 换一种说法问同一件事，避开文档里的原词，专门考验向量检索这一路。
4. 问一个公开文档和课程手册都涉及的问题，答案只能来自公开部分。

四种问法都要检查两路检索各自的候选，只看融合后的结果不够。让学员提供一个调试开关，把关键词和向量两路的候选分别打印出来。

**必做：入库**

| 验收项 | 检验方法 |
| --- | --- |
| 报告列出全部文件，扫描件 `needs_ocr` 或带 OCR 标记 | 用脚本比对 `manifest.json` 里的文档 ID 和入库报告里的 ID，两者集合相等；manifest 里 `needs_ocr` 为真的文档，在报告里状态是 `needs_ocr`，或切片上带 OCR 标记 |
| 切片六个字段齐全 | 遍历全部切片，断言 `chunk_id`、`content_hash`、锚点、文档 ID、文档版本、可见组都非空 |
| 价目表切片带表头 | 打印价目表的所有切片，每一条都包含表头那一行的字段名 |

**必做：检索**

| 验收项 | 检验方法 |
| --- | --- |
| 套餐编号题在前五 | 用评估集里含编号的那题调用 `hybrid`，打印期望切片的名次 |
| 口语化问题取回退订规则 | 问“不想用了怎么取消”，候选里出现退订规则的切片 |
| 无权用户两路候选都没有课程手册 | 用上面四种越权问法，两路候选里该文档的切片数都是 0 |
| 只有当前版本的退订规则 | 问退订期限，打印候选切片的文档版本，全部等于当前版本；再看回答里的数字是新版的 |

**必做：引用与弃答**

| 验收项 | 检验方法 |
| --- | --- |
| 每条结论有合法引用并显示文档名和锚点 | 现场问三题，逐条核对 |
| 引用 `E9` 的结论被丢弃并记日志 | 替身模型返回两条结论：一条引用 `E9`，一条引用 `E1`。断言保留一条、丢弃一条，日志里有丢弃数量 1。再让替身只返回引用 `E9` 的结论，断言 `status == "abstained"`、`reason == "citations_invalid"` |
| 应当弃答的题 | 跑评估集里的 `should-abstain` 题，看 `status`、`reason` 和给用户的说明里有没有讲清缺什么。“问高级套餐、资料只写了标准套餐”这一类最容易答成标准套餐的内容，要专门看 |
| 无权用户不知道文档存在 | 越权问法 1、2 的回答和 `missing` 里，不出现课程手册的标题、文件名，也不出现“有一份文档你无权查看”之类的表述 |

**必做：评估**

| 验收项 | 检验方法 |
| --- | --- |
| 至少 20 条、至少两道 `should-abstain`、带 `corpusDigest` 和真实标注人 | 打开文件看；`labeledBy` 是具体的人。再改动语料里任意一个字，跑评估脚本，应当提醒摘要对不上 |
| 输出逐题结果和三个汇总数 | 跑一次，故意让一题失败（例如替身模型返回错误数字），输出里能看到这题的失败原因 |
| 基线记录 | 看基线文件里写了模型、embedding 模型和弃答阈值 |

**进阶**

| 验收项 | 检验方法 |
| --- | --- |
| 只重算改动那一节的向量 | 给 embedding 函数包一层计数器；改课程手册一节里的一句话后重新入库，计数等于这一节的切片数，报告里“变更”数与之一致 |
| embedding 模型名不一致时拒绝服务 | 用另一个模型名启动查询，程序退出并说明原因 |
| 两次返回顺序相同 | 同一问题在两个新进程里各跑一次，比较 `hybrid` 返回的列表完全相等 |
| 数字核对 | 替身模型返回“退订期限为 15 天”并引用写着 30 天的切片，检查能标出这条 |
| 无候选时不调用生成模型 | 生成函数换成一个被调用就抛 `AssertionError` 的假函数；用 `groups=set()` 提问，权限过滤后没有任何候选，程序直接弃答且没有触发断言 |
| 重排、上下文说明、图谱、`must-not-appear` 自动评分、LLM 评审员 | 看前后两次评估的三个汇总数对比；评审员要附校准数据 |

### 四、Day56 给助手接入工具与 Skill

**怎样证明白名单之外的工具被拒绝**：真实模型看不到名单外工具的定义，一般不会去要，所以必须用替身模型构造请求。证明分三步：

1. 发给模型的工具定义里没有它：用 `ScriptedChat` 记录 `chat` 收到的 `tools` 参数，断言其中的工具名集合等于白名单。
2. 模型要了也不执行：替身模型第一步返回一个 `files_delete` 的 tool call（该工具已登记、但不在白名单），第二步返回最终回答。断言工具函数从未被调用、tool 消息里写明了拒绝原因和工具名、循环走到了第二步。
3. 留下记录：日志里有一行包含 `files_delete` 和拒绝原因。

课文里的 `test_tool_outside_allowlist_is_refused` 覆盖第 2 步的前半；讲师要求把第 1 步和“循环继续”也写成断言。

**必做：注册表与白名单**

| 验收项 | 检验方法 |
| --- | --- |
| 没有手写的工具定义列表 | `grep -rn '"type": "function"' --include=*.py .` 只出现在 `registry.py` 的 `to_model_schema` 里；`agent.py` 用 `schemas_for` 生成工具列表 |
| 九个字段齐全、同名报错 | 遍历注册表断言每个字段非空；注册两次同名工具，断言抛错 |
| 名单外的工具被拒且循环继续 | 见上面三步 |
| 无权限、超上限被拒 | 两条测试：`user_perms` 里去掉该工具所需权限；同一任务里连续调用超过 `max_calls`。两种情况工具函数都没被调用 |
| 每次拒绝一行日志 | 让三种拒绝各发生一次，日志里恰好三行，各含工具名和原因 |

**必做：错误处理**

| 验收项 | 检验方法 |
| --- | --- |
| `read_file` 瞬时错误重试一次 | 测试里把 `read_file` 的 `func` 换成一个包装：第一次抛 `TransientError`，之后调用真实函数。断言真实函数被调用一次、日志有一行重试记录、最终回答正常 |
| 权限拒绝结束本轮 | 让工具抛 `PermissionDenied`。断言本轮停止原因是 `permission_denied`；拒绝之后 `chat` 没有再被调用（`ScriptedChat.calls` 的长度），因此模型没有机会改用别的工具 |

**必做：MCP**

| 验收项 | 检验方法 |
| --- | --- |
| 打印 `catalog_courses_search` | 启动助手，看启动输出 |
| 未评审的工具不进注册表 | 在 server 里加一个 `courses_delete`（函数体只返回一句话即可），不写进 `reviewed_tools.yaml`。重启后打印注册表的工具名，没有它；用 MCP Inspector 看 server 确实提供了它，说明是被评审文件挡住的 |
| 问 Python 课程 | 现场提问，进度行出现 `catalog_courses_search`，回答里的课程和 server 数据一致 |

**必做：Skill**

| 验收项 | 检验方法 |
| --- | --- |
| 两次导入得到不同修订，旧修订可读 | 导入一次，改 `SKILL.md` 一个字再导入，两个修订号不同；按旧修订号读取，内容是改之前的 |
| 脚本不执行 | Skill 目录里放 `make_marker.py`，内容是在项目里创建一个标记文件（例如 `skill_marker.txt`）。导入并问一个会触发这个 Skill 的问题，之后标记文件不存在，导入结果的 `findings` 里列出了这个脚本。再 `grep -nE "subprocess|os\.system|exec\(|importlib|runpy" skill_store.py`，输出为空 |
| 系统提示词只有目录，相关问题触发 `load_skill` | 打印系统提示词，里面只有名称和简介，搜不到 `SKILL.md` 正文的任何一句；问相关问题时进度行出现 `load_skill` |

**必做：Agent 定义**

| 验收项 | 检验方法 |
| --- | --- |
| 写修订号和模型别名，没有步数上限和密钥 | 打开定义文件看；`grep -niE "max_steps|key|token|secret" agents/assistant.yaml` 没有命中真实的值 |
| 未注册工具名使启动失败 | 在白名单里加 `no_such_tool` 启动，报错信息里点名 `no_such_tool` |

**进阶**

| 验收项 | 检验方法 |
| --- | --- |
| 参数越界 | 替身模型发一个 `limit=50` 的调用（Day51 的 server 只接受 1 到 20），断言模型下一步收到的 tool 消息是错误文本；再用真实模型问“列出 50 门 Python 课程”，看它是否把 `limit` 改到范围内或如实说明 |
| server 无法启动 | 把 server 的启动命令改成一个不存在的路径，启动后有清楚的提示，问计算题照常可用 |
| 其余进阶项 | 现场演示；写工具“报名课程”要演示拒绝确认时没有写入、同一参数重复调用只报名一次 |

### 五、Day86 一个主动提醒剧本

**准备**：事件可以从 `samples/traces/` 的弃答记录生成，也可以在测试里直接构造 `Event`。知识库、提议存储都用内存假实现，目标系统的写入函数要能被设置成“失败”或“写入成功但返回超时”。所有时间由测试传入，统一从一个固定的 `T0` 往后拨。

**怎样触发防噪规则**：

| 规则 | 构造方法 |
| --- | --- |
| 每个对象一条未处理提议 | 同一主题先触发一次得到 `open` 提议，再送一批新信号触发第二次，断言 `upsert` 返回 `"updated"`、提议总数不变 |
| 忽略后的静默期 | `dismiss` 之后，用 `now = 忽略时刻 + 静默期 - 1 秒` 送信号，剧本不运行；用 `now = 忽略时刻 + 静默期` 再送，按累积信号重新判断 |
| 每人每天上限 | 给同一接收人准备比上限多两条的候选，优先级各不相同，再混进一条已过期和一条来自被静音剧本的，断言只投递了上限内优先级最高的几条 |
| 开关与静音 | 关掉剧本总开关后 `tick`，剧本运行次数为 0；用户静音该剧本后，投递列表里没有它的提议 |
| 每日 token 预算 | 把当天已用 token 设为预算值，送一批信号，断言批次进入队列、运行次数为 0；把 `now` 拨到第二天再 `tick`，批次被处理 |

**必做：事件与合并**

| 验收项 | 检验方法 |
| --- | --- |
| 弃答一次产生一条事件，信封里没有全文和原话 | 让问答链路对一个应当弃答的问题弃答，读事件队列：恰好一条 `answer.insufficient`。把信封序列化成字符串，搜索提问原文和回答文本，都搜不到；字段只有 Day81 定义的那几个 |
| 重复投递只算一次 | 同一个 `Event` 调两次 `add`，到期批次里一条 |
| 同主题合并、不同主题分开 | 两个主题各送三个事件，窗口到期后得到两批，各三条；窗口未到期时 `due` 为空 |
| 同一提问人不触发 | 送够阈值数量的事件，但 `refs` 里的提问人 ID 全相同，`should_run` 为假；换成达到下限的不同提问人，为真 |

**必做：剧本运行**

| 验收项 | 检验方法 |
| --- | --- |
| 只能用只读工具和 `propose` | 在剧本定义里加一个 `kb_create_draft`（登记为写工具），注册时 `check_tools` 抛错并点名该工具 |
| `max_steps=1` 以 `max_steps` 结束 | 替身模型第一步返回一个 `search_kb` 调用；断言结果是 `FAILED`、停止原因 `max_steps`、提议存储为空 |
| 资料足够时返回 `EMPTY` | 在假知识库里放一篇能回答这批问题的文档，用 `eval/scenarios.yaml` 里对应的不应当提议场景跑真实模型，结果是 `EMPTY`，提议存储为空 |

**必做：提议与采纳**

| 验收项 | 检验方法 |
| --- | --- |
| 提议带依据，事实和推断分开 | 打开一条提议：依据里有弃答记录的 trace ID、文档 ID 和版本；说明分成“事实”和“推断”两部分，事实部分的每一句都能在依据里找到 |
| 采纳后创建草稿，创建人是采纳人 | 以用户 `bob` 采纳，假知识库里多一份草稿，`created_by == "bob"`，状态是待审核 |
| 连点两次只建一份 | 顺序调用 `accept` 两次，第二次返回 `already_handled`；再用两个线程同时调用一次，草稿数仍为 1 |
| 依据更新后采纳转为 `expired` | 提议生成后把依据文档的版本加一，再采纳：返回 `expired`，写入函数没被调用 |

**必做：防噪与评估**

防噪三项按上面“怎样触发防噪规则”构造。评估三项的检验方法：

| 验收项 | 检验方法 |
| --- | --- |
| 三个应当提议场景都产生提议且引用正确 | 跑 `eval/scenarios.yaml`，逐个看依据引用和场景里的期望一致 |
| 三个不应当提议场景都没有提议 | 同上。场景里至少要有一个阈值边缘、一个依据已失效、一个同一对象已有未处理提议（Day85） |
| 防噪测试通过、时间由参数注入 | 跑测试；`grep -n "datetime.now" noise.py` 输出为空 |

**进阶**

| 验收项 | 检验方法 |
| --- | --- |
| 每次运行一条 trace、每步一个 span | 用内存导出器或追踪后端打开一次运行，span 数等于工具调用和步骤数，每个带状态和原因码 |
| 发给角色，无人时发给负责人 | 角色有成员时投递给成员；把角色成员清空，投递给剧本负责人 |
| 写入失败一次后重试只有一份草稿 | 把写入函数设为“第一次写入成功但返回超时”：提议进入 `failed`；重试后成功，草稿数为 1，两次调用用的是同一个幂等键。这种构造比“第一次直接失败”更能检验幂等 |
| 静音与总开关、每日预算排队 | 按上面“怎样触发防噪规则”的构造 |
| 第二个剧本、看板、队列 worker、每日摘要 | 现场演示；队列 worker 要演示两个 worker 并行时同一批次只处理一次（Day72） |
