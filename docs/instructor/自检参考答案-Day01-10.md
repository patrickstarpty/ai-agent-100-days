## 自检参考答案：Day01～10

给讲师用，不进课程目录。每题列出要点，学员答到主要意思即可，不要求措辞一致。Day10 是实战课，两道题没有标准答案，这里列出讲评时要看的点。

### Day01 认识 AI Agent

1. 一个“先检索三篇文档，再总结成一段话”的功能，属于三种形态里的哪一种？依据是什么？
   - 固定工作流。
   - 依据是步骤由写代码的人事先定死（检索、再总结），模型只在每一步里完成一项具体工作，不决定下一步做什么。
   - 如果改成“模型自己决定要不要再检索、检索什么、何时停”，才算 agent。
2. 为什么说没有验证手段的任务不适合交给 agent？
   - agent 每一步都可能出错，错误会沿后续步骤累积。
   - 没有验证手段，循环拿不到“做对了没有”的反馈，既无法自我纠正，人也无法判断结果是否可信。
   - 这类任务要么先补上验证（测试、校验规则、人工抽查），要么改用步骤固定、可逐步检查的工作流。

### Day02 调用模型 API

1. 第十轮对话时，发给模型的 `messages` 里有哪些内容？这对 `prompt_tokens` 意味着什么？
   - system 消息，加上前九轮的全部 user 和 assistant 消息，再加第十轮的 user 消息。
   - 接口无状态，“记忆”就是每次重发的完整历史。
   - 所以 `prompt_tokens` 随轮数持续增长，越往后每轮越贵、越慢，Day07 会讲怎样控制。
2. 如果业务代码里有五处直接调用 `completion`，加统一的超时和日志需要改几处？换成 `chat` 之后呢？
   - 直接调用要改五处，而且容易漏改、改得不一致。
   - 换成 `chat` 之后只改 `llm.py` 一处，所有调用自动生效。
   - 同理，换供应商、加重试、在测试里换成假实现，也都只动这一处。

### Day03 提示词基础

1. 示例里三条全是“账单”类，会对分类结果产生什么影响？
   - 模型会紧跟示例，输出偏向“账单”，本该归入物流或其他的工单也更容易被判成账单。
   - 示例还缺少边界情况，模型学不到类别之间的分界在哪里。
   - 改法：示例覆盖每个类别，并放进容易混淆的边界样本，再用测试用例验证。
2. 你改了提示词里的两处，通过数从 8 条变成 9 条。这能说明两处改动都有效吗？
   - 不能。可能只有一处有效，另一处无效甚至有害，被前者抵消了。
   - 一次只改一处，才能把通过数的变化归因到具体改动。
   - 用例少时一条的差异也可能来自随机波动，最好固定 `temperature`，必要时多跑几次。

### Day04 结构化输出

1. JSON 模式和 JSON schema 约束，各自保证了什么，没有保证什么？
   - JSON 模式只保证输出是合法 JSON，不保证字段名、类型、必填项符合预期。
   - JSON schema 约束在支持的模型上让输出符合 schema 的形状，但不保证业务规则（如字数上限、取值是否合理），也挡不住被 `max_tokens` 截断成半截 JSON。
   - 两种情况下都要用 Pydantic 校验。
2. 重试用尽后返回一个 `category="其他"` 的默认对象，会给下游带来什么问题？
   - 下游把失败当成功处理，这张工单被静默分到“其他”，没人知道它其实没被正确解析。
   - 统计和评估会被污染，“其他”类的数量虚高，问题被掩盖。
   - 正确做法是抛出异常，由调用方决定转人工还是跳过。

### Day05 工具调用

1. 从模型返回 tool call 到用户看到最终回答，中间哪些事发生在你的代码里？
   - 解析 `function.arguments`（JSON 字符串）并校验参数。
   - 按工具名找到函数并执行，决定是否放行。
   - 把模型的 assistant 消息和每个工具结果（带 `tool_call_id`）追加进 `messages`，再次调用模型，最后把回答展示给用户。
2. 为什么要把模型生成的工具参数当作不可信输入？举一个不校验会出问题的例子。
   - 参数由模型生成，可能填错、格式不对，也可能受用户输入或文档里的注入影响。
   - 例子：读文件工具收到 `../config` 或绝对路径，不校验就会读到目录外的文件；查询工具收到别人的订单号，不按当前用户校验就会越权。
   - 校验方式和对待用户提交的表单一样：格式、范围、权限都要查。

### Day06 手写一个 Agent 循环

1. 循环里哪一行决定了“任务完成”？这个判断是谁做出的？
   - `if not msg.tool_calls:` 这一行。
   - 判断由模型做出：它返回一条不带工具请求的回答，就表示它认为任务完成。
   - 代码只负责兜底：`max_steps` 用完仍未结束，按“未完成”处理，不把中间内容当答案。
2. 工具执行抛出异常时，让程序直接崩溃和把错误返回给模型，各自适合什么情况？
   - 返回给模型：参数错误、记录不存在、表达式不合法这类任务过程中的正常情况，模型可以据此换参数或向用户说明。
   - 直接崩溃（或终止任务）：配置缺失、凭据失效等模型无法纠正的问题，以及继续执行可能造成危害的情况。
   - 无论哪种，都要记日志，bug 不能被静默吞掉。

### Day07 上下文窗口与成本

1. 一个 agent 任务走了 10 步，初始内容很短，每步新增的内容大小相近。第 10 步的输入量和第 2 步相比大致是什么关系？整个任务累计的输入量又如何随步数变化？
   - 每步输入量约等于“已走步数 × 每步新增量”，第 10 步大约是第 2 步的 5 倍。
   - 累计输入量是各步之和，大致按步数的平方增长。
   - 所以步数上限、结果截断和上下文管理（Day43）直接决定成本。
2. 为什么把当前时间写在 system 提示词的第一行会让提示缓存失效？
   - 提示缓存按前缀匹配，前缀中任何一个 token 变了，后面的内容都无法命中。
   - 精确到秒的时间每次都不同，等于每次请求的开头都变了。
   - 正确做法：稳定内容（system、工具定义）放前面，易变内容放后面，例如放进 user 消息。

### Day08 流式输出与交互体验

1. 流式输出没有缩短总耗时，为什么用户仍然觉得更快？
   - 首字出现的时间大大提前，用户很快看到系统在工作。
   - 用户可以边看边读，等待时间被阅读时间填满。
   - 看到方向不对时还能提前取消，不必等到全部生成完。
2. 用户在一个“发送通知”工具执行到一半时点了取消。界面应该告诉用户什么？
   - 如实说明状态：通知可能已经发出，也可能没有，系统目前不确定。
   - 告诉用户怎样确认（例如去哪里查发送记录），以及后续会怎样处理。
   - 不能简单显示“已取消”，那会让用户误以为副作用没有发生。

### Day09 错误处理与重试

1. 为什么重试的等待时间要加随机抖动？只用固定的指数退避会出现什么现象？
   - 很多客户端同时失败时，固定退避会让它们在同一时刻一起重试，形成一波波的请求高峰。
   - 高峰可能再次触发限流或压垮服务，失败和重试互相加剧。
   - 加随机抖动把重试时间打散，服务更容易恢复。
2. 一次“发送通知”的工具调用超时了。在决定是否重试之前，你需要知道什么？
   - 超时只说明没收到响应，通知可能已经发出。
   - 需要知道这个操作是否幂等，接口是否支持幂等键，或者能否查询发送状态。
   - 不能确认、又不幂等时，不要自动重试，交给人确认或标记为待核实。

### Day10 阶段实战：命令行问答助手

1. 你的实现里，哪些限制是由代码强制执行的，哪些只是写在提示词里的？后者失效时会发生什么？
   - 应当由代码强制的：`workspace/` 目录限制、步数上限、`max_tokens`、结果截断、不用 `eval`、重试次数。
   - 只写在提示词里的，通常是“何时用哪个工具”“读不到时如实说明”这类行为期望。
   - 提示词失效时，模型可能越界或编造；讲评时看学员是否把安全边界都放在了代码里，提示词只用于引导行为。
2. 验收清单里的哪一项最难通过？原因出在模型、工具、上下文还是循环？
   - 没有标准答案，看学员能否把现象归到五个部分之一并给出证据（日志、打印的步骤）。
   - 常见的是路径逃逸（工具）、一轮出错后的历史收尾（循环）、截断后模型没说明只读到一部分（上下文和提示词）。
   - 好的回答会说明怎样定位以及改了什么。
