## 自检参考答案：Day35～46

给讲师用，不进课程目录。每题列出要点，学员答到主要意思即可，不要求措辞一致。Day46 是阶段复盘课，没有自检题，用阶段验收清单对照检查。

### Day35 工作流还是 Agent

1. 说出一个你见过的、本该用工作流却做成了 agent 的例子？
   - 没有标准答案，看学员能否指出：步骤其实是固定的、可以事先写清楚，却交给模型每步自己决定。
   - 常见后果：行为不稳定、成本更高、同样的输入偶尔走出不同路径。
   - 好的回答会说出当时为什么选错了（图省事、怕写死不灵活），以及改回工作流后观察到的变化。
2. 路由模式里，分类这一步用模型还是用规则，各自的风险是什么？
   - 用模型：依据可以是自然语言、规则写不全，但分类可能出错或给出未知类别，需要规则在后面兜底。
   - 用规则：确定、可测试，但覆盖不了需要理解语义的场景，规则本身会越写越复杂。
   - 两者常常配合：模型给分类，规则做最终裁决，尤其是权限和风险相关的分支。

### Day36 LangGraph 入门

1. Day06 的哪一行，在图里变成了路由函数返回 `END`？
   - Day06 手写循环里 `if not msg.tool_calls: return` 这一步，对应图里 `route` 函数在 `stop_reason == "completed"` 时返回 `END`。
   - 判断逻辑没变，只是从函数里的 `return` 变成了告诉边“去哪”。
   - 两边都是“模型这轮没有要调用的工具，任务结束”的同一个条件。
2. 为什么有了 `recursion_limit`，状态里仍然需要自己的步数字段和停止原因？
   - `recursion_limit` 是框架按超步计数的最后一道保护，超过时直接抛异常，没有业务含义。
   - 业务上的步数、token、时间上限（Day45）需要在超限之前就平滑停止，并留下可展示、可追踪的停止原因。
   - 抛异常和“达到业务上限后正常结束”在用户和排查人员眼里是完全不同的两件事，不能混用一套机制。

### Day37 状态与 Reducer

1. 两个并行节点都往 `messages` 写入，没有 reducer 会怎样？
   - 两个节点在同一步里写同一个没有 reducer 的字段，图会抛出 `InvalidUpdateError`，这一步失败。
   - 给 `messages` 加上“追加”的 reducer（例如 `operator.add`）后，两边的消息都会保留并接起来，先后顺序不保证。
   - 没有 reducer 时的“新值覆盖旧值”只适用于前后两步先后写入；这正是本课 `tag` 和 `tags` 两段演示的区别。
2. 状态结构升级后，旧检查点怎么处理？列出两种做法。
   - 做法一：状态里带显式版本号，恢复旧检查点时先比对版本，不兼容就按 `version_incompatible` 停止原因处理，不强行往新结构塞。
   - 做法二：写一个迁移函数，把旧版本的字段转换成新结构后再继续跑，迁移规则要单独测试。
   - 两种做法都不能让旧检查点直接按新结构硬读，否则字段缺失或类型不对会在运行期才暴露。

### Day38 路由、并行与子图

1. 模型把一条“帮我退订套餐”的请求分类成了 `faq`，你的路由设计里有哪一层能拦住它？如果拦不住，该补在哪里？
   - 本课例子里 `NEEDS_APPROVAL` 这类规则只在分类结果正确（命中 `unsubscribe`）时才生效，分类本身错了规则拦不住。
   - 能拦住的层：如果有基于关键词或结构化字段的二次校验（例如检测到“退订”字样），可以在路由函数之外再加一条规则兜底。
   - 如果确实拦不住，应该补在路由函数里加一条不依赖模型分类的关键词检查，把高风险意图的识别从单一依赖模型分类，变成模型加规则双重判断。
2. 并行的三个分支里有一个超时了，你希望用户拿到什么？为了做到这一点，节点该怎么写？
   - 用户应该拿到另外两支的正常结果，加上超时那一支的明确状态说明，而不是整个请求失败或假装没有这一支。
   - 节点要在内部捕获超时异常，返回带 `status: "failed"`、`error` 字段的结果，而不是让异常冒出来影响整个超步。
   - 汇合节点按 `status` 决定怎样呈现：缺一部分证据时如实说明缺了什么，必要时走弃答（Day17）而不是拼凑回答。

### Day39 反思模式

1. 为什么“运行代码得到的报错”比“让模型再检查一遍代码”是更好的反馈？
   - 报错是确定的事实，来自实际执行，不依赖模型是否愿意承认自己的错误。
   - 模型自我检查时容易认可自己的输出，或者提出无关紧要的修改，方向不明确。
   - 外部反馈给出的是具体、可定位的问题，模型据此修改的方向更明确，通常更可靠。
2. 反思两轮后仍未通过，系统应该怎样处理这次请求？
   - 不能把最后一版未通过的结果当作合格答案直接返回给用户。
   - 应该把“达到反思轮数上限、仍未通过”作为明确的停止原因（对应 Day45 的 `max_steps` 或扩展值）记录下来。
   - 向用户如实说明目前的结果达到了上限、尚未完全满足标准，而不是悄悄掩盖。

### Day40 持久化与恢复

1. 为什么“检查点保存成功”不等于“副作用只执行了一次”？
   - 检查点只保证状态快照被持久化，不保证节点内的外部调用（发消息、写数据库、提交代码）只跑了一次。
   - 恢复时中断的节点会从头重新执行，`interrupt()` 或副作用之前的代码会重新跑一遍。
   - 要靠幂等键、先记后做、把副作用单独拆成小节点这类手段，才能让“重跑”变得安全。
2. 权限在任务等待期间被撤销，恢复时应该怎样处理？
   - 恢复前要重新校验发起人的权限是否仍然成立，不能只看任务创建时的权限快照。
   - 权限已经不成立时，应该按 `permission_changed` 或 `permission_denied` 停止原因结束任务，而不是带着旧权限继续执行写操作。
   - 需要把这个结果清楚地告知发起人和审批人，说明任务因为权限变化而停止。

### Day41 人工确认

1. `interrupt()` 之前的代码里有一次外部调用，恢复时会发生什么？
   - 恢复时该节点会从头重新执行，`interrupt()` 之前的所有代码（包括这次外部调用）都会再跑一遍。
   - 如果那次外部调用有副作用且不是幂等的，就会被执行两次。
   - 所以 `interrupt()` 之前的代码要能安全重跑，或者把有副作用的部分挪到 `interrupt()` 之后、确认通过了才做。
2. 哪些动作你认为不需要人工确认？理由是什么？
   - 没有标准答案，看学员能否说清楚判断依据：可逆、影响范围小、不涉及权限升级的动作一般不需要。
   - 例如只读查询、生成草稿但不发布，这类动作出错的代价低，确认关卡反而拖慢节奏。
   - 好的回答会提到“关卡太多，流程会退化成人工流程”这一权衡，而不是无条件都加确认。

### Day42 流式与进度事件

1. 用户在回答流到一半时刷新了页面，按本课的设计，他会看到什么？逐字的 token 会重放吗？
   - 刷新后新建的连接不带 `Last-Event-ID`，会从事件表里从头重放已经入库的步骤事件和最终结果。
   - 逐字的 token 不会重放，因为 token 通常只实时推送、不逐条入库；重放看到的是完整的步骤和最终回答。
   - 界面应显示到当前实际进度，不应该因为刷新就回到“空白”或误报“已完成”。
2. 为什么“最后一个 token 已经收到”不能作为把界面标为“完成”的依据？
   - token 流完只代表模型生成的文字结束，后面可能还有引用校验等节点会修改或否决这个结果。
   - 只有收到明确的终止事件（如 `run_finished`、`run_failed`、`waiting`）才能确定运行的最终状态。
   - 提前标记“完成”可能让用户看到后来被校验打回的错误内容，造成误导。

### Day43 上下文工程与记忆

1. 压缩历史时，哪些信息一旦丢失会让任务出错？
   - 驱动当前决策的关键结论和约束条件，例如用户明确提出的限定条件、前面步骤得出的事实。
   - 带编号的证据和引用关系，一旦转述或摘要就可能对不上原文，引用校验会失败。
   - 任务目标本身和已完成步骤的状态，丢了会导致重复劳动或偏离原来的目标。
2. 什么情况下子 agent 带来的隔离不值得它增加的成本？
   - 任务本身很简单、不需要大量阅读时，启动子 agent 的调用和协调成本比它节省的上下文更大。
   - 子 agent 返回的浓缩结论如果仍然需要原始细节才能验证，隔离反而增加了一次转述出错的机会。
   - 任务量小、步骤少、不涉及大批量资料阅读的场景，直接在主上下文里处理更划算。

### Day44 规划模式

1. 计划做成结构化数据，相比一段自然语言，多出了哪些控制手段？
   - 可以展示给用户或审批人看，执行前就能发现目标理解错了。
   - 可以用代码做执行前校验：动作是否在白名单里、步数是否超限、是否有需要人工确认的步骤。
   - 可以逐步记录和恢复进度，也可以单独评估“计划合不合理”，不必等执行完才知道。
2. 执行到第 3 步时发现第 1 步找错了文件，系统应该怎么办？
   - 把已完成的步骤和实际结果（包括发现错误的这一步）交给模型，让它重新规划剩余步骤。
   - 重新计划的次数要有上限，不能无限重试下去。
   - 如果某一步的 `expects` 和实际结果明显不符，应该在继续执行前先暴露这个偏差，而不是在错误的基础上继续往下走。

### Day45 有界循环：预算与停止条件

1. 步数上限和 token 上限为什么都需要，只留一个会怎样？
   - 步数反映“思考—调用工具—观察”的轮次，token 反映实际消耗的资源和成本，二者不是线性对应关系：少数步骤也可能消耗大量 token（例如返回很长的工具结果）。
   - 只留步数上限，可能在步数不多的情况下消耗过多 token，成本失控。
   - 只留 token 上限，可能在 token 还够用时陷入大量空转的小步骤，响应变慢。两个上限需要同时检查，谁先触发谁决定停止原因。
2. “达到上限”和“任务失败”在界面上应该怎样区分？
   - “达到上限”对应 `max_steps`、`budget_exhausted` 这类停止原因，应明确提示“已达到步数/预算上限，以下是目前的结果”，而不是说任务失败。
   - “任务失败”对应 `tool_failed` 等停止原因，应说明具体失败在哪一步、是否可以重试。
   - 两者都要走本课定义的停止原因枚举，由代码而不是靠解析文本来区分，保证界面提示和实际情况一致。
