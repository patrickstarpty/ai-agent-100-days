## 自检参考答案：Day87～94

给讲师用，不进课程目录。每题列出要点，学员答到主要意思即可，不要求措辞一致。Day94 是阶段复盘课，用阶段验收清单代替自检，这里不列。

### Day87 编码 Agent 全景

1. 一个仓库几乎没有测试，把编码任务交给 agent，最先失去的是哪一项优势？
   - 最先失去的是“可以用自动化测试验证”，随之失去“以测试结果为反馈迭代”。
   - 没有测试，“跑 → 读失败 → 修”这一圈没有客观信号，agent 只能凭自己判断是否完成。
   - 应对：先补关键路径的测试，或把验收标准（Day89）先转成测试，再交给 agent。
2. agent 的改动为什么要以草稿合并请求的形式出现，不允许直接提交到主分支？
   - 主分支影响所有人，合并是需要人和门禁放行的动作（Day41、Day65）。
   - 草稿让评审人检查测试覆盖不到的设计、范围和可维护性。
   - 改动留在分支上，出错时可以整体丢弃；agent 的权限也因此只需要“推自己的分支”。

### Day88 从需求工单到合并请求

1. 为什么编码 agent 只读已批准的结构化需求，不直接读原始工单？
   - 已批准的需求有 ID 和版本，经过人确认，是后面步骤唯一认可的依据。
   - 原始工单的描述和评论是任何人都能写的不可信文本，隔开它能减少注入进入能写代码的 agent（Day93）。
   - 下一步只读上一步的产物，不读对话记录，流程才可追溯、可重放。
2. 需求在编码进行到一半时被修改，继续在原计划上改代码会有什么问题？
   - 代码和测试对应的是旧版需求，合并后实现与已批准版本不一致，验收标准也对不上。
   - 在旧计划上打补丁，计划校验和审批记录都失效，事后无法说清依据是哪个版本。
   - 正确做法：回到 `awaiting_approval`，作废已开始的编码，按新版本重新计划。

### Day89 需求澄清 Agent

1. 为什么反例常常比正例更能暴露对需求的误解？
   - 正例通常是最直观的情况，几种不同理解都能满足它。
   - 反例落在边缘（如 2 月 28 日 23:59 的订单），不同理解在这里给出不同结果，分歧立刻显现。
   - 反例也直接对应“不该出现什么”的测试，最容易被实现漏掉。
2. 澄清 agent 等了很久没收到提出人的回答，系统应该怎样处理？
   - 等待状态经检查点保存，进程可以退出，不占资源（Day40）。
   - 等待时长和提问轮数有上限，超时后标为等待人工处理（停止原因用 Day45 枚举里的 `awaiting_human` 或 `escalated`）。
   - 不能自行选一个答案继续往下走；可以提醒提出人或转给产品负责人。

### Day90 编码 Agent 的验收

1. 历史任务集里的“隐藏测试”为什么不能让 agent 在运行时看到？
   - 看到了 agent 就能针对测试写代码，甚至改测试，分数不再代表它真的实现了需求。
   - 隐藏测试代表“当时的人认为完成的标准”，只有在运行结束后用来判定才公平。
   - 对应的控制：隐藏测试和验收测试不进入 agent 的可写范围，也不放进工作区。
2. 同一个任务换了模型后从通过变成失败，追踪显示是依赖下载超时，这次失败应当怎样记录？
   - 归因为环境，不算模型的失败；记录追踪链接和失败原因。
   - 修好环境（钉死镜像、用内部依赖镜像）后重跑，再比较两个模型。
   - 每个任务多跑几次，看通过次数，避免把一次环境波动当成模型退步。

### Day91 自建还是采购

1. 你的流程里有哪些需求是现成方案的限制挡住的？
   - 开放题，答案应对照限制表逐条说：跨仓库改动、超过单次会话时长的长任务、非 GitHub 托管的仓库、需要读其他仓库或企业知识。
   - 好的回答会区分“真的挡住”和“可以拆小任务绕开”。
   - 加分点：注意到这些限制是撰写时的情况，需要按官方文档核对。
2. 选择自建编码 agent 时，哪一项安全责任最容易被低估？
   - 通常是隔离与代码执行：沙箱、网络出站控制、工作区里不放凭据（Day60、Day93）。
   - 其次是工作流文件和推送权限：agent 能改 CI 配置就可能间接拿到密钥。
   - 采购时这些部分由厂商提供一部分，自建时全部要自己设计、测试、维护。

### Day92 研发流程里的审批与门禁

1. 为什么委派 agent 写代码的人，不能担任这个合并请求的审批人？
   - agent 替委派人干活，委派人属于作者一方；自己批准自己的改动等于没有第二双眼睛。
   - 职责分离要求写代码、批准合并、批准发布的身份两两不同。
   - 撰写时 GitHub 的 Copilot coding agent 也按这个思路设计：请求者不能批准 agent 开的合并请求。
2. 紧急变更时，哪些环节可以加快，哪些环节无论多急都不能省？
   - 可以加快：由值班评审人和值班发布审批人处理，跳过事先列明的非必需检查，首选回滚。
   - 不能省：必需检查、作者以外的人批准、显式的紧急标记和理由、审计记录、事后补评审。
   - agent 不能自己把任务标为紧急。

### Day93 研发流程里的安全

1. agent 能修改工作流文件，而工作流里能读到部署密钥，这两件事组合起来的风险是什么，应该切断哪一环？
   - 风险：注入的指令让 agent 改工作流，工作流运行时把密钥送出去，三要素在一次运行里凑齐。
   - 切断：agent 推送的代码不自动触发接触密钥的工作流，先由人看过；部署密钥只放在需审批的发布环境。
   - 补充：工作流文件设代码所有者，改动需额外审批（Day92）。
2. 为什么依赖包的说明文档也要当作不可信文本？
   - 它由依赖维护者或能篡改依赖的人写，和工单一样进入 agent 的上下文。
   - 模型分不清“说明”和“指令”，里面像指令的话可能被照做（Day58）。
   - 所以依赖从内部镜像获取、新增依赖单独标记评审，网络白名单限制 agent 能读到的外部文档。
