## 复盘评分标准

> 讲师用，不进学员目录。适用于六个复盘课的产出：Day34、Day46、Day66、Day76、Day94、Day97。

**一句话**：复盘评的是文档能不能被别人检验和照着做，篇幅和措辞不计分。

**怎样用**：每份产出按“缺项 / 合格 / 优秀”三档评。合格档的每一条都满足才算合格；优秀档在合格的基础上满足其中至少三条。缺项档列的是最常见的不合格情形，命中任何一条就退回补写。课文的“阶段验收”清单是硬性底线，阶段验收没过的，产出写得再好也只能评缺项。

**通用规则**（六课都适用）：

- 每条结论要附证据位置：文件路径、测试名、追踪链接或评估结果。只写“有”“已考虑”的结论视为没写。
- 决策记录用 [决策记录模板](../../模板/决策记录模板.md)，“决定”一节要可检验（Day95）：读者只看这一节就知道该怎么做，评审人能判断一段代码是否违反它。
- 评审清单新增的问题要问“怎样做到的”，少问“有没有”（Day97）。
- 评分时可以请作者当场口头回答一两个追问，口头讲不清的部分按缺项处理。

### Day34 阶段复盘：评估策略

产出：《评估策略》决策记录、评审清单“评估”一节。阶段验收：几十条人工标注用例并有基线；分数低于阈值时回归命令让构建失败；能不看文档讲清没选另一种方案的原因。

| 档 | 可检验的表述 |
| --- | --- |
| 缺项 | 评估集只有几条或没有标注人；没有基线分数，或基线没写当时的模型和配置；CI 里的回归命令没有让构建失败的条件，或从没实际失败过一次；“考虑过的方案”为空或只摆了一个明显不行的方案；评审清单只抄了课文的问题 |
| 合格 | 决策记录回答了课文列的五问：评估集位置和格式及维护人、每类失败用哪类评分器、评审员怎样校准和多久重做、CI 跑什么和阈值是多少、没采用的方案及原因；评估集有几十条人工标注用例，包含 `should-abstain` 和 `must-not-appear` 两类，带 `corpusDigest`；能演示一次故意改坏导致回归命令失败，失败输出逐条列出用例；评审清单“评估”一节对检索类和编码类系统分别有问题 |
| 优秀 | 失败分类表来自真实记录的错误分析（Day24），每类有频次，评分器只覆盖出现过的类别；LLM 评审员有校准数据，分别报告抓住不通过和放行通过的比例（Day27）；替身模型的结构性回归和真实模型的质量回归分两层，各自的触发时机写清（Day30）；检索单独评估，失败能区分“没取回”和“取回没用上”（Day28）；“重新评估”的触发条件写成可观察的事件 |

### Day46 阶段复盘：编排规格

产出：编排规格、评审清单“编排”一节。阶段验收：四个上限都有数值，每个上限和每种停止原因有测试；能解释数值怎样定的；没参与设计的同事能据此画出流程图。

| 档 | 可检验的表述 |
| --- | --- |
| 缺项 | 任何一个上限没有数值，或数值没有依据；停止原因只有“成功 / 失败”两种，或与 Day45 的枚举对不上且没说明扩展了什么；有副作用的节点没有写恢复时怎样防止重复；人工确认没写通过后以谁的身份执行；同事按规格画出的流程图与作者的版本有明显出入 |
| 合格 | 规格包含课文列的六部分：任务清单（执行方式和推理方式）、状态结构（字段、类型、reducer、版本号）、节点与条件边（标出副作用节点及防重复手段）、人工确认（位置、审批人看到什么、执行身份）、上下文规则（每类工具结果的长度上限和清除规则）、四个上限和停止原因；停止原因用 Day45 的标准枚举，扩展的值写明“在 Day45 的枚举之上扩展”；每个上限和每种停止原因都能对上一条测试名；同事画出的流程图与原图一致 |
| 优秀 | 上限数值来自追踪数据里真实任务的步数和 token 分布，并写明留了多少余量（Day45）；副作用节点用幂等键或“先记后做”，并有一条模拟中途崩溃再恢复的测试（Day40）；恢复时重新检查权限，权限不足以 `permission_changed` 结束（Day59）；标出了哪些任务不应进入 agent 循环，并说明理由（Day35）；状态结构有版本号和兼容策略（Day74） |

### Day66 阶段复盘：信任模型与威胁模型

产出：工具与 Skill 的信任模型（决策记录）、威胁模型定稿、OWASP 清单对照、评审清单“工具与安全”一节。阶段验收：Day61 的 OWASP 对照结果已复核，每条待办已关闭或写明未关闭的原因和新期限；评审清单“工具与安全”一节已按项目增删并写明理由；在测试环境里导入过一个真实外部 Skill 并确认代码没执行；每条剩余风险有明确接受人。

| 档 | 可检验的表述 |
| --- | --- |
| 缺项 | 信任等级只有“可信 / 不可信”两级，或没写每一级能做什么；威胁模型里有三要素同时出现的路径却没写控制措施；剩余风险没有接受人，或接受人写的是团队名；Day61 的待办没有逐条复核，或复核结论写的是条目原文的复述；评审清单一节与模板一字不差，没有任何按项目的增删；控制措施只有提示词层面的要求 |
| 合格 | 信任模型回答了课文四问：分几级、每级能否进入系统提示词、能否触发写操作、能否访问网络；导入的 Skill 是否执行代码以及怎样保证；写操作以谁的身份执行。威胁模型用模板填写，列出每个 agent 的三要素和每条路径的控制、剩余风险、接受人；Day61 的十项结论逐条复核过，已关闭的附证据位置，未关闭的写明原因和新期限；评审清单“工具与安全”一节对照模板逐条核对过，每处增删写明理由；能演示导入带脚本的 Skill 后标记文件不存在 |
| 优秀 | 每条控制都落在模型之外（权限、网络、审批、门禁），并能指出对应的代码或配置（Day57、Day58）；每个 agent 至少去掉了三要素中的一项，并写明去掉的是哪一项；不可信内容的入口按 Day58 的入口表逐行检查过，包括工具描述和长期记忆；“已有控制”的条目附了测试名或演示记录；评审清单在模板之外补充了运行身份和权限范围的问题 |

### Day76 阶段复盘：技术栈映射

产出：技术栈映射表、评审清单“权限与平台底座”一节。阶段验收：参考实现每个组件在目标栈里有对应，每处差异有决策记录；每个“两者并存”的决定写明了各自负责什么和收敛时间；一次真实对话的完整追踪能在 Langfuse（或团队的追踪后端）里看到；能从一条回答追溯到实际模型和 token 用量。

| 档 | 可检验的表述 |
| --- | --- |
| 缺项 | 映射表缺行，或行名与 [技术栈映射表](../../模板/技术栈映射表.md) 模板不一致；“差异”一栏写“无”却没有核对依据；“决定”一栏空着或只写“待定”；选了“两者并存”却没写各自负责什么、什么条件下收敛；追踪里看不到检索、模型调用、工具调用中的任何一类；只能查到配置里的逻辑模型名，查不到实际应答的模型 |
| 合格 | 映射表按模板的行名填全（追踪后端、评估平台、向量与关键词检索、权限过滤、检查点与任务队列），并覆盖课文要求的模型入口、部署形态；每行五栏齐全：参考实现、目标栈、差异、决定、理由；每处有实质差异的行链接到一份决策记录；每个仍然“两者并存”的决定写清参考实现和目标栈各自负责哪部分、什么条件下收敛到目标栈；能现场打开一条真实对话的完整追踪，三类 span 都在；能从一条回答查到实际模型和 token 用量 |
| 优秀 | 对目标栈里产品行为的描述写明了核对日期，并注明以官方文档为准（Day100）；追踪后端、模型入口这类可替换的部分写了替换方案，方案里有具体的切换条件而不是“以后再定”；权限一行写清用户身份在哪一跳进入检索、缺身份时怎样拒绝（Day52）；追踪的保留期和查看权限有具体设置（Day63、Day69）；评审清单这一节问到了派生物是否继承权限 |

### Day94 案例复盘

产出：研发流程设计文档、用评审清单七节过一遍的结论。课文的阶段验收分“必做”和“进阶”两组：必做是没参与的同事能说出一条需求经过哪些状态、在哪三处等人，每个 agent 有威胁模型并至少去掉一项，评审清单七节都有结论、待办有负责人；进阶是合并门禁有测试证明 agent 无法合并自己的合并请求（或用现成产品时在仓库设置里确认），以及历史任务集至少跑过一次基线。进阶两项需要一个能跑起来的环境，没做到不算缺项，但要写明原因，并计入能否评到优秀。

| 档 | 可检验的表述 |
| --- | --- |
| 缺项 | 必做三项任一项没做到：流程图里有步骤没标“确定性 / agent / 人”，或读工单的 agent 能推送代码、能推送代码的 agent 能读原始工单；某个 agent 没有威胁模型或三要素一项都没去掉；清单七节有问题没结论，或待办没有负责人。此外，不论必做还是进阶都不能出现：合并前的构建能拿到生产凭据；写代码、批准合并、批准发布的身份有重合；“完成”由 agent 自己宣布 |
| 合格 | 必做三项都做到，且设计文档包含课文列的八部分：流程图与步骤表、状态枚举、需求格式、编码 agent 的工具与运行框架、“完成”的定义与历史任务集、门禁与审批、威胁模型、自建与采购的决策记录；三层“完成”各自写明在哪一步、由谁判定；四个上限有数值；清单七节的每个问题有一句结论和证据位置，答不出的进入待办并有负责人；课文列的五个编码类专项问题都有回答；进阶两项即使没做，也写明了没做的原因（例如没有自建的编码 agent） |
| 优秀 | 进阶两项都做到：合并门禁有一条测试证明 agent 的身份无法合并自己的合并请求，用现成产品时改为在仓库设置里确认这条规则生效并写下确认方法；历史任务集用隐藏测试判定，每个任务跑多次并报告通过次数，失败按需求、计划、代码、环境归因（Day90）。再满足其中至少两条：有削弱测试的确定性检查，并说明命中后交给谁看；紧急变更通道写清哪些环节可加快、哪些不能省（Day92）；网络白名单逐项写了理由（Day93）；作者把这份文档与 Day99 的评审报告对照过，并写下自己设计中同样没做到的地方 |

### Day97 设计评审清单

产出：定稿的设计评审清单；用它评审一个真实项目，交出一页评审报告和对方的书面反馈（Day97 动手练习）。这一课没有单列阶段验收，以下三档即验收标准。

| 档 | 可检验的表述 |
| --- | --- |
| 缺项 | 清单少于七节，或某一节只有“有没有”式的问题；清单与课文模板一字不差，没有任何结合自己经验的增删；评审报告超过五条发现，或发现里没有“问题、可能的后果、建议的下一步”三部分；没有排序，或排序没有依据；没有被评审方的书面反馈 |
| 合格 | 七节齐全，每节的问题来自对应的复盘课并按自己的情况增删，删掉的写明理由；问题以“怎样做到的”为主，并写明要什么证据；评审报告三到五条，按不可逆、影响范围、修复成本排序；每条发现指向被评审设计中的具体内容，后果用业务上会发生的事表述，下一步可以排进计划并写明怎样验证；附被评审方的反馈：哪条最有用、哪条不符合实际 |
| 优秀 | 清单对检索类系统和编码类 agent 有不同的问法（Day97 自检第 1 题）；每节末尾有“最可能出事的地方是什么、出事时谁会先知道”这一问；报告开头有一句话的共同根因，并肯定了做得对的地方；根据对方反馈修改了清单，修改记录可查；Day98、Day99 的演练报告排序与讲师答案一致，或不一致时理由站得住 |
