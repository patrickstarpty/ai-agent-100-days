## 自检参考答案：Day77～86

给讲师用，不进课程目录。每题列出要点，学员答到主要意思即可，不要求措辞一致。

### Day77 何时拆成多 Agent

1. 举一个“为了隔离权限而拆 agent”的例子。
   - 案例 B：读取工单原文（不可信内容）的需求澄清 agent 没有写权限，只产出结构化需求；能提交代码的编码 agent 只读已批准的结构化需求。
   - 这样外部内容里的注入到不了有写权限的 agent（Day57、Day58）。
   - 学员的例子只要满足“读不可信内容的一方不能写，能写的一方不读不可信内容”即可。
2. 群聊模式为什么不适合需要确定性结果的场景？
   - 发言顺序和讨论走向由模型决定，同样的输入跑两次可能得到不同的结论。
   - 讨论可能循环或漂移，难以设定清楚的停止条件，也难以复现和评估。
   - 需要确定性结果时用顺序模式或代码判定，群聊只适合需要多视角讨论、结果由人或代码最终裁决的场合。

### Day78 顺序、并发与交接

1. 并发模式里，`quorum` 设成分支总数和设成 1，分别适合什么任务？
   - 设成分支总数：每个视角都不可缺，例如合规检查的几个维度，缺一个结论就不完整。
   - 设成 1：多个分支是冗余的备选来源，任何一个返回就够用，例如向几个等价的数据源查同一件事。
   - 介于两者之间的取值用于投票类任务，同时 `PARTIAL` 要在界面上写明缺了哪些视角。
2. 交接模式为什么要由代码检查交接目标，只靠 agent 自己判断会出什么问题？
   - 模型可能交给不存在或无权处理的 agent，也可能在几个 agent 之间来回踢，形成无限交接。
   - 外部内容里的注入可以诱导 agent 把任务交给权限更高的一方。
   - 代码检查允许名单、禁止回到已经经过的 agent、跳数上限，不满足就交给人，这是“模型提议、代码裁决”的落点。

### Day79 子 Agent 与委派

1. 委派消息里的“背景”一项为什么不能省，省了之后最常见的后果是什么？
   - 子 agent 从空白上下文开始，委派消息是它知道的全部，看不到主 agent 已经确认或排除的东西。
   - 最常见的后果是重复主 agent 做过的工作，或者沿着已经排除的方向继续查。
   - 浪费 token 和时间，交回的结论还可能和主 agent 已确认的事实冲突。
2. 子 agent 返回 `LIMIT_REACHED` 时，主 agent 应当怎样使用它交回的部分结论？
   - 当作“没查完”的部分结果，不能当成“查完了没有”（`NOT_FOUND`）或完整结论。
   - 带着已有结论和 `open_questions` 决定：缩小范围再委派一次、自己顺着证据引用补查，或在最终回答里写明不完整。
   - 部分结论仍要按证据引用核对后才能使用。

### Day80 Agent 之间的契约

1. 检索组件在索引重建期间返回 `EMPTY` 而不是 `NOT_READY`，下游会做出什么错误的决定？
   - 下游会把“暂时查不了”当成“资料里确实没有”，直接弃答或告诉用户没有相关内容。
   - 主动剧本还可能据此误判出“知识缺口”，产生错误的提议（Day81、Day86）。
   - 正确处理是稍后重试或退化到不依赖它的路径，并在追踪里能看到原因。
2. 为什么规定模型只能用 `chunk_id` 指向证据，不能把它复述的文字当作证据往下传？
   - 复述可能改动原文，来源和版本也会丢失，下游无法校验引用是否存在、版本是否仍有效（Day16）。
   - 原样传递的 `Evidence` 对象让代码可以做确定性的引用校验，也让提议采纳时能比对来源版本（Day82）。
   - 模型可以读证据，但证据的身份由检索组件给出，模型不能伪造。

### Day81 主动 Agent：信号、触发与剧本

1. 事件信封里放全文会带来哪两类问题？
   - 权限与隐私：信封经过队列、日志、追踪，被复制到很多地方，能看到这些地方的人都能看到内容，绕开源系统权限（Day21），还可能带出个人信息（Day63）。
   - 一致性与体积：全文在信封里是一份快照，可能已过期；消息变大也增加传输和存储负担。
   - 做法是只放 ID 和去标识化摘要，剧本运行时用只读工具按权限去取。
2. 同一个事件同时触发两个剧本时，`seen` 为什么要按（剧本，幂等键）记录？
   - 只按幂等键记录，第一个剧本处理后，第二个剧本会把同一事件当成重复而丢弃。
   - 去重的含义是“同一个剧本不重复处理同一事件”，不同剧本各自需要看到它。
   - 生产中 `seen` 放持久化存储并设保留期。

### Day82 提议与采纳

1. 去掉 `accepting` 状态、采纳时直接写入再标 `accepted`，在什么情况下会出问题？
   - 写入目标系统成功后、改状态前进程重启或超时，提议仍是 `open`，下次采纳会再写一次。
   - 两个人同时点采纳时，没有一个先占住状态的步骤，两次写入都会发生。
   - 有了 `accepting`，恢复时知道写入可能已发生，用同一幂等键重试，由目标系统去重。
2. 提议发给一个角色时，为什么要在投递时才解析成员，而不是在剧本运行时？
   - 剧本运行和投递之间可能隔了很久（合并窗口、排队、每日上限），期间人员可能变动。
   - 投递时解析，送到的是当时真正负责的人，人员变动不需要改剧本或重跑。
   - 投递时还要检查接收人的写权限和能否看到依据，这些也必须用当时的状态判断。

### Day83 防噪与节流

1. 每日上限之外的提议留到之后，和直接丢弃相比，各有什么风险？
   - 留到之后：积压可能越来越多，提议送到时依据已经变了或已过时效，需要靠过期规则清理。
   - 直接丢弃：真实的问题被悄悄丢掉，也丢了“这个信号出现过”的数据。
   - 课程的做法是留下、按优先级排序、到期自动过期并记录过期率，用 Day85 的指标调整上限。
2. 静默期检查放在剧本运行前和放在投递时，结果有什么不同？
   - 放在运行前：静默期内剧本根本不运行，一个 token 都不花，新信号只累积。
   - 放在投递时：剧本照常运行、花了 token，产出的提议再被拦下，浪费成本，还可能堆积提议。
   - 所以静默期在运行前检查；投递时查的是过期、静音和每日上限。

### Day84 长时运行 Agent 的运行框架

1. 为什么功能清单里“只允许改状态字段”这条限制很重要？
   - 防止 agent 改写、删除或合并清单里的功能，把没做完的事从清单上“变没”，然后宣布完成。
   - 清单是判断完成的外部标准，标准本身不能由被检查的一方修改。
   - 本课程进一步要求状态由代码在验证通过后更新，模型只能提出建议。
2. 进度记录和提交历史各自解决什么问题，能否只留一个？
   - 进度记录说明做到哪、为什么这样做、下一步打算做什么，供新一轮快速接上。
   - 提交历史记录代码实际变成了什么样，可以回退到某个干净的状态。
   - 两者互补：只有提交历史看不出意图和未完成的事，只有进度记录无法回退，一般都要保留。

### Day85 主动 Agent 的评估

1. 为什么只看“提议的内容对不对”不足以评估主动 agent？
   - 主动 agent 更常见的失败是不该出声时出声，内容再对，频繁打扰也会让用户关掉它。
   - 评估集要有“不应当提议”的场景，线上还要看采纳率、忽略率及原因、过期率。
   - 成本也要结合采纳率看是否值得。
2. 写一个“看起来该提议、实际不该”的场景。
   - 例：同一主题一小时内五次资料不足，但五次都来自同一个提问人反复改写问题，不满足“不同提问人数”的下限。
   - 例：资料不足的回答发生在索引重建期间，检索返回的是暂不可用，现有文档其实能回答。
   - 例：同一主题已有一条未处理的提议，或刚被忽略、还在静默期内。

### Day86 阶段实战：一个主动提醒剧本

1. 你的实现里，哪些判断由代码做出，哪些交给了模型？交给模型的那部分出错时，哪条验收项能发现？
   - 代码：去重、合并、阈值和提问人数、开关、静默期、预算、每日上限、过期、权限、状态迁移。
   - 模型：查完资料后判断现有文档是否确实答不了，写提议的说明（事实与推断分开）。
   - 模型出错时，“现有资料能回答时返回 `EMPTY`”一项和 Day85 的不应当提议场景能发现误报，应当提议场景和依据引用检查能发现漏报和依据错误。
2. 如果知识管理员连续忽略了这个剧本的大部分提议，你会先看哪个数据，再改哪一处？
   - 先看忽略原因的分布（`already_covered`、`not_a_gap`、`later`），以及对应的提议和依据。
   - `already_covered` 多：检查剧本查现有资料的步骤或检索；`not_a_gap` 多：提高触发阈值或修正触发条件；`later` 多：调整投递时机、每日上限或改成每日摘要。
   - 每次只改一处，用评估场景回归，再看线上指标的变化；长期偏低就默认关闭这个剧本。
