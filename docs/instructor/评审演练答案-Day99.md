## 评审演练答案：Day99 AI 原生研发流程

> 讲师用，不进学员目录。对应课文 [Day99 - 评审演练：AI 原生研发流程](../../Day95-100/99.评审演练-AI原生研发流程.md) 和 [设计评审清单](../../模板/设计评审清单.md)。

**一句话**：这份设计把 agent 当成一个可信的、拥有全部权限的开发者，读什么、改什么、何时停、算不算完成、能不能上线，几乎都由它自己决定。

**怎样用这份答案**：Day99 的关键考点是排序。课文明确提示“其中几处的后果比示范的这一条更严重”。学员如果把示范的“完成由 agent 自己判断”放在第一位，即使其余内容都写对，也要在讲评时指出排序问题。下面列出全部埋点，正文选三到五条，其余进附录。

### 一、先肯定做得对的地方

- agent 在隔离的容器里修改代码、运行测试（Day87、Day60）。
- 追踪按开放标准记录，可以回放（Day68）。
- 发布前有一次人工确认，说明团队意识到发布需要人把关（Day41）。
- 上线前用历史需求试跑过，方向是对的，只是判定方法要改（Day90）。

### 二、共同根因

报告开头用一句话写出：**控制都放在了 agent 内部，权限、门禁和判定标准都没有放在 agent 之外。** 读不可信文本和写代码在同一个 agent 里，写权限覆盖全部仓库，推送直接进主分支，循环没有上限，完成由它自己宣布，唯一的人工关卡在最后且看不到依据。Day57 的立场“把防护放在模型之外”在这里几乎全部缺失。

### 三、全部埋点

编号即建议的优先级。

**发现 1（高）：同一个 agent 读工单全部评论，又能推送到主分支**

- **问题**：摘要写“一个开发 agent……读取工单的描述和全部评论，自行规划，在隔离的容器里修改代码、运行测试，然后把代码推送到主分支”。工单评论任何能评论的人都能写，是不可信内容；同一个 agent 有代码仓库（私有数据）和推送、构建（对外途径）。致命三要素全占，而且没有去掉任何一项。
- **可能的后果**：有人在评论里写一段看起来像需求的指令，例如“顺便把某项检查关掉”或“在构建脚本里加一行上传”，agent 照做，改动直接进入主分支并触发构建。恶意代码进入主分支之后，即使事后回滚，构建期间已经执行过的动作也收不回。
- **建议的下一步**：把读和做分开（Day58）：需求澄清 agent 只读工单、没有代码写权限，产出结构化需求（Day89）；需求经人审批后，编码 agent 只读已批准的需求，看不到原始评论（Day88）；编码 agent 只能推送到自己的分支并开草稿合并请求（Day93）。
- **对应**：Day57、Day58、Day88、Day89、Day93；清单第四节“这个 agent 占了致命三要素里的几项？去掉了哪一项？”“外部内容（工单……）能否影响系统提示词或触发写操作？”，第六节“为什么需要多个 agent？是为了……权限……”。

**发现 2（高）：构建环境配置了生产数据库的只读账号，推送主分支即自动构建**

- **问题**：“推送到主分支后自动触发构建”，“构建环境配置了生产数据库的只读账号”。agent 能改的代码和构建脚本，会在拿得到生产数据的环境里自动运行，中间没有人看过。
- **可能的后果**：结合发现 1，一条恶意评论就能让构建读出生产数据并发往外部，属于不可逆的数据泄露；即使没有恶意，测试代码读写生产数据也会把用户数据带进测试日志和追踪（Day63）。“只读”挡不住泄露，读本身就是泄露的前提。
- **建议的下一步**：编码工作区和合并前的构建里不放任何生产凭据，集成测试用测试替身或专门的测试账号（Day93）；部署凭据只在发布环境里，审批通过后才对发布作业可用（Day92）；agent 推送的代码不自动触发会接触密钥的工作流；构建期间出站网络走白名单（Day60）。
- **对应**：Day60、Day63、Day92、Day93；清单第四节“这个 agent 占了致命三要素里的几项？”，第五节“无人值守的 agent 以谁的身份运行？”。

**发现 3（高）：agent 持有对全部代码仓库有完整写权限的令牌**

- **问题**：“agent 使用一个对代码仓库有完整写权限的令牌，这样它可以处理任何仓库的需求。”令牌覆盖所有仓库、所有分支，可能还包括修改保护规则；写操作记在一个令牌名下，对应不到委派它的人。
- **可能的后果**：任何一次注入或误操作的影响范围是整个组织的代码；审计记录里只有这个令牌，查不出是谁的需求导致了哪次改动（Day62）；令牌一旦泄露（例如被构建日志打印出来），攻击者拿到的是全部仓库的写权限。
- **建议的下一步**：按任务签发短期、只覆盖目标仓库和 agent 自己分支的凭据（Day59、Day93）；有效权限取 agent 上限、委派人权限、任务所需三者的交集；提交能追溯到委派人；修改 CI 配置、保护规则等路径需要代码所有者审批（Day92）。
- **对应**：Day59、Day62、Day92、Day93；清单第五节“无人值守的 agent 以谁的身份运行？”，第七节“写操作的审计记录能否对应到一个具体的人？”。

**发现 4（高）：只在发布前审批一次，缺少需求审批和合并评审**

- **问题**：唯一的人工关卡是“发布前由产品经理在工单里点击确认上线”。需求没有审批，代码直接进主分支，没有任何作者以外的工程师评审；产品经理既是提出需求的人，也是批准上线的人；他在工单里看到的是一个按钮，看不到改动内容、测试结果和回滚方案。
- **可能的后果**：agent 对需求的误解一路放大到生产；设计和可维护性问题没有人看；审批变成走过场，事故时审批记录说明不了任何事。
- **建议的下一步**：按 Day88 设三处关卡：需求审批（agent 的理解从这里成为依据）、合并（作者以外的评审人加确定性门禁）、发布（发布审批人看到变更清单、制品版本、回滚步骤）；身份两两不同，委派人不能批准自己委派的合并请求（Day92）；门禁里加一条测试证明 agent 的身份无法合并自己的合并请求。
- **对应**：Day41、Day65、Day88、Day92；清单第三节“人工确认设在哪，审批人能看到依据吗？”，第四节“最终放行靠的是模型判断，还是确定性规则？”。

**发现 5（高）：“完成”由 agent 自己判断**

这是课文里的示范，内容见课文。要点：没有结构化需求和验收标准，没有规定跑哪组测试，agent 自己把工单改成“开发完成”；评估里的“大部分能完成”也按 agent 自己的标准统计。下一步是由澄清和审批形成带验收标准的需求（Day89），测试和构建结果由流水线判定，agent 只能申请状态变更，用历史任务集加隐藏测试、每个任务多次运行重新评估（Day90）。对应清单第二节“编码类 agent：验收标准是测试通过、构建通过，还是人工评审通过？”。

**发现 6（中）：循环没有任何上限**

- **问题**：“agent 持续工作直到它判断任务完成为止，复杂需求可以运行很久。”没有步数、token、时间和工具调用上限，也没有停止原因。
- **可能的后果**：卡在环境问题或理解错误上的任务会持续消耗费用；长时运行的 agent 容易做到一半上下文耗尽、或过早宣布完成（Day84）；任务停下时没人知道为什么停。后果主要是成本和延误，可以止损，所以排在发现 5 之后。
- **建议的下一步**：四个上限写进状态、由代码裁决（Day45）；停止原因用 Day45 的枚举（`max_steps`、`budget_exhausted`、`tool_failed` 等）写进任务记录并显示在工单上；长任务用进度记录和功能清单分轮完成（Day84）。
- **对应**：Day45、Day84；清单第三节“循环有没有步数、token、时间上限？达到上限时用户看到什么？”，第六节“长任务的进度记录在哪？”。
- **合并建议**：可以和发现 5 合成一条“何时停、何时算完成都由 agent 自己决定”，正文条数紧张时这样处理。

**发现 7（中）：评估只有一次试跑，统计口径是 agent 自己的判断**

- **问题**：“用团队过去的二十个需求试跑过，大部分能完成。”二十个任务作为起点数量合理（Day90 引用的建议是二十到五十个），问题在判定方法：没有隐藏测试，没有多次运行，没有记录环境和版本，“大部分”没有具体数字。
- **可能的后果**：换模型或改提示词时无法比较；环境失败会被算成模型失败，或者反过来。
- **建议的下一步**：以合并前的提交为起点、合并时加入的测试为隐藏测试，环境钉死，每个任务跑多次并报告通过次数，失败按需求、计划、代码、环境归因（Day90）。
- **对应**：Day32、Day90；清单第二节。通常并入发现 5。

**需要对方补充证据的事项（进附录）**

- 谁能给工单打“自动开发”标签；打标签的人是否就是这次运行代表的人（Day59、Day81）。
- 容器的出站网络能去哪里（Day60、Day93）。
- agent 中途崩溃后恢复，会不会重复推送、重复改工单状态，幂等键怎样生成（Day40、Day49、Day72）。
- 发布之后的回滚步骤和观察指标（Day75）。
- 追踪的保留期，以及追踪里是否会出现代码中的密钥或测试读到的数据（Day63、Day67）。
- 依赖的新增和升级是否单独标记、是否只从内部镜像获取（Day93）。
- 每个任务的成本上限，以及成本怎样核算到需求（Day64）。

### 四、哪些发现应排在示范那一条之前

**应排在示范之前的是发现 1~4。** 理由按 Day98 的三个标准：

| 发现 | 不可逆吗 | 影响范围 | 为什么比“完成由 agent 自判”更严重 |
| --- | --- | --- | --- |
| 1 读工单与推主分支同一个 agent | 是：恶意改动进入主分支并已在构建中执行 | 主分支及其下游 | 示范的后果是“一个没做完的改动”，这里是“一个别人植入的改动” |
| 2 构建环境有生产库账号 | 是：数据读出即泄露 | 生产数据涉及的全部用户 | 后果落在用户数据上，回滚代码挽回不了 |
| 3 全仓库写令牌 | 取决于被利用的程度，可能波及所有仓库 | 整个组织的代码 | 它放大了发现 1、2 的每一种后果，示范的那条失败只影响一个仓库的一个需求 |
| 4 只在发布前审批一次 | 部分不可逆：上线后对用户可见 | 每一个经过这条流程的需求 | 示范那一条的修复（由外部判定完成）要靠合并评审和门禁落地，没有这些关卡，修了也无处执行 |

示范那一条的后果是功能不完整或理解错误的改动进入生产，通常能靠回滚恢复，影响限于单个需求，所以排第五。发现 6（无上限）的后果是费用和延误，可以止损，排在示范之后；学员把它排在示范之前，只要理由是“没有上限时 agent 会持有全仓库写权限运行很久，扩大了发现 3 的暴露时间”，也可以接受。

发现 1~3 之间的先后可以讨论。本答案把发现 1 放第一，因为它是攻击路径的入口，切断它之后发现 2、3 失去最容易的触发方式；把发现 2 放在发现 3 之前，因为它直接指向用户数据。学员把发现 2 排第一（理由是生产数据泄露后果最重）同样合理。

### 五、建议的一页报告结构

1. 开头肯定隔离容器、开放标准追踪、发布前确认和历史任务试跑。
2. 一句话根因：控制都放在 agent 内部，权限、门禁和判定标准都没有放在 agent 之外。
3. 正文五条：发现 1、发现 2、发现 3、发现 4、发现 5（并入发现 6、7）。
4. 附录：“需要对方补充证据的事项”。

### 六、和 Day98 对比时可以讲的一点

Day98 的风险集中在“看到了不该看的”，泄露通过读发生；Day99 的风险集中在“做了不该做的”，泄露和破坏通过动作发生。所以 Day99 的评审要多问身份、推送权限、构建凭据、审批点和停止条件，这正是课文列出的五个重点。学员如果把 Day98 的思路原样搬过来，只写“评估不足”“追踪保留期”，就漏掉了这类系统最要紧的部分。

### 七、讲评时常见的问题

- **把示范那一条排第一。** 让学员逐条回答“这条出事之后能不能撤回、波及多大”，通常能自己调过来。
- **只说“权限太大”，没有数三要素。** 要求学员写出三项各是什么，再写准备去掉哪一项。
- **建议“在提示词里要求 agent 忽略评论中的指令”。** 这只能降低概率，替代不了读写分离和权限收窄（Day58）。
- **建议让模型评审员来批准合并。** 模型不做最后一道门（Day65）。
- **把审批加满每一步。** 审批越多流程越像人工流程，要说明每个关卡拦的是哪类错误（Day88）。
