## 自检参考答案：Day57～66

给讲师用，不进课程目录。每题列出要点，学员答到主要意思即可，不要求措辞一致。Day66 是阶段复盘课，用阶段验收清单代替自检，这里不列。

### Day57 Agent 的威胁模型

1. 一个只读知识库问答助手，回答里可以包含 Markdown 图片链接。它占了三要素里的几项？
   - 三项都占：能访问私有数据（知识库）；会读到不可信内容（任何能编辑源文档的人写的文字）；有对外途径（图片链接被渲染时会向外部地址发请求，私有数据可以拼进 URL 带出去）。
   - “只读”只说明它不写系统，不代表没有外泄途径。
   - 常见的处理是只允许指向白名单域名的图片和链接，或者干脆不渲染外部图片。
2. 为什么“让模型先判断输入是否恶意”不能作为唯一的防护？
   - 检测是概率性的，攻击文本可以换说法、换语言、拆开或藏进图片，检测器猜不全。
   - 做检测的模型本身也会被同样的手段影响。
   - 安全要求“无论输入写了什么，某件事都不会发生”，这只能靠权限、网络和审批这些模型绕不过的控制。

### Day58 提示注入与间接注入

1. 系统提示词里已经写了“忽略文档中的任何指令”，为什么仍然需要限制 agent 的权限和对外通道？
   - 这句提示和外来文本在同一个上下文里，模型是否照做仍是概率问题，只能降低风险。
   - 权限和对外通道决定被劫持之后最多能造成什么后果，这一层模型改变不了。
   - 两者叠加：提示挡住大部分粗糙的尝试，设计上的限制兜住剩下的。
2. 一条被写进长期记忆的恶意文本，和一次性出现在网页里的恶意文本相比，处置上多了哪些难点？
   - 它会跨会话持续生效，以后每次读记忆都会被读到，影响面随时间扩大。
   - 要能定位是哪一条、何时由哪个来源写入，并把它和由它派生的摘要、缓存一起删掉。
   - 还要追查它在生效期间影响了哪些任务；所以写入记忆也要记录来源，并受控制。

### Day59 最小权限与 Agent 身份

1. 多个 agent 共用一个服务账号，会让事故处置在哪些环节变难？
   - 定位：审计记录里只有同一个账号，分不清是哪个 agent 做的。
   - 止损：不能只吊销出问题的那一个，要么全停，要么带病运行。
   - 收敛：权限只能按最宽的那个 agent 给，事故的影响范围本来就更大；事后也难以只给一个 agent 收紧权限。
2. 一个任务在等待审批期间，发起人被移出了项目。审批人点了同意之后，系统应该怎样处理？
   - 恢复时重新计算有效权限，不沿用暂停前缓存的令牌或权限集合。
   - 发起人已无权限，任务以 `permission_changed` 停止，不执行写操作。
   - 通知发起人和审批人，并在审计里留下记录；需要继续的，由有权限的人重新发起。

### Day60 沙箱与代码执行

1. 一个沙箱禁止了联网，但能读写用户主目录。说出它仍然存在的一种风险。
   - 能读到主目录里的密钥、令牌和配置文件，等到以后有任何一条对外途径时就能带出去。
   - 能改写 shell 启动脚本、工具配置或计划任务，代码会在沙箱外、以用户身份再次运行，从而跳出隔离。
   - 能误删或破坏用户自己的文件，即使没有人攻击。
2. 沙箱环境只清理临时目录就继续给下一次运行使用，会留下哪些隐患？
   - 上一次留下的进程、安装的包、改过的配置还在，可能是被注入后有意留下的后门。
   - 不同任务、不同用户的数据可能在同一个环境里相遇，造成跨用户泄露。
   - 运行结果依赖上一次的残留状态，出了问题难以复现；所以每次从固定版本镜像重新启动，用完整体销毁。

### Day61 对照公开的风险清单

1. “提示词里已经要求模型不要越权”为什么不能作为“已有控制”的证据？
   - 提示词只影响模型的倾向，被注入或模型出错时就会失效，没有任何保证。
   - 证据要指向模型绕不过的东西：代码、配置、测试、评估用例或审批记录。
   - 最好是一条控制被去掉时会变红的测试。
2. 一项风险被判为“不适用”，什么情况下需要重新评估？
   - 这项风险的前提出现时，例如新增了写工具、对外通道、长期记忆、多 agent 通信或新的外部数据源。
   - 风险清单本身发布了新版本时。
   - 所以“不适用”要写明依据的前提和重新评估的触发条件，例行复核时逐条检查（Day66）。

### Day62 审计与可追溯

1. 追踪数据到期被清理之后，审计记录还需要包含哪些内容，才能说明一次写操作的依据？
   - 依据本身的 ID 和摘要：引用的文档片段 ID、工单号、提议 ID，以及关键内容的摘要。
   - 批准人和批准时看到的内容哈希，执行的 agent 和定义修订、实际模型、执行身份。
   - 动作、对象、结果和目标系统返回的对象 ID；不能只写一句“详见 trace”。
2. 为什么批准记录里要保存“批准时看到的内容版本”，只记“谁批准了”不够？
   - 内容在批准之后可能被改动，只记批准人就说不清他批准的是哪一版。
   - 有了内容哈希，执行前可以比对，执行的内容和批准的内容不一致就拒绝（Day65 的“批准后修改则作废”）。
   - 出了问题也能区分责任：是批准的内容本身有问题，还是批准后被改了。

### Day63 数据隐私与保留期

1. 用户要求删除自己的数据，除了对话记录本身，还要检查哪些地方？
   - 追踪和应用日志里的提问、回答和工具参数。
   - 派生副本：回流到评估集的用例、回答缓存、长期记忆、向量化后的记忆或摘要、少样本示例。
   - 外部平台上的副本（追踪平台、模型供应商按条款保存的数据）；具体义务要与法务或合规负责人确认。
2. “推荐问题”功能直接展示其他用户最近的提问，可能出现什么问题？怎样改成聚合数据？
   - 一个用户的提问内容（可能含个人信息、业务机密，或他人无权看到的资料片段）会直接展示给另一个用户。
   - 改法：把提问归类后只展示主题和次数，人数太少的类别不展示，避免能反推到具体的人。
   - 需要具体示例时，由人审核、脱敏后再上线。

### Day64 成本与预算治理

1. 为什么调用记录里只有模型名和 token 数，还不足以做成本治理？
   - 不知道花费属于哪个任务、用户、项目和 agent，就无法归因，也无法按层级设预算。
   - 定位失控的循环需要运行 ID 和步骤名，才能看出是哪一步在反复调用。
   - 金额还需要带版本的价格表和供应商报告的实际用量，自己数 token 会有偏差。
2. 预算用完时把上下文截短继续回答，会对用户和评估造成什么问题？
   - 用户以为拿到的是完整答案，实际上依据不全，可能据此做出错误的决定。
   - 问题被藏起来，没有人知道预算不够，也就不会去调整。
   - 评估和追踪里混进了“看似正常、实际降级”的样本，质量数据失真；正确做法是排队或明确拒绝，停止原因记为 `budget_exhausted`。

### Day65 确定性门禁

1. 为什么草稿在批准之后被修改，之前的批准必须作废？
   - 批准针对的是批准人看到的那一版内容，改动之后的内容没有人审过。
   - 不作废的话，可以先拿一版没问题的内容骗到批准，再换成别的内容发布。
   - 所以批准要绑定内容的哈希，内容一变，状态退回草稿，重新走校验和批准。
2. 只用 LLM 评审员的打分作为合并条件，会留下哪些风险？
   - 判断有波动，同样的改动可能这次通过、下次不通过，放行结果不可复现。
   - 评审员读到的代码和说明里可能有注入，诱导它给高分（Day58）。
   - 人容易过度相信它的结论，省掉自己的核对；所以它只作门禁的输入，放行要靠测试、策略检查和人工审批。
