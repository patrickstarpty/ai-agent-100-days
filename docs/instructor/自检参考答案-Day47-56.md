## 自检参考答案：Day47～56

给讲师用，不进课程目录。每题列出要点，学员答到主要意思即可，不要求措辞一致。

### Day47 工具设计

1. 为什么“返回内部 ID”对 agent 不友好，而对程序调用方却很合理？
   - 程序拿到 ID 后可以零成本地再查一次，ID 精确、稳定，适合拼接后续调用。
   - 对 agent 来说，每多查一次就多一步、多一份 token，还多一次出错的机会；一串编号也没有可供推理的语义。
   - 所以给 agent 的返回优先放人能读懂的名称和摘要，确实需要 ID 时和名称一起返回。
2. 哪些工具应该标为高风险？依据是什么？
   - 依据是后果：会写入、删除、对外发送、花钱或改权限的工具，以及结果难以撤销的工具。
   - 读取敏感数据、且与对外通道同时出现在一个 agent 里的工具，也要提高级别（Day57 的三要素）。
   - 级别由评审决定，不照抄工具自己的声明；它决定是否需要人工确认和调用上限多大。

### Day48 工具注册表与白名单

1. 只把白名单里的工具定义发给模型，为什么还不够，分发时还要再检查一遍？
   - 模型可能编出一个工具名，也可能被注入的文本诱导去要一个它没看到的工具。
   - “不发定义”只是降低概率，真正的拦截要靠代码在执行前比对白名单、权限和调用上限。
   - 两道检查各管一件事：第一道减少误用，第二道保证名单外的工具一定不执行。
2. 一个外部 MCP server 声称它的某个工具是只读的，你在注册表里应该怎样处理这条信息？
   - 把它当作待核实的参考，不直接填进注册表；规范也要求对不可信 server 的 annotations 按不可信处理。
   - 只读或写、风险级别、所需权限由自己的评审填写，写进评审文件，作为注册的依据。
   - 没经过评审的工具不进注册表，更不进任何白名单。

### Day49 工具的错误、超时与重试

1. 为什么不能用模型返回的 `tool_call_id` 作为写工具的幂等键？
   - 模型看到报错后重发同样的调用，每次的 `tool_call_id` 都不同，下游会当作两个请求各执行一次。
   - 幂等键要表达“同一任务里的同一个动作”，应由代码根据任务 ID、工具名和规范化后的参数算出。
   - 键不让模型生成、也不让它看见，避免被改写或被注入诱导。
2. 工具返回“无权访问”之后，为什么不应该让模型自己想办法继续完成任务？
   - 权限拒绝不是模型能改正的错误，它“想办法”往往就是换一个工具去拿同一份数据，正好绕过最小权限（Day59）。
   - 正确处理是代码按 `permission_denied` 停止、记录、如实告诉用户。
   - 被拒绝的调用还要进追踪，它可能是注入或工具描述不清的信号。

### Day50 MCP 架构

1. 为什么说“工具描述是不可信输入”？
   - 工具描述由 server 的提供方编写，在任何调用发生之前就进入了模型的上下文。
   - 模型分不清指令和数据，描述里夹带的文字可能改变它的行为（Day57、Day58）。
   - 所以接入 server 要评审描述，描述变化时要能发现，并重新评审。
2. stdio 和 Streamable HTTP 两种传输，在身份和权限上各自要注意什么？
   - stdio：server 是本机进程，以启动它的人的身份和权限运行，能读到这个人能读的文件和环境变量，要控制它能接触的范围。
   - Streamable HTTP：远端 server 要认证调用方，按规范走 OAuth、校验令牌受众；server 能看到传过去的参数，其中可能有用户数据。
   - 两种情况下，涉及“这个人能不能看”的数据都要按最终用户的身份过滤（Day52）。

### Day51 编写一个 MCP server

1. 为什么 stdio server 不能往 stdout 打印日志？
   - stdio 传输用 stdout 承载 JSON-RPC 消息，混进任何其他文本，client 都会解析失败。
   - 日志一律写到 stderr，或者写文件。
   - 排查“工具没被发现”时，先看 stderr 有没有报错。
2. “没找到课程”和“limit 越界”这两种情况，你的 server 分别怎样返回？为什么这样区分？
   - 没找到是正常结果，作为普通文本返回，附上下一步建议（例如换一个更短的关键词）。
   - limit 越界是参数错误，抛出异常，client 收到 `is_error` 为真的结果，模型读到说明后改参数。
   - 区分开，模型才知道该换查询条件还是该改调用方式；把“没找到”当错误会让模型反复重试。

### Day52 MCP 的认证与身份透传

1. MCP server 为什么不能把 client 发来的令牌原样转给下游？不转的话，下游怎样知道请求来自哪位用户？
   - 规范禁止 server 接受或转递签发给别人的令牌；原样转发会让令牌的受众失去意义，一张令牌能在多个系统通用。
   - 做法是在 server 这一跳用收到的用户令牌换一张以下游为受众、仍代表这位用户的令牌（例如 on-behalf-of）。
   - 下游凭这张新令牌识别用户，按这位用户的权限过滤。
2. 下游在缺少用户令牌时返回未过滤的结果，你的链路要在哪一步、用什么方式防住？
   - 在调用下游之前，由宿主或 server 代码检查用户令牌是否存在且有效，缺失就直接拒绝。
   - 不退回服务账号，也不依赖下游的默认行为。
   - 在评估集里加一条“不带令牌应当被拒绝”的用例，防止以后的改动把这道检查弄丢。

### Day53 Skills：渐进式披露

1. 为什么 `description` 写得好不好，直接决定一个 Skill 有没有用？
   - 平时进上下文的只有名称和简介，模型拿用户请求和 `description` 比对，决定要不要加载正文。
   - 简介没写清“什么时候用”，该触发时不触发，正文写得再好也用不上；写得太宽又会抢走别的 Skill 的触发。
   - 所以要用应触发和不应触发的用例评估触发准确率。
2. 一个 Skill 的正文写着“用 tickets_update 工具把结论写回工单”，而当前 agent 的白名单里没有这个工具，会发生什么？
   - 工具定义不会发给模型；模型即使照着正文去要这个工具，分发层也会按白名单拒绝。
   - 拒绝原因作为工具结果交还模型，它应当如实告诉用户这一步做不了。
   - Skill 只能影响模型读到的文字，不能扩大白名单（Day48、Day54）。

### Day54 导入外部 Skill 的信任边界

1. 一个 Skill 从未被触发过，为什么仍然可能影响 agent 的行为？
   - 每个装上的 Skill，名称和简介每次任务都放在系统提示词里。
   - 简介里夹带的指令会一直在上下文中，模型可能在无关任务里照做。
   - 所以审核要覆盖简介，个人导入的 Skill 不能和写工具出现在同一个 agent 里。
2. 为什么 Skill 的更新必须生成新修订并重新审核，而不能在原处修改？
   - 审核结论只对审过的那份内容成立，原处修改会让已审核的结论悄悄失效。
   - agent 定义引用修订号，修订不变，agent 的行为就不变；要用新内容就发布新的定义，评估和回滚都有对象。
   - 用内容哈希做修订号，任何改动都会被发现。

### Day55 Agent 定义

1. 为什么步数上限和权限不应该写在 agent 定义里？
   - 能编辑定义的人，就能自己给自己放宽预算和权限，定义也会被复制和分享。
   - 上限按 agent 类型和任务类型由平台统一设定（Day45），权限按使用者身份由平台决定（Day59）。
   - 定义描述“想做什么”，平台决定“最多能做多少”；定义里即使写了也不生效。
2. 一个用户定义的 agent 被分享给同事使用，它访问数据时应该用谁的身份？
   - 用正在使用它的那位同事本人的身份，不用作者的身份。
   - 否则作者的权限会随着分享传给别人，造成越权。
   - 这也是用户定义的 agent 默认只能选只读工具、能力不超过使用者本人的原因。

### Day56 阶段实战：给助手接入工具与 Skill

1. 你的实现里，哪些边界是由代码保证的，哪些仍然只写在提示词或 Skill 正文里？后者被绕过时会发生什么？
   - 代码保证的通常有：白名单、权限、调用上限、只登记评审过的 MCP 工具、Skill 脚本不执行、启动校验。
   - 只写在提示词里的常见有：引用格式、“不要猜测”、Skill 里的操作步骤。
   - 后者被注入或模型忽略时会失效，所以要靠评估发现，凡是有后果的边界都应移到代码里。
2. 如果 MCP server 的作者悄悄修改了 `courses_search` 的描述，你的助手会受到什么影响？你会在哪一步发现？
   - 新描述会在下次 `tools/list` 后进入上下文，可能改变模型何时调用、怎样填参数，甚至夹带指令。
   - 只登记评审过的工具挡不住描述被改，因为工具名没变。
   - 发现手段：登记时记录描述的哈希并与评审时比对，或在 CI 里用 Inspector 冒烟测试比较工具列表；不一致就停用并重新评审。
