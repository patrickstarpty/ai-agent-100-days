## 自检参考答案：Day23～34

给讲师用，不进课程目录。每题列出要点，学员答到主要意思即可，不要求措辞一致。Day34 是阶段复盘课，没有自检题，不在下面列出。

### Day23 评估全景

1. 为什么回归评估的通过率低于 100% 是问题，而能力评估的通过率 100% 也是问题？
   - 回归评估测的是“以前会的还会不会”，低于 100% 说明有改动造成了退步，应当拦住发布。
   - 能力评估测的是“能做到什么”，通过率满了说明题目已经不再反映系统的上限，没法再指出改进方向。
   - 两者的健康状态正好相反，不能用同一个目标（“越高越好”）去看。
2. 举一个你项目里“评路径会误伤”的例子。
   - 没有标准答案，看学员能否举出具体例子，例如要求固定的检索顺序、固定的工具调用步骤或固定的重试次数。
   - 好的例子会说明：换了个更好的做法后，评估反而判失败，暴露出评分器在检查步骤而不是结果。

### Day24 错误分析

1. 为什么不建议把错误分析外包给不了解业务的人？
   - “什么算失败”需要业务判断，不了解业务的人容易按字面通顺与否打分，标出来的类别和真实问题对不上。
   - 错误分析的产出（失败分类表）要指导后面所有评分器和评估集，标错了会让整套评估体系跑偏。
2. 你的分类表里，哪几类可以用代码评分器直接检出？
   - 没有标准答案，常见的是“没引用该引用的来源”“该弃答没弃答或反过来”“泄露无权来源”“引用了没取回的片段”这几类。
   - 需要判断“结论是否真由证据推出”“是否答非所问”的类别，留给模型评审员。

### Day25 评估集设计

1. 你的格式里，哪些期望可以完全由代码检查？
   - 没有标准答案，常见的是 `mustCiteSources`、`mustContain`（短字符串）、`mustAbstain`、`mustNotCiteSources`、`edges` 这类结构化字段。
   - 需要人工或模型判断的，例如“措辞是否得体”，不属于这一类。
2. 语料更新后，怎样发现哪些用例的期望已经过期？
   - 给评估集和语料都记一份摘要（`corpusDigest`），评估脚本运行前核对两者是否对应。
   - 对不上时提醒复核，而不是直接套用旧期望继续跑分，避免分数变化和语料变化混在一起看不清楚。

### Day26 代码评分器

1. 为什么“该弃答却回答”记为 `wrong`，而“该回答却弃答”只记为 `miss`？
   - 两种失败对用户的伤害不同：错答可能带着不存在或无权访问的引用，用户会带着错误信息继续工作；没答出，用户大不了去别处找。
   - 把更有害的一类标得更重，是为了让汇总结果能区分“不敢答”和“编答案”这两种完全不同的风险。
2. `mustContain` 里放一整句参考答案，会带来什么问题？
   - 模型措辞稍有不同（标点、同义词、语序）就会被判定没包含，造成大量误判为 `miss`。
   - `mustContain` 应该只放短而确定的字符串（数字、专有名词），比较前还要做规范化（去空白、统一大小写）。

### Day27 LLM 评审员与校准

1. 你的人工标注里只有 5 条不通过，算出来的漏判率能说明多少？下一步该做什么？
   - 5 条样本太少，漏判率的波动很大，一条标注错了，漏判率就能从 0 跳到 20%，不足以下结论。
   - 下一步是继续标注更多“真失败”的样本，让分母足够大之后再看这个数字。
2. 哪些检查你原本打算用模型评审，其实可以改成代码检查？
   - 没有标准答案，常见的是“引用的格式是否合法”“引用的来源是否取回过”这类其实有确定答案的检查，原本也可能被当成“让模型顺便看一眼”的一部分。
   - 判断标准：凡是能写成字符串匹配、集合比对或读环境状态的，都应该挪给 Day26 的代码评分器，模型评审员只留给真正需要判断的部分。

### Day28 检索评估

1. recall@5 很高而 MRR 很低，说明什么？应当优先改哪一段？
   - 说明相关片段基本都被找到了（不缺），但排序把它们放得靠后，用户或下游生成很可能用不到排名靠前的那几条。
   - 应当优先改第二段（重排），而不是去改第一段的召回策略。
2. 为什么“检索没取回但回答正确”的用例也值得单独看？
   - 这类回答很可能是模型凭自身知识或碰巧答对的，资料一变或换一批问题就不可靠。
   - 单独看能避免把“模型瞎蒙对了”误判成“系统表现好”，并提示检索本身还有缺口要补。

### Day29 Agent 轨迹与工具调用评估

1. “不得调用 `deploy`”为什么不能只靠最终状态检查？
   - 只看最终状态时，agent 可能调用了 `deploy` 又把结果撤回，最终状态看起来“没有部署”，但越权动作已经发生过。
   - 这类红线必须在过程里查工具调用记录，而不是只信任结果快照。
2. 一个任务五次运行里通过三次，你会怎样向团队报告它的结果？
   - 不能只报一个“通过率 60%”，要同时给出“至少一次成功”和“每次都成功”两个口径（这里分别是高和 60%）。
   - 再看失败的两次违反了哪条约束、卡在哪个里程碑，而不是只给一个数字。

### Day30 CI 回归

1. 替身模型跑通的评估，证明了什么，没证明什么？
   - 证明了链路本身能跑通：引用格式合法、权限过滤生效、各个环节接得上，不依赖真实模型的输出质量。
   - 没有证明真实模型给出的回答是否正确、是否真的有依据，这部分要靠质量回归（真实模型跑评估集）来看。
2. 真实模型的评估结果有波动时，怎样判断一次下降是不是真的退步？
   - 先看是不是噪声：同样配置重跑几次，比较这次的下降幅度和基线自身的波动范围。
   - 逐条看翻转的用例（而不只看总分），看失败是否集中在某一类、是否和这次改动的方向吻合。

### Day31 在线评估与用户反馈

1. 为什么反馈表里只存 trace ID，不复制问题和回答原文？
   - 原文留在追踪里统一管理保留期和查看权限，反馈表另存一份会造成同一份数据两套访问控制、两套保留期。
   - 只存 trace ID 也能把反馈和那次请求的完整上下文（检索结果、引用、模型参数）关联起来，便于复核。
2. 只复核被点踩的请求，会漏掉哪些失败？
   - 大多数用户不会点任何按钮，点踩的人也不代表全体，很多真实失败完全没人举报。
   - 需要再加一部分纯随机抽样的请求，才能发现没有被任何信号覆盖的失败类型。

### Day32 实验与对比

1. 新提示词的总通过率比基线高了两条用例，你还需要看哪些信息才能决定采用它？
   - 要看逐条翻转：是单纯修好了两条，还是修好了几条又弄坏了几条，总分正好抵消出“+2”。
   - 还要和不改动时重跑的噪声水平比较，确认这个差异明显大于基线自身的波动，并看翻转的用例是否集中在预期会受影响的那一类。
2. 为什么留出的那部分评估集只能在最后用一次？
   - 日常调参只看开发集，如果留出集也被反复查看和用来调整，它就会被过拟合，失去检验泛化能力的作用。
   - 只在决定上线前用一次，才能如实反映这次改动在没见过的问题上表现如何。

### Day33 评估平台实践

1. 如果评估集只放在平台上、不进仓库，会失去哪些能力？
   - 失去像代码一样评审、回溯版本变化的能力，改动评估集不会经过和代码一样的审查流程。
   - CI 里的结构性回归（Day30）要能只靠仓库运行，评估集只在平台上会让这条线路依赖平台是否可用。
2. 平台上的人工标注结果，除了补充评估集，还能用来做什么？
   - 用来校准模型评审员（Day27）：对照人工标注计算一致率和两类错误率。
   - 也可以用来发现新的失败类型，反过来更新错误分析的失败分类表（Day24）。
