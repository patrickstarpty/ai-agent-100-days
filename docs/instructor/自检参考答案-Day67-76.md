## 自检参考答案：Day67～76

给讲师用，不进课程目录。每题列出要点，学员答到主要意思即可，不要求措辞一致。Day76 是阶段复盘课，用阶段验收清单代替自检，这里不列。

### Day67 追踪：trace 与 span

1. 接口进程和 worker 各自都有 span，但在追踪平台里显示成了两条 trace，最可能是哪一步漏了？
   - 跨进程时没有传递追踪上下文：接口进程没把 `traceparent` 注入任务消息，或 worker 没有提取出来作为父上下文。
   - 也可能是队列库的插桩没装，或手写和插桩两套传播互相覆盖。
   - 排查：看任务消息里有没有 `trace` 字段，看 worker 的根 span 是否带父 span ID。
2. 为什么“检索到的片段”记 ID 比记原文好？只记 ID 会给排查带来什么不便，怎么弥补？
   - 原文又大又敏感，记进追踪后，能看追踪的人都能看到，绕开了源系统的权限（Day21）和保留期（Day63）。
   - 只记 ID 时，排查要回源系统取原文；文档更新后，原来的版本可能已经不在。
   - 弥补：ID 带上来源版本和位置；需要时把内容存到单独的、有访问控制和保留期的存储，span 上只记引用。

### Day68 OpenTelemetry 与 GenAI 语义约定

1. 换追踪后端时，代码里哪些部分要改，哪些不用改？
   - 不用改：创建 span、记属性的埋点代码，以及 OTLP 协议本身。
   - 要改：导出器的地址和认证（配置），或者只改 Collector 的配置，应用完全不动。
   - 如果用了某个后端的私有 SDK 或回调，这部分要换掉，这正是优先用开放标准的原因。
2. GenAI 语义约定还处在 Development 状态，这对你的埋点代码和后端里的看板意味着什么？
   - 属性名和取值可能调整，升级插桩库后，看板和告警依赖的属性可能改名。
   - 做法：属性名集中定义在一处（例如模型入口），不散落在业务代码里；升级插桩库时核对变更说明。
   - 后端看板按属性名做的查询要有测试或巡检，避免改名后静默变空。

### Day69 追踪与评估后端

1. 为什么说“追踪平台里的原文”是 Day21 权限问题的一部分？
   - Day21 要求谁能看什么由源系统权限决定；追踪里的问题、检索片段、回答都是从受控资料派生出来的。
   - 追踪平台只按组织、项目分配权限，不认识源系统的文档级权限，能进项目的人就可能看到无权看的内容。
   - 所以默认不记原文、内容类数据单独存放并设访问控制和保留期，生产追踪只给排查需要的人。
2. 评估（Day23～Day34）和追踪共用一个平台有什么好处？如果两者分开，要靠什么把它们连起来？
   - 好处：线上坏例子能直接加进数据集，在线分数（Day31）和离线实验（Day33）挂在同一份 trace 和版本上，少一层导出。
   - 分开时：用 trace ID 和版本清单（Day74）关联两边；写导出脚本把选中的 trace 转成评估用例。
   - 无论哪种，都要说清哪边是权威数据，避免两边数据不一致时没人能裁决。

### Day70 模型网关

1. 如果业务代码里有两处直接调用模型 SDK，会给评估和成本核算带来什么问题？
   - 这两处绕过了网关的统一记录，token、实际模型、错误没有进追踪，成本核算漏算。
   - 预算、超时、重试、数据范围策略对它们不生效；换模型时这两处也要单独改，容易漏。
   - 评估时说不清某次回答是哪个模型给的，结果无法复现和归因。
2. API key 和托管身份相比，在审计上差在哪？
   - API key 是共享的秘密，日志里只能看到“用了这把 key”，看不出是哪个服务或哪个 agent。
   - 托管身份走 Entra ID 和 RBAC，每次调用能对应到具体身份，权限可以按身份收窄、撤销不影响别人。
   - key 还有泄露和轮换的问题，泄露后无法区分合法和非法调用。

### Day71 延迟与成本优化

1. 两位权限不同的用户问了一字不差的问题，结果缓存应当怎样处理？
   - 缓存键里必须有权限范围（可见资料范围的摘要），两人的键不同，各自命中各自的结果。
   - 绝不能让一位用户拿到依据另一位用户可见资料生成的答案（Day21）。
   - 键里还要有索引版本、提示词版本和模型，资料或提示词更新后自动失效。
2. 一项优化让成本降了不少，通过率也降了一点，你用什么来决定要不要上线？
   - 先看下降的是哪些用例：如果集中在关键类型或安全用例，直接不上线。
   - 把通过率下降的代价（用户流失、人工返工）和省下的钱放在一起算，必要时只对部分请求类型启用。
   - 结论和依据写进实验记录（Day32），并确认这次只改了一项。

### Day72 可靠性：队列、租约与重试

1. 为什么尝试次数要在领取任务时加一，而不是在捕获到异常时加一？
   - worker 崩溃时根本执行不到异常处理那一行，按失败计数，计数永远不会增加。
   - 一个每次都把 worker 弄崩的任务就会被无限收回、无限重跑。
   - 领取时计数保证每次尝试都被算上，超过上限就进入死信等人看。
2. 一个 worker 卡住超过租约时间后又恢复，正好和接手它的 worker 同时运行。哪些设计保证结果不会被写两次？
   - 交结果时带条件更新：只有 `lease_owner` 仍是自己才写入，原 worker 写入失败后放弃（`LeaseLost`）。
   - 结果和 outbox 事件在同一个事务里，条件不满足时整体回滚，不会发出事件。
   - 过程中的外部写操作带幂等键（Day49），接收方按事件 ID 去重。

### Day73 部署形态

1. 你的 agent 有哪些需求是配置型 agent 承载不了的？
   - 确定性的编排控制：固定的步骤顺序、代码判定的门禁、有界循环和停止原因（Day45、Day65）。
   - 自己管理的检查点和长时间人工等待（Day40、Day41），以及带幂等键的写操作。
   - 按版本清单钉住运行、可测试的版本化（Day74）；学员举出自己项目的具体需求即可。
2. 自行部署时，“每个 agent 一个身份”要怎样实现？
   - 每个 agent（或剧本）用独立的服务身份或托管身份运行，不共用一把密钥。
   - 每个身份只授予它需要的权限（Day59）；写操作需要用户身份时，用身份透传（Day52）以用户身份执行。
   - 身份写进追踪和审计记录（Day62），密钥放密钥管理并能单独撤销。

### Day74 版本化

1. 运行开始时按标签解析提示词，之后为什么要按版本号取，不能每一步都按标签取？
   - 标签随时可能被移到别的版本上，按标签取，一次长任务可能前后用了两个版本。
   - 出了问题既无法复现，也说不清是哪个版本造成的。
   - 开始时解析一次、记进版本清单，之后按版本号取，评估和追踪也能按版本分组。
2. 哪些状态结构的改动可以不写迁移就直接恢复，哪些不行？
   - 可以：只加带默认值的可选字段，新节点不在旧任务的路径上。
   - 不行：删字段、改字段含义或类型、改 reducer 的合并方式、删除或改名节点。
   - 不兼容又没有迁移时，保留旧版本 worker 排空旧任务，或以 `version_incompatible` 停止，不让新代码“试着读”。

### Day75 发布与回滚

1. 为什么灰度要和同一时段的对照组比，而不比较上线前后的数字？
   - 时段、用户和问题分布本身在变，前后对比里混着这些变化，分不清是改动造成的还是环境变了。
   - 同时段对照组和实验组经历同样的环境，差异才能归到这次改动。
   - 分流要稳定（按用户或会话），否则两组数据会互相污染。
2. 新提示词灰度了一天后决定回滚，在此期间它已经回复了一些工单评论。回滚之后还要做什么？
   - 把指针移回旧版本只能阻止新的问题，已发出的评论收不回来。
   - 用审计记录（Day62）和版本清单找出受影响的工单，逐条评估是否需要更正、撤回或通知相关人。
   - 复盘为什么门禁没拦住，补回归用例；写操作类改动以后先影子运行。
