## Day06 - 手写一个 Agent 循环

> 大模型应用基础 ｜ 建议用时 1 小时

> **一句话**：一个 agent 的核心只有二十来行：调用模型，执行它要的工具，把结果交回去，重复到它不再要工具为止。
>
> **放在全局看**：之后学到的所有框架和工程手段，都是在给这个循环加护栏：预算、持久化、人工确认、权限。

### 学习目标

- 不借助任何框架，写出一个完整的 agent 循环并运行。
- 说清循环里每一部分的作用，以及去掉它会发生什么。
- 知道这个最小循环还缺什么，后续课程分别在哪里补上。

### 核心概念

**打个比方**：像你和同事来回对话：他说“帮我查个数”，你查完告诉他，他再说下一步，直到他说“好了，结论是……”。

**从一次调用到一个循环**

Day05 的代码只处理了一轮：模型请求一次工具，拿到结果，作答。真实任务往往需要多轮，例如先查两个订单，再把金额相加。把 Day05 的 `if` 换成循环，让模型反复“请求工具、看结果”，直到它不再请求工具，这就是 agent。

循环本身很短。它的全部状态就是 `messages` 列表：用户的输入、模型每一步的决定、每个工具的结果，都按顺序追加在里面。

**第一部分：工具和分发表**

```python
# tools.py
import ast
import json
import operator

ORDERS = {
    "A1001": {"status": "已发货", "amount": 129.0},
    "A1002": {"status": "待付款", "amount": 58.5},
}

def get_order(order_id: str) -> str:
    order = ORDERS.get(order_id)
    if order is None:
        raise ValueError(f"订单 {order_id} 不存在，请核对订单号")
    return json.dumps(order, ensure_ascii=False)

_OPS = {
    ast.Add: operator.add, ast.Sub: operator.sub,
    ast.Mult: operator.mul, ast.Div: operator.truediv,
}

def _eval(node):
    if isinstance(node, ast.Constant) and isinstance(node.value, (int, float)):
        return node.value
    if isinstance(node, ast.BinOp) and type(node.op) in _OPS:
        return _OPS[type(node.op)](_eval(node.left), _eval(node.right))
    if isinstance(node, ast.UnaryOp) and isinstance(node.op, ast.USub):
        return -_eval(node.operand)
    raise ValueError("只支持数字、括号和 + - * /")

def calculate(expression: str) -> str:
    return str(_eval(ast.parse(expression, mode="eval").body))

def _spec(name: str, description: str, param: str, param_desc: str) -> dict:
    return {"type": "function", "function": {
        "name": name,
        "description": description,
        "parameters": {
            "type": "object",
            "properties": {param: {"type": "string", "description": param_desc}},
            "required": [param],
        },
    }}

TOOLS = [
    _spec("get_order", "按订单号查询订单状态和金额。用户问到具体订单时使用。",
          "order_id", "订单号，例如 A1001"),
    _spec("calculate", "计算一个四则运算表达式。任何算术都用它完成，不要心算。",
          "expression", "只含数字、括号和 + - * / 的表达式，例如 (129 + 58.5) * 2"),
]

TOOL_FUNCS = {"get_order": get_order, "calculate": calculate}
```

`TOOLS` 是给模型看的说明，`TOOL_FUNCS` 是给你的代码用的分发表，两者通过工具名对应。计算器用 `ast` 解析表达式，只放行数字和四则运算。表达式是模型生成的，直接交给 `eval` 等于让模型在你的机器上执行任意代码。

**第二部分：循环**

```python
# agent.py
import json
from llm import chat
from tools import TOOLS, TOOL_FUNCS

SYSTEM = (
    "你是订单助手。需要订单数据或计算时使用工具，不要凭记忆回答。"
    "工具返回错误时，根据错误信息调整后重试，或者向用户说明情况。"
)

def run_tool(call) -> str:
    fn = TOOL_FUNCS.get(call.function.name)
    if fn is None:
        return f"错误：没有名为 {call.function.name} 的工具"
    try:
        args = json.loads(call.function.arguments)
        return fn(**args)
    except Exception as e:
        return f"错误：{type(e).__name__}: {e}"

def run_agent(user_input: str, max_steps: int = 8) -> str:
    messages = [
        {"role": "system", "content": SYSTEM},
        {"role": "user", "content": user_input},
    ]
    for step in range(1, max_steps + 1):
        resp = chat(messages, tools=TOOLS)
        msg = resp.choices[0].message
        if not msg.tool_calls:                 # 停止条件：模型不再请求工具
            return msg.content or ""
        messages.append(msg)
        for call in msg.tool_calls:
            result = run_tool(call)
            print(f"[第 {step} 步] {call.function.name}({call.function.arguments}) -> {result}")
            messages.append({"role": "tool", "tool_call_id": call.id, "content": result})
    raise RuntimeError(f"{max_steps} 步内没有完成任务")

if __name__ == "__main__":
    print(run_agent("订单 A1001 和 A1002 的金额加起来是多少？"))
```

一次典型的运行里，模型先请求查询两个订单（可能在同一步里发出两个 tool call，也可能分两步），再请求 `calculate`，最后不带 tool call 给出答案。具体走几步由模型决定，每次运行可能不同。

**逐部分说明**

| 部分 | 作用 | 去掉会怎样 |
| --- | --- | --- |
| `messages` 列表 | 保存任务到目前为止的全部过程，是 agent 的工作记忆 | 模型每一步都从头开始，看不到之前的结果 |
| 停止条件 `not msg.tool_calls` | 模型给出不带工具请求的回答，即认为任务完成 | 循环无法正常结束 |
| `max_steps` | 给循环加硬上限 | 模型反复调用同一个工具时，程序一直运行并持续计费 |
| 分发表 `TOOL_FUNCS` | 从工具名找到函数；名字不在表里就不执行 | 用 `eval` 或 `getattr` 按名字找函数，模型可以调用到你没打算开放的东西 |
| `run_tool` 里的 `try/except` | 把工具错误变成返回给模型的结果 | 一次参数错误就让整个任务崩溃 |
| 每个 tool call 都追加结果 | 保持消息序列完整 | 缺一条结果，下一次请求被接口拒绝 |
| `print` | 记录每一步调用了什么、得到了什么 | 出了问题无从排查 |

**工具错误是给模型的信息**

模型填错参数、订单不存在、表达式不合法，这些都是任务过程中的正常情况。把错误信息作为工具结果返回，模型通常能自己纠正：换一个参数重试，或者告诉用户订单号有误。所以错误信息要写得让模型能据此行动，“订单 A9999 不存在，请核对订单号”比只有一个 `KeyError` 有用。

`except Exception` 范围很宽，会把你代码里的 bug 也包装成工具结果交给模型。这是有意的取舍：循环保持运行，同时每一步都有记录，bug 能从日志里看到。

**达到步数上限**

走完 `max_steps` 仍未结束，说明任务没有完成。代码在这里抛出异常，调用方必须把“未完成”如实告诉用户。把最后一步的中间内容当作答案返回，是 agent 系统里常见的一类缺陷。

**这个循环还缺什么**

| 缺少的能力 | 在哪里补 |
| --- | --- |
| 上下文越来越长，成本没有控制 | Day07 |
| 运行期间用户看不到进度，无法取消 | Day08 |
| 模型调用本身失败时没有重试 | Day09 |
| 有副作用的工具执行前没有人工确认，中断后不能恢复 | Day35–46 |
| 没有权限控制 | Day57–66 |

后面学到的框架，核心都是这个循环加上述能力。
