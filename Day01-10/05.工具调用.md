## Day05 - 工具调用

> 大模型应用基础 ｜ 建议用时 1 小时

> **一句话**：模型只负责提出“要调用哪个工具”，真正动手执行的永远是你的代码。
>
> **放在全局看**：工具是 agent 接触外部世界的唯一途径，所以也是权限和安全控制的落点（Day47~66）。

### 学习目标

- 能说清工具调用协议的五个步骤，以及每一步由谁完成。
- 能写出一个工具的定义，并跑通“模型请求、代码执行、结果回传、模型作答”的完整过程。
- 知道一份好的工具描述包含哪些内容。

### 核心概念

**打个比方**：模型像一位只能动口的指挥：它说“查一下订单 A1001”，动手去查的是你。

**协议的五个步骤**

| 步骤 | 谁做 | 内容 |
| --- | --- | --- |
| 1. 描述工具 | 你 | 随请求发送工具的名称、描述、参数的 JSON schema |
| 2. 请求调用 | 模型 | 返回一个 tool call：工具名加一组参数 |
| 3. 执行 | 你的代码 | 解析参数，调用真正的函数 |
| 4. 回传结果 | 你的代码 | 把执行结果作为 `tool` 角色的消息追加到对话里，再次调用模型 |
| 5. 继续 | 模型 | 读结果，给出回答，或者请求下一次调用 |

**模型自己不执行任何东西**

模型的输出始终是文本。Tool call 只是一段结构化的文本，意思是“我想用这些参数调用这个工具”。查数据库、读文件、发请求，全部发生在你的进程里，由你的代码完成。

由此得出两点：

- 能做什么、不能做什么，由你的代码决定。模型请求了一次调用，你的代码可以拒绝执行。
- 参数是模型生成的，要当作不可信的输入来校验，和对待用户提交的表单一样。

**一个工具的完整例子**

```python
import json
from llm import chat   # Day02 写的薄封装

ORDERS = {
    "A1001": {"status": "已发货", "eta": "2 天后"},
    "A1002": {"status": "待付款", "eta": None},
}

def get_order_status(order_id: str) -> str:
    order = ORDERS.get(order_id)
    if order is None:
        return json.dumps({"error": f"订单 {order_id} 不存在，请向用户核对订单号"}, ensure_ascii=False)
    return json.dumps(order, ensure_ascii=False)

TOOLS = [{
    "type": "function",
    "function": {
        "name": "get_order_status",
        "description": (
            "按订单号查询订单的当前状态和预计送达时间。"
            "用户询问某个具体订单的进度时使用。"
            "用户没有提供订单号时，先向用户询问，不要猜测订单号。"
        ),
        "parameters": {
            "type": "object",
            "properties": {
                "order_id": {
                    "type": "string",
                    "description": "订单号，字母 A 加四位数字，例如 A1001",
                },
            },
            "required": ["order_id"],
        },
    },
}]

messages = [{"role": "user", "content": "帮我看看订单 A1001 到哪了"}]
resp = chat(messages, tools=TOOLS)                      # 步骤 1、2
msg = resp.choices[0].message

if msg.tool_calls:
    messages.append(msg)                                # 先放回带 tool_calls 的 assistant 消息
    for call in msg.tool_calls:
        args = json.loads(call.function.arguments)      # arguments 是 JSON 字符串
        result = get_order_status(**args)               # 步骤 3：执行发生在你的代码里
        messages.append({                               # 步骤 4
            "role": "tool",
            "tool_call_id": call.id,
            "content": result,
        })
    resp = chat(messages, tools=TOOLS)                  # 步骤 5

print(resp.choices[0].message.content)
```

对照代码注意四点：

- 模型请求调用工具时，`finish_reason` 是 `tool_calls`，`content` 可能为空。
- `function.arguments` 是字符串，需要 `json.loads`。模型偶尔会生成不合法的 JSON 或漏掉参数，这里没有处理，Day06 补上。
- 一次响应可以包含多个 tool call。每一个都要有一条对应的 `tool` 消息，用 `tool_call_id` 配对。
- 顺序固定：先追加模型的 assistant 消息，再追加工具结果。缺了前者，或者有 tool call 没有对应的结果，下一次请求会被接口拒绝。

**好的工具描述**

模型只能通过名称、描述和参数 schema 了解一个工具。描述写得含糊，模型就会在不该用的时候用，或者填错参数。

| 要写清的内容 | 例子 |
| --- | --- |
| 工具做什么，返回什么 | 查询订单的当前状态和预计送达时间 |
| 什么时候用，什么时候不用 | 用户问具体订单的进度时使用；问退货政策时不用 |
| 参数的格式和例子 | 订单号，字母 A 加四位数字，例如 A1001 |
| 信息不足时怎么办 | 没有订单号时先问用户，不要猜 |

其他建议：名称用“动词 + 对象”，如 `get_order_status`；取值有限的参数用 `enum`；必填项放进 `required`。

**工具结果怎么写**

结果是给模型读的文本，写法直接影响它下一步的判断。

- 返回模型作答需要的字段，不要把整条数据库记录原样倒出来。
- 出错时返回说明性的内容：出了什么错，可以怎么处理。上面的“订单不存在，请向用户核对订单号”就是例子。
- 结果会留在上下文里，每一轮都要计费，所以要控制长度（Day07）。

### 动手练习

1. 运行上面的例子。在执行工具的地方加一行打印，输出工具名和参数。
2. 依次换成下面三个问题，记录模型是否调用了工具、参数是什么、最终怎么回答：
   - “你们的退货政策是什么？”
   - “帮我查一下我的订单。”
   - “订单 A9999 到哪了？”
3. 把工具的 `description` 改成只有“查询”两个字，参数的 `description` 删掉，重跑第 2 步，比较差别。

### 自检

1. 从模型返回 tool call 到用户看到最终回答，中间哪些事发生在你的代码里？
2. 为什么要把模型生成的工具参数当作不可信输入？举一个不校验会出问题的例子。
