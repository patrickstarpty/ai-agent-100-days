## Day02 - 调用模型 API

> 大模型应用基础 ｜ 建议用时 1 小时

> **一句话**：调用模型就是发一组消息、收一条回答，其余一切都建立在这一次调用之上。
>
> **放在全局看**：这是整个系统最底层的一块砖。Day03~10 的代码都通过今天写的 `chat` 调用模型，Day09 在它上面加超时和重试；Day70 的模型网关，就是把这个函数做成全系统唯一的入口。

### 学习目标

- 能用代码完成一次模型调用，并读出回答、结束原因和 token 用量。
- 说清 system、user、assistant 三种角色各放什么内容，以及多轮对话是怎么实现的。
- 把模型调用收在一个薄函数后面，后续课程都通过它调用。

### 核心概念

**打个比方**：模型没有记忆。每次调用都像给一位从没见过你的专家递一张纸条，他只能看到纸条上写的内容。

**一次调用的全貌**

本阶段用 `litellm` 库，它用同一套 OpenAI chat-completions 格式调用不同供应商的模型。模型名从环境变量读取，写法通常是 `供应商/模型名`，具体以你所用供应商在 litellm 文档里的说明为准。litellm 只是其中一种接法，直接用供应商的官方 SDK 或别的封装库也可以，只要把调用收在下文的 `llm.py` 里，换的时候只改这一个文件。

```python
import os
from litellm import completion

MODEL = os.environ.get("LLM_MODEL", "your-model-name")

resp = completion(
    model=MODEL,
    messages=[
        {"role": "system", "content": "你是一个简洁的技术助手，回答不超过三句话。"},
        {"role": "user", "content": "什么是上下文窗口？"},
    ],
    max_tokens=300,
    temperature=0.2,
)

print(resp.choices[0].message.content)        # 回答正文
print(resp.choices[0].finish_reason)          # 结束原因
print(resp.usage.prompt_tokens, resp.usage.completion_tokens)
```

**消息与角色**

| 角色 | 谁写的 | 放什么 |
| --- | --- | --- |
| system | 开发者 | 身份、任务、规则、输出要求。一次对话里通常只有一条，放在最前面 |
| user | 用户，或你的程序 | 问题和待处理的数据 |
| assistant | 模型 | 模型之前的回答 |

Day05 还会出现第四种角色 `tool`，用来放工具的执行结果。

模型接口是无状态的，它不记得上一次调用。多轮对话的做法是每次都把完整的历史发过去：把模型的回答作为 assistant 消息追加到列表，再追加新的 user 消息，然后整个列表重新发送。所谓“记忆”就是你的代码维护的这个列表。

**三个关键参数**

| 参数 | 含义 | 建议 |
| --- | --- | --- |
| `model` | 用哪个模型 | 从配置读取，不要散落在业务代码里 |
| `max_tokens` | 本次输出的 token 上限 | 每次都设。设得过小，回答会被截断 |
| `temperature` | 输出的随机程度，越低越稳定 | 抽取、分类用低值；需要多样性的写作可以调高 |

不同模型支持的参数不完全相同。传了某个模型不支持的参数时，litellm 默认会报错；调用时加 `drop_params=True`，它会丢掉不支持的参数再发送。

**读响应**

- `resp.choices[0].message.content`：回答文本。
- `resp.choices[0].finish_reason`：`stop` 表示模型正常结束；`length` 表示达到 `max_tokens` 被截断；`tool_calls` 表示模型要求调用工具（Day05）。
- `resp.usage`：`prompt_tokens` 是输入 token 数，`completion_tokens` 是输出 token 数。计费和上下文预算都基于这两个数字（Day07）。
- `resp.model`：实际应答的模型名。

`finish_reason` 为 `length` 时拿到的是不完整的回答。程序应当检查这个字段，不能把截断的内容当作完整结果继续往下用。

**把供应商收在一个函数后面**

新建 `llm.py`，整个应用只通过这一个函数调用模型：

```python
# llm.py
import os
from litellm import completion

MODEL = os.environ.get("LLM_MODEL", "your-model-name")

def chat(messages, **kwargs):
    return completion(model=MODEL, messages=messages, **kwargs)
```

这样做有三个好处：

- 更换模型或供应商只改这一个文件。
- 超时、重试和日志（Day09）加在这里，所有调用自动生效。
- 测试时可以把 `chat` 换成返回固定内容的假实现，不花钱也不依赖网络。

后面几天的示例都写成 `from llm import chat`。生产系统里这一层会发展成模型网关，Day67–76 再展开。

**常见接入方式**

同一个 `chat` 背后可以接不同来源的模型。下表按撰写时（2026 年 10 月）的 litellm 文档整理，变量名和前缀以官方文档为准：

| 接入方式 | `LLM_MODEL` 的写法 | 地址和 key |
| --- | --- | --- |
| OpenAI 兼容端点（很多供应商和自建推理服务提供这种接口） | `openai/模型名` | 地址用 `api_base` 参数传入；key 可放在环境变量 `OPENAI_API_KEY` |
| Azure OpenAI | `azure/你的部署名` | 环境变量 `AZURE_API_KEY`、`AZURE_API_BASE`、`AZURE_API_VERSION` |
| 本地模型（通过 Ollama） | `ollama_chat/模型名` | 用 `api_base` 传入本机 Ollama 服务的地址 |
| 企业统一网关 | 网关是 LiteLLM Proxy 时写 `litellm_proxy/模型名`；其他网关若提供 OpenAI 兼容接口，按第一行接入 | LiteLLM Proxy 用环境变量 `LITELLM_PROXY_API_KEY`、`LITELLM_PROXY_API_BASE`；其他网关按管理员给的地址和凭据 |

需要传 `api_base` 时，也只在 `llm.py` 里处理，业务代码不用知道模型从哪里来：

```python
API_BASE = os.environ.get("LLM_API_BASE")   # 本课程自己约定的变量名，不设就不传

def chat(messages, **kwargs):
    if API_BASE:
        kwargs.setdefault("api_base", API_BASE)
    return completion(model=MODEL, messages=messages, **kwargs)
```

### 动手练习

**20 分钟必做**

1. 设置 `LLM_MODEL` 和供应商的 key，运行第一段代码，确认能打印出回答和两个 token 数。
2. 写一个多轮对话的小循环：用 `input()` 读用户输入，追加到 `messages`，调用 `chat`，把回答作为 assistant 消息追加回去。先告诉它你的名字，下一轮问它“我叫什么”。然后改成每轮只发送最新一条 user 消息，再试一次，观察差别。

**课后选做**

3. 把 `max_tokens` 设为 20，让它“详细介绍 Python 的列表”，打印 `finish_reason`。
