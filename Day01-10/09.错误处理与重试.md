## Day09 - 错误处理与重试

> 大模型应用基础 ｜ 建议用时 1 小时

> **一句话**：模型调用一定会失败，系统要能重试、能降级，并且绝不把没做完的事说成做完了。
>
> **放在全局看**：可靠性从这里开始。Day40 的恢复和 Day72 的队列与租约，是同一个问题在更大范围内的版本。

### 学习目标

- 能把模型应用里的错误分类，判断哪些该重试、哪些不该。
- 写出带指数退避、抖动和上限的重试，并接入 `llm.py`。
- 知道有副作用的操作为什么需要幂等，以及失败时怎样如实告知。

### 核心概念

**打个比方**：像打电话没接通：等一会儿再拨，拨几次还不通就换个办法，并如实告诉对方“没联系上”。

**先分类，再决定怎么处理**

| 错误 | 例子 | 处理 |
| --- | --- | --- |
| 瞬时错误 | 限流、超时、连接中断、服务端临时故障 | 等一会儿重试，次数有上限 |
| 请求本身有问题 | 认证失败、参数不合法、输入超过上下文窗口 | 不重试，修请求 |
| 输出不合格 | JSON 不合法、缺字段 | 带着错误信息让模型重做（Day04） |
| 工具执行失败 | 订单不存在、表达式不合法 | 作为工具结果返回给模型（Day06） |
| 输出被截断或被拒绝 | `finish_reason` 为 `length` 或 `content_filter` | 不当作正常结果，如实告知 |

今天处理第一类，以及重试用尽之后怎么办。

**每次调用都要有超时**

没有超时的调用可能无限期挂起。调用时传 `timeout`（秒）：分类这样的短任务设得短，长文本生成设得长。Agent 任务除了单次调用的超时，还应当有整个任务的总时限。

**指数退避、抖动、上限**

```python
import random
import time

def with_retry(fn, retryable, max_attempts=4, base_delay=1.0, max_delay=20.0, on_retry=None):
    for attempt in range(1, max_attempts + 1):
        try:
            return fn()
        except retryable as e:
            if attempt == max_attempts:
                raise                                   # 用尽后原样抛出，不吞掉
            cap = min(max_delay, base_delay * 2 ** (attempt - 1))
            delay = random.uniform(0, cap)
            if on_retry:
                on_retry(attempt, e, delay)
            time.sleep(delay)
```

| 设计 | 原因 |
| --- | --- |
| 等待上限逐次翻倍 | 给服务恢复的时间，不在对方过载时继续加压 |
| 在 0 到上限之间随机取值（抖动） | 避免大量客户端在同一时刻一起重试 |
| `max_delay` | 等待时间不会无限增长 |
| `max_attempts` | 总次数有界，最终要么返回要么抛出异常 |
| 只捕获 `retryable` | 认证失败、参数错误直接抛出 |

**接入 llm.py**

```python
# llm.py
import json
import os
import sys
import time

import litellm
from litellm import completion

from retry import with_retry

MODEL = os.environ.get("LLM_MODEL", "your-model-name")
RETRYABLE = (litellm.RateLimitError, litellm.APIConnectionError)

def log(**fields) -> None:
    print(json.dumps({"ts": round(time.time(), 3), **fields}, ensure_ascii=False), file=sys.stderr)

def chat(messages, **kwargs):
    kwargs.setdefault("timeout", 60)
    start = time.monotonic()
    try:
        resp = with_retry(
            lambda: completion(model=MODEL, messages=messages, **kwargs),
            RETRYABLE,
            on_retry=lambda n, e, d: log(event="retry", attempt=n, error=type(e).__name__, wait=round(d, 2)),
        )
    except Exception as e:
        log(event="llm_error", error=type(e).__name__, seconds=round(time.monotonic() - start, 2))
        raise
    if not kwargs.get("stream"):
        log(event="llm_call", model=resp.model, seconds=round(time.monotonic() - start, 2),
            prompt_tokens=resp.usage.prompt_tokens, completion_tokens=resp.usage.completion_tokens,
            finish_reason=resp.choices[0].finish_reason)
    return resp
```

说明：

- litellm 把各家供应商的错误映射成与 OpenAI 一致的异常类型，可以从 `litellm` 直接导入。`RETRYABLE` 里先放了限流和连接错误两类。超时和服务端故障在你所用的版本里对应哪个异常类，用练习 1 的办法确认后再补进去。
- 重试只包住了发起请求这一步。流式响应读到一半中断时，用户已经看到部分内容，要在界面上提示，由用户决定是否重新生成。
- litellm 自带 `num_retries` 参数。这里手写是为了看清机制，并记录每一次尝试。两者只用一个，两层重试叠加时实际尝试次数是两层次数的乘积。

**有副作用的操作要幂等**

超时只说明没有等到响应，不说明操作没有发生。只读操作重试没有风险；创建订单、发通知、退款这类操作，盲目重试可能执行两次。在 agent 里，除了你的重试逻辑，模型看到工具报错后也很可能再调用一次。

应对办法是让操作幂等，即执行多次和执行一次效果相同：

- 给每个逻辑操作生成一个幂等键（例如由任务 ID、操作名和参数算出），接收方遇到重复的键直接返回上次的结果。
- 对方不支持幂等键时，重试前先查询状态，确认上一次是否已经生效。
- 做不到幂等的操作不自动重试，交给人确认。

```python
_processed: dict[str, str] = {}

def send_notice(user_id: str, text: str, idempotency_key: str) -> str:
    if idempotency_key in _processed:          # 重复请求：返回上次的结果，不再发送
        return _processed[idempotency_key]
    result = f"已向 {user_id} 发送通知"         # 真正的发送动作放在这里
    _processed[idempotency_key] = result
    return result
```

**降级**

重试用尽后的退路，按对用户的影响从小到大：

| 手段 | 用户看到什么 |
| --- | --- |
| 切换到备用模型（litellm 的 `fallbacks` 参数） | 正常回答，日志记录实际应答的模型 |
| 关闭部分能力，例如不调用工具直接回答 | 回答，并说明“未能查询实时数据” |
| 转入队列稍后处理，或转人工 | 明确的状态和预期 |
| 直接报错 | 清楚的错误信息和可以采取的行动 |

降级要让用户看得见。否则用户会把降级后的结果当作正常结果来信任。

**不要假装完成**

下面几种写法都会让失败看起来像成功：

- `finish_reason` 是 `length`，被截断的回答被当作完整答案展示或解析。
- 达到步数上限，把最后一步的中间内容当作最终答案返回。
- 工具结果或历史被截断，没有留下标记（Day07）。
- 重试用尽后返回一个编造的默认值，或者 `except Exception: pass`。

没完成就说没完成，并说明做到了哪一步。明确的失败可以被重试、上报或由人工接手，伪装成成功的失败只会在下游更晚、更难地被发现。

**每次调用都记日志**

上面的 `log` 每次调用输出一行 JSON，记录实际应答的模型、耗时、输入和输出 token、`finish_reason`、重试次数和错误类型。有了这些，才能回答“这个任务花了多少钱”“慢在哪一步”“哪一类错误最多”。示例里还缺一个把同一任务的多次调用串起来的任务 ID，练习里补上。完整的追踪体系在 Day67–76。

### 动手练习

1. 调用 `completion` 时把 `timeout` 设成一个极小的值（如 0.01），捕获异常并打印 `type(e).__mro__`，看超时对应哪个异常类、它继承自谁。据此决定 `RETRYABLE` 里要补什么。
2. 把 `with_retry` 存为 `retry.py`。写一个前两次抛出 `ConnectionError`、第三次返回 `"ok"` 的假函数，用 `with_retry(fake, ConnectionError, on_retry=print)` 验证重试了两次并返回 `"ok"`。再让它一直失败，确认第四次失败后异常被抛出。
3. 用今天的版本替换 `llm.py`，运行 Day06 的 agent，查看标准错误里的日志行。给 `log` 增加一个任务 ID 字段，让一次任务的所有调用带同一个 ID。
4. 在 Day06 的 `run_agent` 里检查 `finish_reason`：为 `length` 时不返回被截断的内容，改为抛出异常或返回明确的未完成状态。
