## Day07 - 上下文窗口与成本

> 大模型应用基础 ｜ 建议用时 1 小时

> **一句话**：上下文是按 token 计费的有限空间，放进去的每一段内容都要值得。
>
> **放在全局看**：成本、延迟和回答质量都受上下文长度影响。它解释了 Day06 的循环为什么每多一步都更贵，Day10 用今天的办法给助手加预算；Day43 的上下文工程和 Day64 的成本与预算治理是这一课的进阶。

### 学习目标

- 说清 token、上下文窗口、输入成本和输出成本之间的关系。
- 能从响应里统计一次任务的 token 用量，并估算费用。
- 理解提示缓存的原理，知道提示词各部分应该怎么排列。

### 核心概念

**打个比方**：上下文窗口像一张办公桌：桌面有限，摆得越满，越难找到当前要用的那份材料。

**Token**

模型读写的单位是 token。文本先被切成 token 再送进模型，计费、上下文上限、输出上限都按 token 计算。同一段文字在不同模型下的 token 数不同，中文和英文的切分比例也不同，字符数只能当粗略参考。准确的数字有两个来源：

- 调用之后：响应里的 `resp.usage`。
- 调用之前：`litellm.token_counter(model=MODEL, messages=messages)` 给出估算值。

**上下文窗口**

上下文窗口是模型单次调用能处理的 token 上限，输入和输出合计。占用窗口的内容包括：

- system 提示词
- 工具定义（每次请求都会发送）
- 全部历史消息，包括每一条工具结果
- 本次的输出

超过上限，请求会失败。

**长上下文的两个代价**

第一是钱和时间。输入越长，每次调用越贵，响应也越慢。

第二是质量。上下文里的内容越多，模型对每一条信息的注意力越分散，重要的信息更容易被忽略。窗口没满不代表可以随意往里放。

Agent 循环会放大这两个代价，因为每一步都要把此前的全部历史重新发送一遍。单步的输入量随步数线性增长，整个任务累计的输入量增长得比步数快得多。昨天练习 4 打印出的 `prompt_tokens` 就是这个趋势。

**输入和输出分开计价**

| 类别 | 特点 |
| --- | --- |
| 输入 token | 单价较低，但 agent 循环每一步都重发历史，累计数量大 |
| 输出 token | 单价通常明显高于输入；逐个生成，输出长度也是延迟的主要来源 |
| 缓存命中的输入 token | 按折扣价计费，见下文 |

单价以供应商的价目表为准，会变化，应当放在配置里。

**从响应里统计用量**

```python
from dataclasses import dataclass

@dataclass
class UsageMeter:
    prompt: int = 0
    completion: int = 0
    calls: int = 0

    def add(self, resp) -> None:
        self.prompt += resp.usage.prompt_tokens
        self.completion += resp.usage.completion_tokens
        self.calls += 1

    def cost(self, price_in: float, price_out: float) -> float:
        """price_in、price_out 是每百万 token 的单价，从价目表查得。"""
        return self.prompt / 1e6 * price_in + self.completion / 1e6 * price_out
```

在 agent 循环里每次调用 `chat` 之后执行 `meter.add(resp)`，任务结束时就得到总用量。litellm 也提供 `completion_cost(completion_response=resp)`，按内置的价格表算出金额，前提是价格表里有你用的模型。

**提示缓存**

多数请求的开头是重复的：同一份 system 提示词，同一组工具定义。提示缓存让供应商保存这段前缀的处理结果，后续请求只要前缀完全一致，这部分输入就按折扣价计费，响应也更快。

缓存按前缀匹配，前缀里任何一处变化都会让变化点之后的内容失效。所以稳定的内容放前面，变化的内容放后面。

| 位置 | 放什么 |
| --- | --- |
| 最前 | 工具定义、system 提示词、固定的参考资料 |
| 中间 | 对话历史 |
| 最后 | 本轮的用户输入、当前时间这类每次都变的内容 |

常见的错误是在 system 提示词开头写入当前时间或请求 ID，每个请求的前缀都不同，缓存完全失效。另外三点：

- 有的供应商自动缓存，有的需要在请求里显式标记缓存位置；前缀太短时不会被缓存。
- 命中数量可以从用量里读：`resp.usage.prompt_tokens_details.cached_tokens`。部分供应商不返回这个字段，读取时要处理字段不存在的情况。
- Agent 循环每一步只在末尾追加，适合缓存。改写或删除靠前的历史会让缓存失效，压缩历史时要考虑这个代价（Day43）。

**给每次请求定预算**

预算是写在配置里、由代码强制执行的一组数字：

| 预算项 | 控制手段 |
| --- | --- |
| 单次输出长度 | `max_tokens` |
| 单个工具结果的长度 | 进入上下文前截断，并标明已截断 |
| 单个任务的步数 | `max_steps`（Day06） |
| 单个任务的总 token | 累计用量超过阈值时停止，并报告未完成 |

```python
MAX_TOOL_RESULT_CHARS = 4000   # 示例值，按模型窗口和预算调整

def clip(text: str, limit: int = MAX_TOOL_RESULT_CHARS) -> str:
    if len(text) <= limit:
        return text
    return text[:limit] + f"\n[结果已截断：原文 {len(text)} 字符，仅显示前 {limit} 字符]"
```

截断标记是必须的。没有它，模型会把半截内容当成全部，并据此下结论。
