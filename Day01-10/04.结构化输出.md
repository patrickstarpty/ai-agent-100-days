## Day04 - 结构化输出

> 大模型应用基础 ｜ 建议用时 1 小时

> **一句话**：给程序用的输出必须有固定结构，并且每次都要校验。
>
> **放在全局看**：结构化输出把“模型的一段话”变成“程序可以依赖的数据”。它接在 Day03 的提示词之后，Day05 的工具参数、Day16 的带引用回答、Day38 的路由和 Day27 的评审员输出都靠它。

### 学习目标

- 能让模型按指定的 JSON 结构输出，并用 Pydantic 校验。
- 输出不合法时，按“校验、带错误信息重试、限制次数”的流程处理。
- 知道 schema 为什么要小，以及怎样设计字段。

### 核心概念

**打个比方**：像让人填表，而不是写信：表格的栏目是固定的，填错了可以退回重填。

**下游代码需要结构**

模型的输出一旦要交给程序使用，例如写入数据库、决定走哪个分支、填进界面上的字段，程序需要的是确定的字段和类型。从一段自由文本里用正则表达式抠数据很脆弱，模型换一种说法就失效。结构化输出把模型和下游代码之间的约定写成一份 schema。

**三种做法**

| 做法 | 怎么做 | 保证程度 |
| --- | --- | --- |
| 在提示词里要求 | 写明“只输出 JSON，字段如下” | 没有保证，可能夹带解释文字或格式错误 |
| JSON 模式 | `response_format={"type": "json_object"}` | 约束输出为合法 JSON，不保证字段符合预期 |
| JSON schema | `response_format` 传入 schema，或直接传 Pydantic 模型类 | 支持该功能的模型会按 schema 约束输出 |

并非所有模型都原生支持 JSON schema。所以无论用哪种做法，拿到输出后都要自己校验。

**用 Pydantic 定义和校验**

```python
from typing import Literal
from pydantic import BaseModel, Field, ValidationError, field_validator
from llm import chat

class Ticket(BaseModel):
    category: Literal["账单", "物流", "其他"]
    urgent: bool
    summary: str = Field(description="一句话概括，不超过 30 字")

    @field_validator("summary")
    @classmethod
    def summary_is_short(cls, v: str) -> str:
        if len(v) > 30:
            raise ValueError("summary 超过 30 字")
        return v

SYSTEM = "从 <ticket> 标签内的工单文本中提取信息，按给定的结构输出 JSON。"
```

一个模型类同时承担三件事：生成发给模型的 schema，校验模型的输出，给下游代码提供带类型的对象。

即使模型支持 schema 约束，校验仍然必要。schema 只能约束形状，字数上限这类业务规则要靠校验器（上面的 `summary_is_short`）；输出被 `max_tokens` 截断时，得到的是半截 JSON。

**输出不合法时怎么办**

流程固定为三步：校验；失败时把错误信息发回给模型，让它修正；重试次数有上限，用尽后明确报错。

```python
def extract(text: str, max_attempts: int = 3) -> Ticket:
    messages = [
        {"role": "system", "content": SYSTEM},
        {"role": "user", "content": f"<ticket>\n{text}\n</ticket>"},
    ]
    for _ in range(max_attempts):
        resp = chat(messages, response_format=Ticket, max_tokens=300)
        raw = resp.choices[0].message.content or ""
        try:
            return Ticket.model_validate_json(raw)
        except ValidationError as e:
            messages += [
                {"role": "assistant", "content": raw or "（空）"},
                {"role": "user", "content": f"上面的输出没有通过校验：\n{e}\n请只输出修正后的 JSON。"},
            ]
    raise ValueError(f"连续 {max_attempts} 次输出不合法")
```

几个要点：

- 错误信息要原样给模型。Pydantic 的报错会指出哪个字段、什么问题，模型据此修正的成功率比单纯重发一遍高。
- 必须有次数上限。同一个错误重复三次，继续重试多半也没用，还在持续花钱。
- 用尽后抛出异常，由调用方决定转人工还是跳过。不要返回一个编造的默认对象，那会让下游把失败当成成功。

**schema 要小**

- 只放下游真正要用的字段。字段越多、嵌套越深，出错的机会越多。
- 取值有限的字段用枚举（`Literal`），不用自由字符串。
- 给字段写 `description`，它会进入 schema，相当于字段级别的提示词。
- 信息可能不存在时，允许字段为空（`str | None`）。强制必填会逼模型编一个值。
- 模型通常按 schema 里的字段顺序生成（多数实现如此，以所用模型或接口的文档为准）。需要先分析再下结论时，把分析字段放在结论字段前面。
- 一个很大的抽取任务，拆成几次小 schema 的调用，通常比一次大 schema 更稳，也更容易定位问题。

### 动手练习

**20 分钟必做**

1. 准备五段工单文本，其中一段信息不全（例如只有一句“在吗”）。运行 `extract`，打印每个结果。
2. 在循环里加一行打印，输出每次尝试的序号和校验错误。把校验器里的 30 改成 8（`description` 保持不变），观察模型收到错误信息后如何修正。

**课后选做**

3. 给 `Ticket` 加一个可为空的字段 `order_id: str | None`，并在 `description` 里写明“文本中没有订单号时为 null”。检查没有订单号的工单是否返回了 `None`。
