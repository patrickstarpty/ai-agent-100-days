## Day08 - 流式输出与交互体验

> 大模型应用基础 ｜ 建议用时 1 小时

> **一句话**：用户在意的是“有没有动静”，流式输出和进度提示让等待变得可以接受。
>
> **放在全局看**：agent 的一个任务可能要跑几十秒到几分钟，交互设计是产品能不能用的前提。Day42 讲编排框架里的同一件事。

### 学习目标

- 说清流式输出改善的是哪个指标，没有改善的是哪个。
- 能消费一个流式响应，并在结束后得到完整文本。
- 让多步任务在运行过程中向用户报告进度，并支持取消。

### 核心概念

**打个比方**：像餐厅的出餐进度：菜还没上，但看到“正在制作”比一直没消息强得多。

**流式改善的是等待的感受**

| 指标 | 含义 | 流式的影响 |
| --- | --- | --- |
| 首字延迟 | 从发出请求到看到第一个字 | 大幅缩短 |
| 总耗时 | 从发出请求到回答结束 | 基本不变 |

一段较长的回答需要一段明显的生成时间。非流式下用户在这段时间里面对的是空白，流式下很快就开始看到文字，可以边生成边读，发现方向不对还能提前打断。面向人的交互界面应当默认使用流式。输出只给程序读的场景，例如 Day04 的结构化抽取，流式没有必要。

**消费一个流**

```python
from llm import chat

def stream_reply(messages: list) -> str:
    parts = []
    for chunk in chat(messages, stream=True):
        if not chunk.choices:              # 防御：个别分片可能不带 choices
            continue
        delta = chunk.choices[0].delta.content
        if delta:                          # delta.content 可能是 None
            parts.append(delta)
            print(delta, end="", flush=True)
    print()
    return "".join(parts)
```

三点说明：

- 每个分片只带一小段新增文本。要自己拼出完整回答，再作为 assistant 消息追加到历史里。
- 流式响应要拿到用量，需要传入 `stream_options={"include_usage": True}`，最后一个分片会带上 `usage`。
- 流式输出的 JSON 在结束之前是不完整的。校验和后续动作都要等流结束后再做，不要对半截内容采取行动。工具调用的参数在流式模式下同样是分片到达的，要拼完整才能解析。

**多步任务要报告进度**

Agent 完成一个任务可能要调用模型和工具好几轮。如果只在最后输出答案，用户在这期间看不到任何变化，无法判断程序是在工作还是卡住了。

做法是让循环在关键节点产出事件，由界面决定怎么显示。把 Day06 的循环改成生成器（`SYSTEM`、`TOOLS`、`run_tool` 沿用 Day06 的定义）：

```python
def run_agent_events(user_input: str, max_steps: int = 8):
    messages = [
        {"role": "system", "content": SYSTEM},
        {"role": "user", "content": user_input},
    ]
    for step in range(1, max_steps + 1):
        yield {"type": "model_start", "step": step}
        resp = chat(messages, tools=TOOLS)
        msg = resp.choices[0].message
        if not msg.tool_calls:
            yield {"type": "final", "text": msg.content or ""}
            return
        messages.append(msg)
        for call in msg.tool_calls:
            name = call.function.name
            yield {"type": "tool_start", "name": name, "args": call.function.arguments}
            result = run_tool(call)
            yield {"type": "tool_end", "name": name, "ok": not result.startswith("错误")}
            messages.append({"role": "tool", "tool_call_id": call.id, "content": result})
    yield {"type": "stopped", "reason": f"{max_steps} 步内没有完成"}
```

循环只负责产出事件，不关心显示。命令行程序把事件打印成一行文字，Web 服务把同样的事件通过 SSE 或 WebSocket 推给浏览器，循环代码不用改。这些事件同时也是日志和追踪的原始数据（Day67–76）。

**工具运行时显示什么**

| 事件 | 建议显示 |
| --- | --- |
| `model_start` | “思考中”一类的状态提示 |
| `tool_start` | 用人能看懂的话说明正在做什么，带上关键参数，例如“正在查询订单 A1001” |
| `tool_end` | 成功时简短确认或直接收起；失败时明确显示失败 |
| `final` | 回答正文 |
| `stopped` | 明确说明任务没有完成，以及原因 |

几条原则：

- 显示真实状态。不要用假的进度条或百分比，agent 的总步数事先并不知道。
- 不直接展示原始的参数 JSON，其中可能有内部标识或敏感信息。
- 耗时长的工具显示已用时间，让用户知道程序还在运行。
- 失败和未完成要显示出来，不能只在成功时才有输出。

**取消**

用户应当能随时停下一个正在运行的任务。取消涉及三个层面：

- 正在流式输出：停止读取并关闭连接，不再继续消费后面的分片。
- 步与步之间：每一步开始前检查是否已请求取消。生成器写法下，调用方停止迭代，循环就不会再往下走。
- 工具正在执行：已经发出的操作无法收回。如果工具有副作用，要告诉用户哪些步骤已经执行。这也是 Day09 讲幂等的原因之一。

```python
def render(event: dict) -> None:
    match event["type"]:
        case "tool_start":
            print(f"  正在调用 {event['name']} {event['args']}")
        case "tool_end" if not event["ok"]:
            print(f"  {event['name']} 失败")
        case "final":
            print(event["text"])
        case "stopped":
            print(f"任务未完成：{event['reason']}")

try:
    for event in run_agent_events("订单 A1001 和 A1002 的金额加起来是多少？"):
        render(event)
except KeyboardInterrupt:
    print("\n已取消。上面列出的工具调用可能已经执行。")
```

被取消的那一轮，已经生成的部分内容是否保留在历史里，需要定一个规则并保持一致。常见做法是保留，并附上“用户中断了回答”的说明，避免模型在下一轮把半截内容当成完整结论。
