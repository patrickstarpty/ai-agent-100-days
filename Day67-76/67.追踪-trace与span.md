## Day67 - 追踪：trace 与 span

> 可观测性与生产化 ｜ 建议用时 1 小时

> **一句话**：一次请求记成一条 trace，其中每个步骤记成一个 span，带上摘要、耗时和状态，跨进程也要连成一条。
>
> **放在全局看**：追踪是可观测性阶段的地基。Day68 讲用什么标准记，Day69 讲记到哪里，Day71 的优化和 Day31 的在线评估都从这里取数据。

### 学习目标

- 说清 trace、span、父子关系、属性、状态这几个概念，并能画出一次问答请求的 span 树。
- 把追踪上下文从接口进程传到后台 worker，让两边的 span 落在同一条 trace 里。
- 列出一份“记什么、不记什么”的清单。

### 核心概念

**打个比方**：像出差报销：一次出差一张总单（trace），每张发票是一行明细（span），写着时间、金额和事由；总单转给财务时单号跟着走，财务那边补的明细也挂在同一张单子下面。

**几个基本概念**

| 概念 | 含义 |
| --- | --- |
| trace | 一次请求从进入系统到结束的完整记录，用一个 trace ID 标识 |
| span | trace 里的一个步骤，有开始和结束时间；每个 span 有自己的 ID 和父 span |
| 属性 | span 上的键值对：模型名、命中条数、工具名、停止原因 |
| 状态 | 成功、失败；失败时附错误类型 |
| 事件 | span 生命周期里的一个时间点，例如“开始重试” |

父子关系把 span 组织成一棵树。看一次慢请求时，先找最长的那根枝，再往下钻。

**一次问答请求的 span 树**（数字为示例）

```
POST /ask                                  （接口进程）
└─ run qa-graph                            （worker，同一条 trace）
   ├─ retrieve          命中 12 条，权限过滤后 7 条，耗时、状态
   ├─ graph_expand      扩展 5 个实体，带 3 条关系
   ├─ chat              逻辑模型名、实际模型、输入/输出 token、finish_reason
   ├─ execute_tool get_order    参数摘要、结果大小、状态
   ├─ chat              ……
   └─ verify_citations  4 条引用，1 条不通过
```

每个 span 至少记四样：输入摘要、输出摘要、耗时、状态。摘要的意思是够排查用、但不是原文，例如“查询词的前 100 个字 + 检索到的片段 ID 列表”。编排图的每个节点也可以各占一个 span，并在根 span 上记下图版本（Day74）和停止原因（Day45）。

**跨进程：把追踪上下文随任务带走**

接口进程收到请求后把任务放进队列，由 worker 执行（Day72）。如果什么都不做，两边会各自生成一条互不相关的 trace。做法是：接口进程把当前的追踪上下文序列化进任务消息，worker 取出后以它为父，继续创建 span。

OpenTelemetry 默认用 W3C Trace Context 格式，序列化结果是一个 `traceparent` 字符串，里面有 trace ID 和父 span ID。下面按 OpenTelemetry Python 文档的手动传播示例改写，把载体从 HTTP 头换成任务消息里的一个 dict（初始化部分见 Day68）：

```python
from opentelemetry import trace
from opentelemetry.trace.propagation.tracecontext import TraceContextTextMapPropagator

tracer = trace.get_tracer("qa-platform")

# 接口进程
def submit(question: str, user_id: str) -> None:
    with tracer.start_as_current_span("POST /ask"):
        carrier: dict = {}
        TraceContextTextMapPropagator().inject(carrier)      # 写入 traceparent
        enqueue({"question": question, "user_id": user_id, "trace": carrier})

# worker 进程
def handle(job: dict) -> None:
    ctx = TraceContextTextMapPropagator().extract(carrier=job["trace"])
    with tracer.start_as_current_span("run qa-graph", context=ctx):
        run_graph(job)                                       # 里面的 span 都挂在这条 trace 下
```

常用的任务队列库有现成的 OpenTelemetry 插桩，会自动做这件事，文档也建议优先用插桩库，手写只用于理解机制或没有插桩的场合。

**等待很久的任务**

一个任务停在人工确认（Day41）几个小时后才恢复，把恢复后的步骤硬塞进原来那条 trace，时间轴会很难看。常见做法是恢复时开一条新 trace，用 span link 指向原来的 trace，并在两边都记上同一个 `run_id`。按 `run_id` 能查到一个任务的全部 trace。

**记什么、不记什么**

| 记 | 不记 |
| --- | --- |
| 步骤名、耗时、状态、错误类型 | 密钥、令牌、Authorization 头、连接串 |
| 实际使用的模型和 token 用量（Day70） | 整篇文档；只记片段 ID 和来源定位 |
| 片段 ID、得分、是否经过权限过滤 | 默认不记完整提示词和回答原文 |
| 工具名、参数里白名单内的字段、结果大小 | 工具返回的大块原始数据 |
| `run_id`、线程 ID、用户的内部标识 | 用户的姓名、联系方式等个人信息（Day63） |

完整的提示词和回答对排查很有用，但又大又敏感。OpenTelemetry 的 GenAI 语义约定对此的建议是：插桩默认不采集这些内容，由使用者选择开启；生产环境推荐把内容存到单独的存储，span 上只记引用，这样内容可以有自己的访问控制和保留期（Day69）。
