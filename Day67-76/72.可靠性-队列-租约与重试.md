## Day72 - 可靠性：队列、租约与重试

> 可观测性与生产化 ｜ 建议用时 1 小时

> **一句话**：长任务放进队列交给后台 worker，按“消息会重复、worker 会崩溃、有的任务永远做不成”来设计，用 outbox、幂等、租约、尝试上限和退避把这三种情况都接住。
>
> **放在全局看**：Day09 在一次调用里重试，Day40 让图从检查点接着跑；这一课把同一个问题放到任务这一层：谁来跑、跑到一半崩了谁接手、失败几次后放弃。Day67 的追踪上下文和 Day42 的进度事件都随这里的任务流转。

### 学习目标

- 说清为什么“业务变更”和“要发出的事件”必须在同一个事务里写入，以及 outbox 怎样做到。
- 用带过期时间的租约和尝试计数，设计一张能回收崩溃任务、又不会无限重跑的任务表。
- 写出一个单个任务失败不会让自己退出的 worker 循环，并区分可以退避重试和不该重试的失败。

### 核心概念

**打个比方**：像洗衣店接单：前台收衣服时当场开单，衣服和单据一起入账（outbox）；店员领单时写上“我在洗，几点前交回”，过点没交就换人接手（租约）；所以同一件衣服可能被洗两次，洗法要保证洗两次也不坏（幂等）；一件衣服反复洗不干净，就挂到问题件架子上等店长看，不能一直洗下去（尝试上限）。

**长任务交给后台 worker**

一次 agent 运行可能有十几步工具调用，还可能停下来等人工确认（Day41）。把它挂在 HTTP 请求上，连接一断任务就没了，接口进程也被占满。做法是接口只负责建任务、返回 `run_id`，worker 从队列里领任务执行，进度通过事件推给界面（Day42）。下面的草图用数据库里的一张 `jobs` 表充当队列；换成独立的消息中间件，机制相同。

**outbox：业务变更和对外事件同一个事务**

任务做完后，往往要通知别的系统：在工单里回复、发一条“运行完成”的消息。如果先提交数据库、再发消息，两步之间崩溃，结果存了却没人知道；反过来先发消息，事务回滚后下游收到的是一件没发生的事。outbox 模式的做法是：把要发出的事件当作一行数据，和业务变更写在同一个事务里；另一个转发进程读出未发送的行，发出去后再标记已发送。转发进程在“已发出、未标记”之间崩溃，会再发一次，所以接收方要按事件 ID 去重。

**至少一次投递，处理方必须幂等**

队列、outbox 转发、租约回收，都会让同一个任务或事件被处理不止一次。“恰好一次”靠投递方保证不了，能做到的是“至少一次投递 + 处理方幂等”，效果上等于一次。worker 里的每个写操作都带由代码生成的幂等键（Day49），agent 运行本身从检查点恢复（Day40），重跑时跳过已经完成的步骤。

**租约：让崩溃的 worker 的任务被收回**

worker 领任务时写下自己的名字和租约到期时间。到期还没交回，就当它已经崩溃，任务可以被别的 worker 领走。耗时长的任务定期续租（心跳）；续租失败说明任务已经被收回，应当立刻停手。租约过期不代表原 worker 一定死了，它可能只是卡住，之后又醒过来。所以交结果时要校验“租约还在我手里”，不在就放弃写入。托管队列也有同样的机制，例如 Amazon SQS 的可见性超时：消息被领取后暂时对其他消费者不可见，超时未删除就重新可见。

**尝试次数在领取时计数，并设上限**

尝试次数在领取时加一，不在失败时加一。原因是 worker 崩溃时根本跑不到失败处理那一行，按失败计数，一个每次都把 worker 弄崩的任务会被无限收回、无限重跑。

**进阶：死信**

超过上限的任务进入死信状态，触发告警，等人来看。SQS 的死信队列用 `maxReceiveCount` 表达的也是这个意思：被领取太多次仍未完成，就移出主队列单独处理。

**按失败类型决定是否重试**

| 失败 | 例子 | 处理 |
| --- | --- | --- |
| 瞬时 | 限流、下游超时、连接中断 | 按 Day09 的指数退避加抖动，设置下次可领取时间，放回队列 |
| 确定性 | 参数非法、权限被撤销（Day40）、状态结构版本不兼容（Day74） | 直接标记失败，不重试，告知发起人 |
| 意料之外 | 代码缺陷抛出的异常 | 记录堆栈，标记失败；尝试上限兜底 |

重试只放在一层。模型调用、工具调用、任务各自都重试时，实际尝试次数是各层次数的乘积，下游越忙压力越大。

**一个 worker 循环的草图**

```python
import json, random, time, uuid

LEASE_SECONDS = 300      # 示例值：按任务的实际耗时定，长任务靠心跳续租
MAX_ATTEMPTS = 3         # 示例值

class Transient(Exception): ...      # 限流、超时、下游暂时不可用
class LeaseLost(Exception): ...      # 租约已被收回

def claim(db, worker_id: str):
    now = time.time()
    with db:
        row = db.execute("""SELECT id FROM jobs
            WHERE (status = 'queued' AND run_after <= ?)
               OR (status = 'running' AND lease_until < ?)       -- 租约过期，原 worker 多半已崩溃
            ORDER BY run_after LIMIT 1""", (now, now)).fetchone()
        if row is None:
            return None
        got = db.execute("""UPDATE jobs SET status = 'running', lease_owner = ?,
                lease_until = ?, attempts = attempts + 1               -- 领取时计数
            WHERE id = ? AND (status = 'queued' OR (status = 'running' AND lease_until < ?))""",
            (worker_id, now + LEASE_SECONDS, row[0], now)).rowcount
    if got == 0:
        return None                                                   # 被别的 worker 抢先
    return db.execute("SELECT id, payload, attempts FROM jobs WHERE id = ?", (row[0],)).fetchone()

def finish(db, job_id: str, worker_id: str, result: dict) -> None:
    with db:                                                          # 结果和对外事件同一个事务
        ok = db.execute("""UPDATE jobs SET status = 'done', result = ?
            WHERE id = ? AND lease_owner = ? AND status = 'running'""",
            (json.dumps(result), job_id, worker_id)).rowcount
        if ok == 0:
            raise LeaseLost(job_id)                                   # 回滚，不写 outbox
        db.execute("INSERT INTO outbox (id, topic, body) VALUES (?, 'run.completed', ?)",
                   (str(uuid.uuid4()), json.dumps({"job_id": job_id})))

def worker_loop(db, worker_id: str, handle, stop) -> None:
    while not stop.is_set():
        job = claim(db, worker_id)
        if job is None:
            stop.wait(1)
            continue
        job_id, payload, attempts = job
        try:
            if attempts > MAX_ATTEMPTS:
                mark(db, job_id, worker_id, "dead", "超过尝试上限")    # 死信：告警，等人看
                continue
            finish(db, job_id, worker_id, handle(json.loads(payload)))
        except LeaseLost:
            continue                                                  # 结果交给新的持有者
        except Transient as e:
            delay = random.uniform(0, min(600, 10 * 2 ** (attempts - 1)))   # 基数和封顶为示例值
            requeue(db, job_id, worker_id, run_after=time.time() + delay, error=type(e).__name__)
        except Exception as e:                                        # 一个任务出错，循环照常
            mark(db, job_id, worker_id, "failed", type(e).__name__)
```

`mark` 和 `requeue` 同样只在 `lease_owner` 还是自己时才更新，草图省略。`handle` 里面就是从检查点恢复并运行图，每个副作用都带幂等键。停机时先停止领取新任务，手上的任务要么做完，要么把租约提前释放。等待人工确认的任务应当把状态改为等待并释放租约，不占着 worker（Day40）。

### 参考说明

- Chris Richardson [Pattern: Transactional outbox](https://microservices.io/patterns/data/transactional-outbox.html)：把待发消息和业务变更写在同一个事务里，由独立进程转发；转发方崩溃会导致重复发送，所以消费方要幂等。
- [Timeouts, retries, and backoff with jitter](https://builder.aws.com/content/3EumjoZascWd1oZiEgL8ORlv3qE/timeouts-retries-and-backoff-with-jitter)：多层各自重试会让负载成倍放大；有副作用的接口要做成可安全重试的幂等接口。
- Amazon SQS [Visibility timeout](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-visibility-timeout.html)：消息被领取后暂时不可见、超时未删除重新可见、可用心跳延长，以及至少一次投递下仍可能重复。
- Amazon SQS [Dead-letter queues](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-dead-letter-queues.html)：用 `maxReceiveCount` 把多次领取仍未完成的消息移到死信队列单独分析。
