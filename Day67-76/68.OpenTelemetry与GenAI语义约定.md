## Day68 - OpenTelemetry 与 GenAI 语义约定

> 可观测性与生产化 ｜ 建议用时 1 小时

> **一句话**：用开放标准埋点、按约定的名字记属性，追踪数据就能送到任何支持这个标准的后端，换后端不用改代码。
>
> **放在全局看**：Day67 定了记什么，今天定怎么记；Day69 选后端时，靠的就是今天这层标准让选择可以反悔。

### 学习目标

- 说清 OpenTelemetry 里埋点、导出、协议三层的分工，以及为什么这让后端可替换。
- 认识 GenAI 语义约定里最常用的一组属性，知道哪些属性默认不该采集。
- 用最少的代码把自己的模型调用记成一个符合约定的 span，并通过 OTLP 导出。

### 核心概念

**打个比方**：像统一的快递面单格式：发件人按同一种格式填单，哪家快递公司来取件都认得；换快递公司不用重新填一遍。

**开放标准为什么让后端可替换**

| 层 | 做什么 | 换后端时要不要改 |
| --- | --- | --- |
| API 与 SDK | 在代码里创建 span、记属性 | 不改 |
| 导出器 | 把 span 批量发出去 | 改配置：地址和认证 |
| OTLP 协议 | span 在网络上的格式，有 HTTP 和 gRPC 两种传输 | 不改 |
| Collector（可选） | 独立进程，接收、处理后再转发给一个或多个后端 | 改它的配置，应用不动 |

很多后端都能直接接收 OTLP。以本课程的例子栈为例，Langfuse 提供 OTLP 接收端点，并声明尽量兼容 GenAI 语义约定（核对时它支持 HTTP 上的 JSON 和 protobuf，还不支持 gRPC）；Azure 这边也有文档讲怎样用 OpenTelemetry 和 GenAI 语义约定追踪 LangGraph 应用。同一批 span 想同时送到两个后端，例如一边给开发团队排查、一边进运维统一的监控平台，可以让应用只发给 Collector，由 Collector 分发。OpenTelemetry 文档也把“生产环境使用 Collector”列为最佳实践。

**GenAI 语义约定**

语义约定规定了属性的名字和取值。大家都用 `gen_ai.usage.input_tokens` 记输入 token，后端就能直接画出成本图，不用为每个应用写映射。两点先说清：

- 这套约定目前的状态是 Development，不是 Stable，属性名还可能调整。
- 它已经从 OpenTelemetry 主语义约定仓库迁到单独的 [semantic-conventions-genai](https://github.com/open-telemetry/semantic-conventions-genai) 仓库，opentelemetry.io 上原来的页面现在指向那里。

常用的几个（以核对时的文档为准）：

| 属性 | 含义 | 要求 |
| --- | --- | --- |
| `gen_ai.operation.name` | 操作类型，例如 `chat`、`embeddings`、`retrieval`、`execute_tool`、`invoke_agent` | 必填 |
| `gen_ai.provider.name` | 供应商标识 | 必填 |
| `gen_ai.request.model` | 请求的模型名 | 有就填 |
| `gen_ai.response.model` | 实际应答的模型名（Day70 强调要记的那个） | 推荐 |
| `gen_ai.usage.input_tokens`、`gen_ai.usage.output_tokens` | 输入、输出 token | 推荐 |
| `gen_ai.usage.cache_read.input_tokens` | 命中提示缓存的输入 token（Day71 会用到） | 适用时推荐 |
| `gen_ai.response.finish_reasons` | 停止原因列表 | 推荐 |
| `error.type` | 失败时的错误类别 | 出错时必填 |
| `gen_ai.tool.name` | 工具名，用在 `execute_tool` span 上 | 必填 |
| `gen_ai.prompt.name`、`gen_ai.prompt.version` | 使用的提示词模板及其版本（Day74） | 用了命名模板时填 |

span 名字也有约定：模型调用是 `{gen_ai.operation.name} {gen_ai.request.model}`，例如 `chat <模型名>`；工具执行是 `execute_tool {gen_ai.tool.name}`。

另有一组属性标为 Opt-In：`gen_ai.input.messages`、`gen_ai.output.messages`、`gen_ai.system_instructions`、`gen_ai.tool.call.arguments`、`gen_ai.tool.call.result`。它们装的是提示词、回答和工具参数原文，约定要求插桩默认不采集，这和 Day67 的“不记什么”一致。

**最少的代码**

初始化一次，把 span 通过 OTLP/HTTP 发出去。地址从环境变量读，认证信息按后端文档配置，不写进代码：

```python
import os
from opentelemetry import trace
from opentelemetry.sdk.resources import SERVICE_NAME, Resource
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor
from opentelemetry.exporter.otlp.proto.http.trace_exporter import OTLPSpanExporter

provider = TracerProvider(resource=Resource.create(attributes={SERVICE_NAME: "qa-platform"}))
provider.add_span_processor(BatchSpanProcessor(OTLPSpanExporter(endpoint=os.environ["OTLP_TRACES_ENDPOINT"])))
trace.set_tracer_provider(provider)
tracer = trace.get_tracer("qa-platform")
```

埋点放在全系统唯一的模型入口里（Day09 的 `llm.py`，Day70 的网关），业务代码一行都不用动：

```python
from opentelemetry.trace import Status, StatusCode

def traced_chat(messages, **kwargs):
    with tracer.start_as_current_span(f"chat {MODEL}") as span:
        span.set_attribute("gen_ai.operation.name", "chat")
        span.set_attribute("gen_ai.provider.name", os.environ["LLM_PROVIDER_NAME"])
        span.set_attribute("gen_ai.request.model", MODEL)
        try:
            resp = chat(messages, **kwargs)
        except Exception as e:
            span.set_attribute("error.type", type(e).__name__)
            span.set_status(Status(StatusCode.ERROR))
            raise
        span.set_attribute("gen_ai.response.model", resp.model)
        span.set_attribute("gen_ai.usage.input_tokens", resp.usage.prompt_tokens)
        span.set_attribute("gen_ai.usage.output_tokens", resp.usage.completion_tokens)
        span.set_attribute("gen_ai.response.finish_reasons", [resp.choices[0].finish_reason])
        return resp
```

用了 LangGraph 和现成插桩库的部分，节点和模型调用的 span 会自动产生，手写只补插桩覆盖不到的地方：你自己的工具、检索、引用校验。两套埋点同时记同一次调用，会在后端看到重复的 span，接入前先确认谁负责哪一段。

1. 按 Exporters 页面的说明在本地启动一个 Collector，导出器先用它自带的 debug 输出，跑一次 `traced_chat`，在 Collector 的输出里找到你记的每个 `gen_ai.*` 属性。
2. 给 Day06 的 `run_tool` 加一个 `execute_tool {工具名}` span，记 `gen_ai.operation.name` 和 `gen_ai.tool.name`，失败时记 `error.type`。想一想参数里哪些字段可以作为普通属性记录，哪些不行。
