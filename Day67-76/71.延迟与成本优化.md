## Day71 - 延迟与成本优化

> 可观测性与生产化 ｜ 建议用时 1 小时

> **一句话**：先从追踪里找出最慢、最贵的那一步再动手，每做一项优化都用评估集确认质量没有变差。
>
> **放在全局看**：这一课把 Day07 的成本、Day08 的流式、Day38 的并行和 Day43 的上下文规则收到一起，用 Day67 的追踪定位问题，用 Day30 的回归评估把关。

### 学习目标

- 能从追踪数据里找出一类请求的延迟和成本大头。
- 说出缓存、模型分层、减少步数、并行、流式这几类手段各自省的是什么、风险在哪。
- 为每一项优化设计“优化前后”的评估对比。

### 核心概念

**打个比方**：像控制家里的开支：先翻一个月的账单找出大头，再决定是换便宜的套餐还是少打车；省下来之后，还要确认日子没有因此过得更差。

**先度量**

不看数据的优化常常省错地方。按请求类型（例如“知识问答”“生成测试用例”）把追踪聚合起来，回答三个问题：

| 问题 | 从追踪里看什么 |
| --- | --- |
| 慢在哪 | 每类 span 的耗时分布，看中位数也看尾部；关键路径上最长的那一段 |
| 贵在哪 | 每次模型调用的输入、输出 token 和所用模型，累加到任务 |
| 浪费在哪 | 步数分布、重复的工具调用、被截断后重来的调用、提示缓存命中的 token |

常见的发现是：大部分 token 花在少数几步上，例如每一步都带着完整的检索结果，或者 agent 循环里反复调用同一个工具。

**手段一览**

| 手段 | 省什么 | 做法 | 风险 |
| --- | --- | --- | --- |
| 提示缓存 | 输入成本和首字延迟 | 稳定内容放前面（Day07）；用 `gen_ai.usage.cache_read.input_tokens` 这类字段确认确实命中了 | 前缀里混进时间、请求 ID，缓存悄悄失效 |
| 结果缓存 | 整次调用 | 相同输入直接返回上次结果 | 答案过期；不同权限的用户拿到同一份答案 |
| 模型分层 | 单价 | 分类、改写查询、摘要这类简单步骤用便宜的模型；按难度路由 | 难题被分给小模型，质量下降 |
| 减少步数 | 调用次数和累计上下文 | 确定性步骤移出 agent 循环（Day35）；工具一次返回够用的信息（Day47） | 改动编排后行为变化，需要重新评估 |
| 并行 | 延迟 | 互不依赖的检索、只读工具调用同时执行（Day38） | 写操作并行可能互相冲突；对下游的并发压力 |
| 精简上下文 | 输入成本 | 截断、摘要、清理旧的工具结果（Day43） | 删掉了后面要用的信息 |
| 流式 | 感知延迟 | 先出字、先报进度（Day08、Day42） | 总耗时不变；要防止把半截结果当成完成 |

**结果缓存的键**

结果缓存最容易出的问题是权限。一位用户能看到的资料，另一位可能无权看到（Day21），所以缓存键里要有权限范围，还要有会让答案失效的版本：

```python
import hashlib
import json

def answer_cache_key(question: str, acl_scope: str, index_version: str,
                     prompt_version: str, model_name: str) -> str:
    raw = json.dumps({
        "q": " ".join(question.split()).lower(),   # 只做保守的归一化
        "acl": acl_scope,                          # 用户可见范围的摘要，不是用户名
        "index": index_version,                    # 语料重建后自动失效
        "prompt": prompt_version,                  # 提示词升级后自动失效（Day74）
        "model": model_name,
    }, ensure_ascii=False, sort_keys=True)
    return hashlib.sha256(raw.encode()).hexdigest()
```

只缓存只读的问答；涉及实时数据（订单状态）或写操作的请求不进缓存。

**按难度路由**

模型分层的关键在“谁来判断难度”。可以先用规则：问题很短、命中常见问题库、检索结果置信度高，走便宜的模型；其余走默认模型。也可以先用小模型作答，再用引用校验这类确定性检查判断是否合格，不合格再交给大模型重做。无论哪种，路由规则写在代码里，模型名用 Day70 的逻辑名，追踪里记下每次实际用了哪个模型。

**流式改善的是感受**

流式不减少总耗时，但能显著缩短用户看到第一个字的时间。GenAI 语义约定里有一个记录首个分片到达时间的属性 `gen_ai.response.time_to_first_chunk`，可以把“首字延迟”也纳入度量。对多步任务，先推送进度事件（Day42），比让用户面对空白等待好得多。

**每项优化都过评估**

优化本身就是一次改动。每做一项，用同一批用例比较前后三列数字：通过率、平均成本、延迟（看中位数和尾部）。通过率下降的优化，省下的钱往往会以用户流失和人工返工的形式还回去。一次只改一项（Day32），否则分不清是哪一项带来的变化。
