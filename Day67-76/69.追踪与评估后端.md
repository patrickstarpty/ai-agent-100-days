## Day69 - 追踪与评估后端

> 可观测性与生产化 ｜ 建议用时 1 小时

> **一句话**：追踪数据要有一个明确的落脚处：权威数据存在哪、留多久、谁能看、评估从哪里取数，都在接入之前定下来。
>
> **放在全局看**：Day67 定了记什么，Day68 定了按什么标准记，今天定记到哪里。追踪每天都在用：Day31 的在线评估从这里抽样打分，Day71 的优化从这里找最慢、最贵的步骤，Day33 的评估平台和它共用数据集与分数；今天的选择会写进 Day76 技术栈映射表的“追踪后端”和“评估平台”两行。

### 学习目标

- 说清追踪后端选型要回答的四个问题：权威存储、保留期、谁能看、与评估平台的关系。
- 用框架回调或 OTLP 导出中的一种，把主线项目的追踪接进一个后端；没有账号时，用 Collector 的 debug 输出代替。
- 在技术栈映射表里写下“追踪后端”“评估平台”两行的决定和理由。

### 核心概念

**打个比方**：像超市的收银流水：每一笔都留记录，店长每天看哪类商品卖得慢，审计按月抽查；流水存在哪台服务器、留多少年、谁能调出来看，开业前就要定好。

trace 和 span 的结构、跨进程传递追踪上下文、用 OpenTelemetry 和 GenAI 语义约定埋点，见 Day67、Day68。这一课只讨论数据送到哪里、怎样管。

**选后端要回答的四个问题**

| 问题 | 要定的事 | 常见做法 |
| --- | --- | --- |
| 权威存储 | 业务功能（“从回答跳到调用链”、Day62 的审计）依赖的数据放在业务库还是追踪平台 | 业务必需的少量字段写业务库：`run_id`、trace ID、版本清单（Day74）、停止原因（Day45）；完整的 span 进追踪后端。追踪后端暂时不可用，业务照常运行，只是看不到细节 |
| 保留期 | 普通 span 和内容类数据（提示词、回答原文）各留多久 | 与 Day63 定下的保留期一致；内容类数据单独存放、单独设更短的保留期（Day67）；后端自带的保留设置只是执行手段，期限由你的策略决定 |
| 谁能看 | 追踪里有用户的问题和检索到的片段 | Day21 的权限在追踪平台里同样成立。追踪平台不认识源系统里文档级的权限，所以默认不记原文；按环境和项目隔离，生产数据只给排查需要的人 |
| 与评估平台的关系 | 线上 trace 能否直接变成评估用例，在线分数挂在哪里 | 同一平台时，trace、数据集、实验和分数在一处，坏例子一键加进评估集（Day31、Day33）；分开时，用 trace ID 关联，写一个导出脚本把选中的 trace 转成 Day25 格式的用例 |

以 Langfuse 为例（撰写时，2026 年 10 月，以官方文档为准）：数据保留按项目设置，每晚删除超过期限的 trace、observation、score 和媒体文件，自托管时这项属于企业版功能；访问控制按组织和项目两级分配角色，可以让某人只能进入指定项目。其他后端的保留和权限能力各不相同，选型时把上表四行逐一对照。

**接入追踪后端的两条路（以 Langfuse 为例）**

多数后端同样提供框架回调和 OTLP 两种接入，下面用 Langfuse 说明区别：

| 方式 | 做法 | 特点 |
| --- | --- | --- |
| 框架回调 | 把 `langfuse.langchain` 里的 `CallbackHandler` 放进 LangGraph 调用的 `config={"callbacks": [...]}` | 接入快，图中每个节点和模型调用自动得到 span |
| OTLP 导出 | 应用自己的 OpenTelemetry span（Day68）直接导出到后端的 OTLP 端点 | 与框架无关，你手写的检索、引用校验等 span 一起进入；换后端只改导出配置 |

已有 OpenTelemetry 埋点的项目，优先考虑第二种，避免两套埋点同时记同一次调用、在后端出现重复的 span。

**接入说明**

1. **托管或自托管，二选一。** 托管版按数据所在区域选地址，不用自己运维；自托管时，本地试用可用 Docker Compose，生产环境用 Kubernetes（Helm）或云厂商的部署模板。数据能否离开自己的环境、谁负责运维，决定选哪种（Day73）。
2. **环境变量。** 撰写时 Langfuse 的 Python SDK 读三个变量：`LANGFUSE_PUBLIC_KEY`、`LANGFUSE_SECRET_KEY`、`LANGFUSE_BASE_URL`。托管版的 `LANGFUSE_BASE_URL` 按区域填写，例如欧洲区是 `https://cloud.langfuse.com`；自托管填你自己的地址。框架回调的文档另列了可选的 `LANGFUSE_TRACING_ENVIRONMENT`，用来区分开发和生产。密钥放进密钥管理，不写进代码，也不提交进仓库。
3. **走 OTLP 时。** Langfuse 的 OTLP 端点在 `/api/public/otel` 下，Day68 代码里的 `OTLP_TRACES_ENDPOINT` 填它的 traces 专用路径 `/api/public/otel/v1/traces`；认证是用公钥和私钥做 Basic Auth，放在导出请求的头里，具体格式按它的 OpenTelemetry 文档配置。撰写时只支持 HTTP 传输。
4. **零账号时的替代做法。** 先用 Day68 练习里的本地 Collector，导出器接 debug 输出，在终端里确认 span 树和属性都对；或者接任何一个支持 OTLP 的后端（包括可以本地运行的开源追踪系统）。应用代码不用改，以后接正式后端时只改导出地址和认证。

1. 选一个后端（或本地 Collector），用两条路中的一条接入，跑一次“带引用的知识问答”，在后端里找到 Day67 画的那棵 span 树，核对每个 span 的属性。
2. 从后端里挑一条失败的 trace，按 Day25 的格式把它改写成一条评估用例。
