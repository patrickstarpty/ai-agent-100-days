## Day74 - 版本化

> 可观测性与生产化 ｜ 建议用时 1 小时

> **一句话**：提示词、编排图和状态结构都有显式的版本号，每次运行钉在开始时的那组版本上，旧任务只能由兼容的版本或经过测试的迁移来恢复。
>
> **放在全局看**：Day37 给状态结构加了版本号，Day40 让任务能从检查点恢复，Day55 把 agent 定义存成不可变修订；这一课把它们连起来，回答“代码已经升级，停在半路的旧任务怎么办”。Day75 的发布和回滚以这里的版本为单位，Day30、Day32 的评估结果和 Day62 的审计记录都挂在版本上。

### 学习目标

- 列出一个 agent 系统里需要各自版本化的对象，以及每个对象改动后影响什么。
- 让一次运行在开始时解析并记录版本清单，之后每一步都按清单执行。
- 为旧检查点设计恢复规则：哪些改动兼容，哪些需要迁移，没有迁移时怎样处理。

### 核心概念

**打个比方**：像学校换教材：新学期的新生用新版，正在上课的那一届用旧版教到期末；真要中途换，得先有一张新旧章节对照表，并在一个班试过。

**要版本化的对象**

| 对象 | 版本标识 | 改了会影响什么 |
| --- | --- | --- |
| 提示词 | 模板名 + 版本号 | 模型行为；结果缓存要失效（Day71） |
| 编排图 | 节点、边、路由规则所在代码的版本 | 下一步走到哪个节点，旧检查点能否找到原来的位置 |
| 状态结构 | 状态的字段、类型和含义的版本号（Day37） | 旧检查点能否被新代码正确读出 |
| agent 定义 | 不可变修订（Day55），引用具体的 Skill 修订（Day54） | 可用的工具、Skill、模型 |
| 模型 | 网关上的逻辑名，加上实际应答的模型（Day70） | 质量、成本、延迟 |
| 检索配置 | 索引版本、切片和排序参数 | 能找到哪些资料 |

这些对象各有各的变化节奏，所以各自有版本号，不合并成一个大版本。agent 定义和 Skill 一旦发布就不在原处修改，改动一律产生新修订；“生产”“预发”这类名字只是指向某个修订的指针，指针可以移动，修订本身不变（Day55）。提示词也照此管理，和代码一样进版本库、经评审，这正是《12-Factor Agents》里“掌握自己的提示词”一条的意思。

**一次运行钉在开始时的版本上**

运行开始时，把上面这些对象解析成具体版本，写成一份版本清单存进状态；之后每一步都按清单取提示词、选模型，不再去取“最新版”。

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class RunManifest:
    agent_revision: str           # agent 定义的修订号
    graph_version: str            # 编排图代码的版本
    state_schema: int             # 状态结构版本
    prompts: dict[str, int]       # 模板名 -> 具体版本号，不写“production”这类标签
    model_alias: str              # 网关逻辑名；实际模型逐次记在 span 上
    index_version: str

def start_run(resolve, agent_name: str) -> RunManifest:
    return resolve(agent_name, at="production")    # 只在开始时解析一次标签
```

不钉住版本的后果是：一次跑了半小时的任务，前半段用旧提示词，后半段用新提示词，出了问题既无法复现，也说不清是哪个版本的问题。以 Langfuse 的提示词管理为例（撰写时的行为，以官方文档为准），不指定标签时会取到带 `production` 标签的那一版，而这个标签随时可能被移到别的版本上。所以开始时按标签解析一次，记下版本号，之后按版本号取。版本清单同时写到追踪的根 span 上，提示词版本可以用 `gen_ai.prompt.version` 这类属性记录（Day68）。

**旧检查点的恢复规则**

任务停在人工确认（Day41）的那几天里，新版本上线了。恢复时有三条路：

| 情况 | 做法 |
| --- | --- |
| 改动兼容 | 新代码直接恢复。只加了带默认值的可选字段、新节点不在旧任务的路径上，算兼容 |
| 改动不兼容，但有迁移 | 恢复前执行显式的迁移函数，把旧状态转成新结构；迁移有测试，执行有记录 |
| 改动不兼容，也没有迁移 | 保留能跑旧版本的 worker，按 `graph_version` 把旧任务路由给它，直到旧任务排空；做不到就停止恢复，停止原因记为“版本不兼容”（Day45 枚举里的 `version_incompatible`），告知发起人 |

删字段、改字段含义或类型、改 reducer 的合并方式、删除或改名节点，都算不兼容。检查点里记着“下一步执行哪个节点”，节点改了名，新图里就找不到这个位置。新代码“试着读一读”旧状态最危险：字段缺失被当作空值，任务会带着错误的数据继续执行，还可能触发副作用。

```python
MIGRATIONS = {2: (3, migrate_2_to_3)}        # 旧版本 -> (新版本, 迁移函数)
RUNNABLE = {3}                                # 当前代码能直接执行的状态结构版本

class IncompatibleCheckpoint(Exception): ...

def load_for_resume(state: dict) -> dict:
    v = state.get("schema_version")           # 没有版本号的检查点同样拒绝
    while v not in RUNNABLE:
        if v not in MIGRATIONS:
            raise IncompatibleCheckpoint(v)   # 不猜，按停止原因收场（Day45）
        v, fn = MIGRATIONS[v]
        state = {**fn(state), "schema_version": v}
    return state
```

迁移函数的测试用真实的旧检查点样本，不用手写的理想数据：从线上抽几份旧版本的检查点，迁移后断言关键字段的值、并能在新图上从原来的位置继续跑通。

**评估结果记在版本上**

每次评估运行都附上被测的版本清单，评估结果和版本一一对应。比较两个方案（Day32），就是比较两份清单之间的那一处差异；CI 里的基线（Day30）也是某一份清单上的结果。线上的追踪带着版本清单，在线评估分数（Day31）就能按版本分组。没有记录版本的评估结果，不能拿来作为发布的依据（Day75）。
