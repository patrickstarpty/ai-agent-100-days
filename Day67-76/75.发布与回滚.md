## Day75 - 发布与回滚

> 可观测性与生产化 ｜ 建议用时 1 小时

> **一句话**：换模型、改提示词、调检索都是一次发布：先过评估门禁，再小范围放量、和当前版本同时对比，并且事先想清楚哪些改动退不回去。
>
> **放在全局看**：Day74 给出了发布的单位，Day30、Day32 提供离线门禁和对比方法，Day31 提供线上信号，Day65 的门禁思想在这里用到发布上。Day92 把同样的做法放进研发流程。

### 学习目标

- 认出系统里所有“不改代码也会改变行为”的发布，并让它们走同一条发布路径。
- 设计一次灰度：怎样分流、和谁对比、看哪些指标、什么情况下中止。
- 区分能回滚、有条件回滚和回滚不了的改动，并为后者事先准备办法。

### 核心概念

**打个比方**：像餐厅推新菜：先在后厨试做、内部试吃，再只向几桌推荐，和点老菜的那几桌比反馈；不行就撤下换回老菜。但已经端上桌吃掉的那几盘收不回来，只能道歉补救。

**什么算一次发布**

下面每一项都会改变 agent 的行为，都按发布处理，哪怕只改了一个词：

- 改提示词、换 Skill 修订、改工具白名单，也就是产生新的 agent 定义修订（Day55）。
- 模型逻辑名指向新的模型或部署（Day70）。
- 改检索参数、换向量模型、重建索引。
- 改编排图或状态结构（Day74）。

提示词放在管理平台上时，改动可以不经过代码部署就立即生效。这很方便，也意味着“把生产标签指向新版本”这一下本身就是发布动作，要和代码发布走同样的门禁和记录。

**第一道关：评估门禁**

由代码判定，结果记在被测的版本清单上（Day74）：

| 检查 | 放行条件 |
| --- | --- |
| 回归集（Day30） | 没有新增的不通过用例；出现的每条翻转都有人看过 |
| 留出集（Day32） | 不明显低于开发集，排除对评估集过拟合 |
| 安全用例（Day58） | 注入、越权类用例全部通过 |
| 成本与延迟（Day64、Day71） | 每任务成本和尾部延迟在预算内 |

门禁只能说明评估集上没发现问题，真实流量里的问题要靠下一步。

**第二道关：灰度与对比**

新版本先接一小部分流量，和同一时段仍跑当前版本的那部分对比。要同时对比，不要拿上线前后的数字比：时段、用户和问题分布本身就在变，前后对比里混着这些变化。

- **分流要稳定。** 按用户或会话分组，同一个人始终落在同一组，体验一致，数据也干净。一次运行钉在它开始时的版本上，中途不会因为放量而换版本。
- **指标要能归到这次改动。** 在线评估分数（Day31）、点赞和点踩、弃答率、引用校验失败率、工具失败率、停止原因分布（Day45）、每任务成本和延迟。每条追踪都带版本清单，才能按组统计。
- **阶段和中止条件事先写好。** 例如内部用户、小比例、扩大、全量，每一阶段写清观察多久、哪项指标比对照组差到什么程度就中止。阈值根据自己历史数据的波动来定。
- **带写操作的 agent 先影子运行。** 案例 B 这类会提交代码、回复工单的 agent，新版本可以先在真实输入上运行，写工具一律空跑，只比较它打算做什么，确认后再接真实流量。

**回滚的范围**

| 改动 | 能否回滚 | 怎么做 |
| --- | --- | --- |
| 提示词、agent 定义、模型指向、检索参数 | 能 | 把指针移回上一个版本；结果缓存键里有版本号，会自动切回（Day71） |
| 编排图代码 | 能，但要处理进行中的运行 | 新版本期间开始的运行钉在新版本上，让它们跑完，或经迁移转到旧版本（Day74） |
| 状态结构 | 有条件 | 新版本写入的检查点，旧代码可能读不了。先发一个能读新旧两种结构的版本，再切换写入，最后删旧逻辑 |
| 重建索引 | 删了旧索引就回不去 | 新旧索引并存，查询端用别名或配置切换，观察期结束再删旧索引 |
| 数据迁移 | 破坏性的回不去 | 迁移前备份，尽量只增不删，保留反向迁移并测试过 |
| 已发生的副作用 | 回不去 | 已发的通知、提交的代码、工单里的评论、用户读过的回答，只能更正、撤回或通知相关人；靠 Day62 的审计记录找出受影响的范围 |

从没执行过的回滚步骤，真正需要时往往会卡在某一步，所以回滚也要演练。

**发布前检查清单**

- [ ] 改动对应新的版本号或修订，版本清单写清这次只改了哪一项。
- [ ] 回归集、留出集、安全用例、成本与延迟的评估结果记在这份版本清单上，并已通过门禁。
- [ ] 进行中的运行和旧检查点怎样处理已经确定：兼容、迁移，或保留旧版本 worker（Day74）。
- [ ] 灰度的分流方式、各阶段的观察时长、中止条件已经写下。
- [ ] 线上追踪带版本清单，看板能按版本分组对比。
- [ ] 回滚步骤写清楚并演练过，负责执行的人知道在哪里操作。
- [ ] 回滚不了的部分已经列出：索引、数据迁移、副作用各有准备。
- [ ] 带写操作的改动已完成影子运行，写工具空跑的结果有人看过。
- [ ] 发布人、批准人、发布时间和关联的评估结果写进发布记录（Day62）。

### 动手练习

1. 为主线项目一次真实的改动（例如把摘要步骤换成更便宜的模型）写发布计划：门禁用哪几份评估集，灰度分几个阶段，每阶段看哪三项指标、中止条件是什么。
2. 列出主线项目最近三类改动，按上面的回滚表逐个标注“能”“有条件”“不能”，为每个“不能”写一条事先的准备。
3. 把发布前检查清单复制到 [设计评审清单](../模板/设计评审清单.md) 旁边，按你们的情况增删，删掉的每一项写明理由。

### 自检

1. 为什么灰度要和同一时段的对照组比，而不比较上线前后的数字？
2. 新提示词灰度了一天后决定回滚，在此期间它已经回复了一些工单评论。回滚之后还要做什么？

### 参考说明

- Google SRE Workbook [Canarying Releases](https://sre.google/workbook/canarying-releases/)：灰度是部分、限时的部署和评估；与同时运行旧版本的对照组比较；指标要能归到这次改动并反映用户感受到的问题；前后对比受时间上的噪声影响，风险较大；发现偏离时暂停并回滚。
- Langfuse [Prompt Version Control](https://langfuse.com/docs/prompt-management/features/prompt-version-control)：把 `production` 标签移回之前的版本即可回滚提示词。
- Langfuse [Prompt Management](https://langfuse.com/docs/prompt-management/overview)：提示词更新可以不经过代码部署立即生效，并能把提示词和追踪关联起来按版本分析。
- 其余的讲解、比方、示例和练习为本课程自己编写。
