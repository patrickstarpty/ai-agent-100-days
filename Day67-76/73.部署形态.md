## Day73 - 部署形态

> 可观测性与生产化 ｜ 建议用时 1 小时

> **一句话**：agent 跑在哪里，取决于你想保留多少控制权、愿意承担多少运维。
>
> **放在全局看**：部署形态决定了前面各课要求的能力由谁来提供：Day40 的检查点、Day41 的人工等待、Day59 的 agent 身份、Day69 的追踪导出、Day72 的队列和租约。这一课的结论写成决策记录（Day95 会细讲写法），并填进 Day76 技术栈映射表的“部署形态”一行。

### 学习目标

- 说清三种部署形态各自由谁负责运行、伸缩、身份和状态。
- 用前面各课的需求逐项检验一个托管运行时能否承载你的 agent。
- 把选择写成决策记录，填进技术栈映射表的“部署形态”一行。

### 核心概念

**打个比方**：像解决住处：住酒店最省心，但规矩是别人的；租房可以自己布置，水电物业有人管；自建房一切自己负责。

**三种部署形态**

| 形态 | 说明 | 谁负责什么 | 取舍 |
| --- | --- | --- | --- |
| 平台配置型 agent | 在平台上配置指令、模型和工具，不写编排代码 | 平台负责运行、伸缩、对话状态；你负责配置 | 最省事；编排逻辑受限，难以按 Day46 的规格做确定性控制 |
| 平台托管的代码 agent | 把自己的 agent 代码打包交给平台运行 | 平台负责端点、伸缩、身份；你负责代码和其中的状态设计 | 保留代码控制权；与平台的运行契约绑定 |
| 自行部署 | 自己的服务和 worker，只把平台当作模型和工具的来源 | 你负责全部：伸缩、身份、队列、检查点、运维 | 完全可控；运维成本最高 |

撰写时（2026 年 10 月，以官方文档为准），Foundry Agent Service 的文档把前两种分别称为 prompt agents 和 hosted agents（另有语音类的 prompt agent），并把 LangGraph 列为 hosted agents 支持的框架之一；hosted agents 以容器运行，平台提供托管端点、自动伸缩、每个 agent 专属的 Entra 身份和会话级的状态持久化。agent 代码已经在别处运行、只调用平台的模型和工具时，文档里对应的是直接调用 Responses API，也就是上表的第三种。其他云平台和编排框架厂商也提供类似的托管运行时，名称和能力各异，下面的检验方法同样适用。

**用前面各课的需求逐项检验**

托管运行时的介绍页通常只列它能做什么。对照自己的需求逐项问，才能看出缺口：

| 需求 | 来自 | 要问运行时的问题 |
| --- | --- | --- |
| 检查点与恢复 | Day40 | 状态存在哪，能否用自己的存储；进程重启后能否从检查点接着跑 |
| 队列、租约与重试 | Day72 | 长任务是否脱离请求运行；崩溃后谁接手；重试在哪一层 |
| 人工等待 | Day41 | 等几小时到几天时，是否占着计算资源；恢复时状态还在不在 |
| 运行身份 | Day52、Day59 | 能否每个 agent 一个身份、最小权限；写操作能否以用户身份执行 |
| 追踪与评估 | Day68、Day69 | 能否把 OpenTelemetry 数据导出到你选定的追踪后端 |
| 版本与发布 | Day74、Day75 | 能否钉住版本、灰度、回滚；旧任务能否继续跑在旧版本上 |
| 触发方式 | Day81 | 是否支持定时和事件触发，还是只能由请求驱动 |

任何一行答不上来，就要么在运行时外面补（例如自己的队列和检查点存储），要么这部分改为自行部署。

**从参考实现出发**

本课程说的参考实现，是你按前面各课搭起来的主线项目第一版；目标技术栈是组织选定的生产平台，本课程以 Azure Foundry + LangGraph + Langfuse 为例，不用它们的团队换成自己的平台。

如果参考实现已经有成熟的任务队列、检查点和 worker，自行部署、只把平台当模型来源，往往是迁移成本最低的起点。之后按上表逐项评估，某项能力托管运行时做得更好，再把它迁过去。“两者并存”也是常见结果，例如只读的知识问答放在托管运行时，带写操作和长时间人工等待的案例 B 流程继续自行部署；这时要写明各自负责什么、什么时候收敛（见技术栈映射表的填写说明）。
