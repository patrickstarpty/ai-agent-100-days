## Day73 - 部署形态

> 可观测性与生产化 ｜ 建议用时 1 小时

> **一句话**：agent 跑在哪里，取决于你想保留多少控制权、愿意承担多少运维。
>
> **放在全局看**：部署形态决定了身份、伸缩和长任务这些能力由谁来提供。

### 学习目标

- 在“托管的 agent 运行时”和“自己部署”之间做出有依据的选择。
- 把结论写成决策记录。

### 核心概念

**打个比方**：像解决住处：住酒店最省心，但规矩是别人的；租房可以自己布置；自建房一切自己负责。

**三种部署形态**

| 形态 | 说明 | 取舍 |
| --- | --- | --- |
| 平台配置型 agent | 在平台上配置指令、模型和工具，无需代码 | 最省事；编排逻辑受限，难以版本化和测试 |
| 平台托管的代码 agent | 把自己的 agent 代码打包交给平台运行，平台提供端点、伸缩、身份和可观测性 | 保留代码控制权；与平台的运行契约绑定 |
| 自行部署 | 自己的服务和 worker，只把平台当作模型来源 | 完全可控；伸缩、身份、运维都要自己做 |

Foundry Agent Service 的文档把前两种分别称为 prompt agents 和 hosted agents，并把 LangGraph 列为 hosted agents 支持的框架之一。

**选择时要问的问题**

- agent 有没有自己的持久状态（检查点、任务队列）？托管运行时能否承载？
- agent 运行时的身份是谁，能不能做到每个 agent 一个身份、最小权限？
- 长任务、人工等待、定时触发这些需求，运行时是否支持？
- 评估和追踪数据能否导出到你选定的平台？

如果参考实现已经有成熟的任务队列、检查点和 worker，自行部署加平台模型往往是迁移成本最低的起点。
