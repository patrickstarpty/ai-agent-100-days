## Day70 - 模型入口

> 可观测性与生产化 ｜ 建议用时 1 小时

> **一句话**：全系统只留一个调用模型的入口，换模型、算成本、做限制都在这里办。
>
> **放在全局看**：模型和供应商会不断更换，网关让这种变化不波及业务代码。

### 学习目标

- 说清应用代码和模型供应商之间应该隔一层什么。
- 把参考实现的模型调用路径映射到目标技术栈（Azure Foundry + LangGraph + Langfuse）。

### 核心概念

**打个比方**：像公司的前台总机：外面的线路怎么换，内部的分机号都不变。

**模型网关**

应用里只应有一条调用模型的路径。这层网关负责：

- 用逻辑名（如“默认对话模型”“向量模型”）屏蔽具体的供应商和部署名。
- 统一记录每次调用的模型、实际命中的上游、token 用量、耗时和错误。
- 集中执行超时、重试、预算和数据范围策略。

有了这一层，换模型或换供应商是配置变更，不用改业务代码。评估时也能确定“这次回答到底是哪个模型给的”。

**参考实现与目标栈的差异**

参考实现常见的做法是“自建网关 + 开源代理（如 LiteLLM）+ 某家供应商”。迁到 Azure Foundry 时要决定：

| 问题 | 选项 |
| --- | --- |
| 代理层是否保留 | 保留代理，把 Foundry 当作它的一个上游；或去掉代理，网关直接调用 Foundry |
| 认证方式 | 项目端点 + Microsoft Entra ID（推荐，走 RBAC）；或服务端点 + API key |
| 运行时身份 | 本地开发用 CLI 凭据，生产用托管身份 |

微软的 `langchain-azure-ai` 包提供了 LangChain/LangGraph 可直接使用的模型类，也支持 `init_chat_model("azure_ai:<模型名>")` 这种简写。文档建议开发时使用最小权限角色。

**记录“实际模型”**

配置里的逻辑名和响应里实际命中的模型可能不同（路由、回退）。持久化的应该是后者，否则历史回答无法复现和归因。
