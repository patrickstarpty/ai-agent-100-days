## Day70 - 模型网关

> 可观测性与生产化 ｜ 建议用时 1 小时

> **一句话**：全系统只留一个调用模型的入口，换模型、算成本、做限制都在这里办。
>
> **放在全局看**：Day02 写下、Day09 加上重试的 `llm.py` 是它的雏形，Day68 把模型调用的埋点放在这里；Day64 的预算和 Day71 的模型分层在这里执行，Day74 的版本清单记录这里的逻辑名，Day75 换模型时移动的也是这里的指向。今天的决定会写进 Day76 技术栈映射表的“模型入口”一行。

### 学习目标

- 说清应用代码和模型供应商之间这一层要承担的四件事。
- 把参考实现（你按前面各课搭起来的主线项目第一版）的模型调用路径映射到目标技术栈（组织选定的生产平台；本课程以 Azure Foundry + LangGraph + Langfuse 为例，不用它们的团队换成自己的平台），写出代理层、认证、运行时身份三处决定。
- 区分配置里的逻辑名和响应里的实际模型，知道持久化的应该是哪一个。

### 核心概念

**打个比方**：像公司的前台总机：外面的线路怎么换，内部的分机号都不变；所有来电都过总机，谁打了多久也就都有记录。

**网关承担的四件事**

应用里只应有一条调用模型的路径。这层网关负责：

| 职责 | 做法 | 连到哪一课 |
| --- | --- | --- |
| 屏蔽供应商 | 业务代码只用逻辑名（如“默认对话模型”“向量模型”），逻辑名到供应商和部署名的映射放在配置里 | Day74 的版本清单记逻辑名 |
| 统一记录 | 每次调用记逻辑名、实际应答的模型、token 用量、耗时和错误 | Day67、Day68 的 span |
| 集中执行策略 | 超时、重试（只在一层做，Day72）、每任务预算、哪类数据可以发给哪个供应商 | Day09、Day63、Day64 |
| 路由 | 按步骤或难度选逻辑名，上游不可用时按规则回退 | Day71 的模型分层 |

有了这一层，换模型或换供应商是配置变更，不用改业务代码；评估时也能确定“这次回答到底是哪个模型给的”。

一个纯 Python 的草图，在 `llm.py` 的 `chat` 外面加一层：

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class Route:
    upstream_model: str      # 供应商侧的模型或部署名，来自配置，不写死在代码里
    timeout_s: float

ROUTES: dict[str, Route] = load_routes()   # 逻辑名 -> Route，从配置文件读

def gateway_chat(alias: str, messages, *, budget, **kwargs):
    route = ROUTES[alias]                  # 未知的逻辑名直接报错，不猜
    budget.check()                         # 预算由代码裁决（Day64）
    resp = chat(messages, model=route.upstream_model, timeout=route.timeout_s, **kwargs)
    record_usage(alias=alias, actual_model=resp.model, usage=resp.usage)
    return resp
```

`budget`、`load_routes`、`record_usage` 留给你按项目实现；关键是业务代码只认识 `alias`。

**参考实现与目标技术栈的差异**

参考实现常见的做法是“自建网关 + 开源代理（如 LiteLLM）+ 一家或几家模型供应商”。其他云模型平台或自托管推理也会遇到同样的问题。以迁到 Azure Foundry 为例，要决定：

| 问题 | 选项 |
| --- | --- |
| 代理层是否保留 | 保留代理，把 Foundry 当作它的一个上游；或去掉代理，网关直接调用 Foundry |
| 认证方式 | 项目端点 + Microsoft Entra ID（走 Entra ID 和 RBAC，审计到身份）；或直接用服务端点 + API key |
| 运行时身份 | 本地开发用 Azure CLI 登录的凭据，部署后用托管身份 |

微软的 `langchain-azure-ai` 包提供了 LangChain/LangGraph 可直接使用的模型类，也支持 `init_chat_model("azure_ai:<模型名>")` 这种简写。文档建议用 `DefaultAzureCredential` 作为本地和部署环境的默认凭据，需要更严格时生产环境换成明确的托管身份凭据；开发时在项目上授予最小权限的角色。以上为撰写时（2026 年 10 月）Microsoft Learn 的说明，以官方文档为准。

保留代理的好处是多供应商、回退和本地开发都不变，代价是多一跳和多一处要运维的组件；去掉代理更简单，但网关要自己处理供应商之间的差异。两种都可以，写进决策记录，说明选哪种、为什么。

**记录“实际模型”**

配置里的逻辑名和响应里实际应答的模型可能不同（路由、回退、供应商侧的版本更新）。持久化的应该是后者，同时记下逻辑名，否则历史回答无法复现和归因。GenAI 语义约定里对应的是 `gen_ai.request.model` 和 `gen_ai.response.model` 两个属性（Day68）。
