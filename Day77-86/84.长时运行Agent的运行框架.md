## Day84 - 长时运行 Agent 的运行框架

> 多 Agent 与主动 Agent ｜ 建议用时 1 小时

> **一句话**：任务太长、模型记不住，就把进度写在模型之外，每一轮先读记录再干活。
>
> **放在全局看**：长时运行把 Day43 的“笔记”和 Day45 的“停止条件”推到了极致。

### 学习目标

- 理解 agent 跨多个上下文窗口持续工作时会遇到什么问题。
- 掌握让每一轮都能接上前一轮的四个做法。

### 核心概念

**打个比方**：像倒班的工厂：每班工人都是新来的，全靠交接班记录和任务看板把活接下去。

**问题：每一轮都是失忆的**

一个要做几小时的任务，一定会超出单个上下文窗口。新的一轮开始时，模型对之前做过什么一无所知。常见的两种失败是：一口气想做完所有事，做到一半上下文耗尽，留下半成品；或者看到已经有些成果，就宣布任务完成。

**四个做法**

Anthropic 在 2025 年 11 月介绍了他们让编码 agent 长时间工作的做法，核心是把“记忆”放到上下文之外：

| 做法 | 内容 |
| --- | --- |
| 初始化轮 | 第一轮不写功能，只搭环境：启动脚本、进度记录文件、第一次代码提交 |
| 功能清单 | 用一个结构化文件列出所有端到端功能，初始全部标为未完成；之后每轮只允许修改状态字段 |
| 每轮只做一件事 | 每轮推进一个功能，结束时把代码留在干净、可运行的状态，并更新进度记录 |
| 像用户一样验证 | 用端到端的方式验证功能（例如浏览器自动化），只跑单元测试会漏掉很多问题 |

新一轮开始时，agent 先读进度记录和提交历史，跑一遍基本验证，再挑下一个未完成的功能。出了问题可以靠提交历史回退。

**这套做法的通用部分**

不只是编码任务。任何长时运行的 agent 都需要：

- 一份在上下文之外的任务清单，状态可被检查。
- 每轮结束时的“交接记录”。
- 判断完成的标准由清单和验证决定，不由模型的自我感觉决定。

这和 Day43 的“结构化笔记”、Day45 的“停止原因”是同一件事的不同侧面。

### 动手练习

为案例 B 的“编码”步骤设计运行框架：一张需求工单怎样拆成功能清单、进度记录写在哪、每轮结束的检查项是什么、什么条件下可以提交评审。

### 自检

1. 为什么功能清单里“只允许改状态字段”这条限制很重要？
2. 进度记录和提交历史各自解决什么问题，能否只留一个？
