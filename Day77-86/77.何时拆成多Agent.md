## Day77 - 何时拆成多 Agent

> 多 Agent 与主动 Agent ｜ 建议用时 1 小时

> **一句话**：一个 agent 能做好的事不要拆；拆是为了隔离上下文、隔离权限，或者并行。
>
> **放在全局看**：多 agent 是手段，判断该不该用它比会搭它更重要。这是 Day35“工作流还是 agent”的判断再往上一级；Day78 把常用的三种模式落到代码，Day79 讲子 agent 委派，Day80 定 agent 之间的契约，Day81 起的主动 agent 也建立在这些判断上。

### 学习目标

- 知道多 agent 带来什么、花费什么。
- 能为一个具体场景判断用单 agent 还是多 agent。

### 核心概念

**打个比方**：像团队分工：一个人能干完的活硬拆给三个人，多出来的只有开会和交接。

**三级复杂度**

微软的架构指南把方案分成三级，并建议使用能可靠满足需求的最低一级：

1. 直接调用模型。
2. 单个 agent 加工具。
3. 多 agent 编排。

多 agent 会增加协调开销、延迟和新的失败方式。只有一个 agent 就能做好的事，拆开之后通常更差。

**值得拆的信号**

- 上下文装不下：任务需要读大量材料，但只要结论。让子 agent 在独立的上下文里读，取回摘要。
- 权限必须隔离：读不可信内容的 agent 和有写权限的 agent 应该分开（Day57）。
- 工具太多：一个 agent 面对几十个工具时选择变差，按领域拆开后每个只看到少数几个。
- 可以并行：互不依赖的子任务同时进行能缩短总时间。

**五种编排模式**

| 模式 | 做法 | 适用 | 避免使用的情况 |
| --- | --- | --- | --- |
| 顺序 | 按固定顺序逐个处理，上一个的输出给下一个 | 步骤明确的流水线 | 单个 agent 就能完成各步 |
| 并发 | 多个 agent 同时处理同一输入，再汇总 | 需要多个独立视角 | 各 agent 之间需要互相依赖结果 |
| 群聊 | 多个 agent 在一个对话里讨论，由管理者控制发言 | 需要辩论或共同评审 | 需要确定性的结果 |
| 交接 | 当前 agent 判断该由谁处理，把控制权交出去 | 分诊、转专科 | 路由规则本来就是确定的 |
| 动态规划 | 管理者 agent 边做边制定和调整计划，分派给专门的 agent | 开放式、步骤无法预知的任务 | 路径可以预先确定 |

**契约优先**

无论哪种模式，agent 之间只通过类型化的输入输出交接，证据和引用原样传递，不让模型转述。交接的内容能被记录、被回放、被评估。
