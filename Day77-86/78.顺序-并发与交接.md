## Day78 - 顺序、并发与交接

> 多 Agent 与主动 Agent ｜ 建议用时 1 小时

> **一句话**：三种最常用的多 agent 模式，差别归结为三个问题：agent 之间传什么、谁决定下一步、其中一个失败时整次运行停在哪里。
>
> **放在全局看**：Day77 用一张表讲了五种模式各自适合什么；这一课把其中最常用的三种落到代码上。在 LangGraph 里它们分别对应固定的边、并行分支和条件路由（Day38），失败时的收场沿用 Day45 的停止原因。

### 学习目标

- 对顺序、并发、交接三种模式，各自说清传什么、谁决定下一步、失败时怎样收场。
- 能写出一个让整次运行停在已知状态的纯 Python 编排草图。

### 核心概念

**打个比方**：顺序像流水线上的工位，上一道工序验过才往下传；并发像几位评委同时看同一份作品，各自打分后汇总；交接像医院分诊转科，同一时间只有一个科室负责病人，转科时带着病历走。

**三个问题一览**

| | 顺序 | 并发 | 交接 |
| --- | --- | --- | --- |
| 传什么 | 上一阶段的类型化产出 | 同一份只读输入快照 | 一张交接单：任务摘要、已确认的事实、转交原因 |
| 谁决定下一步 | 代码，顺序事先写死 | 代码决定分给谁、怎样汇总 | 当前 agent 提出交给谁，代码校验能不能交 |
| 失败时 | 停在失败的那一阶段，已完成阶段的产出保留 | 按事先定好的规则：全部成功、达到最少份数，或带缺失标注的部分结果 | 超过跳数上限或目标不合法时，交给人 |

下面的草图共用一个运行结果类型。所有失败都变成一个停止原因，调用方和界面看到的永远是一个明确的状态。`Stop` 在 Day45 的停止原因枚举之上扩展：`completed`、`escalated` 沿用 Day45 的取值，其余三项是多 agent 编排新增的。

```python
from dataclasses import dataclass, field
from enum import Enum
from typing import Any, Callable

class Stop(Enum):                  # 在 Day45 的枚举之上扩展
    COMPLETED = "completed"
    STAGE_FAILED = "stage_failed"
    PARTIAL = "partial"            # 并发时部分分支缺失，但达到了最少份数
    HANDOFF_LIMIT = "handoff_limit"
    ESCALATED = "escalated"        # 交给人处理

@dataclass
class Run:
    stop: Stop
    outputs: dict[str, Any] = field(default_factory=dict)  # 已经拿到的产出
    failed_at: str | None = None
    detail: str = ""
```

**顺序：每一步之后先验再传**

传给下一阶段的是上一阶段的结构化产出，整段对话不往下传。下一阶段需要的上下文越少越好，能只给新指令就只给新指令。每一步之后用代码校验产出，格式不对、缺字段、引用不存在，就在这一步停下，坏的输入不会流进后面的阶段。

```python
Stage = tuple[str, Callable[[Any], Any], Callable[[Any], list[str]]]  # 名称、执行、校验

def run_sequential(stages: list[Stage], first_input: Any) -> Run:
    outputs, current = {}, first_input
    for name, step, validate in stages:
        try:
            result = step(current)
        except Exception as e:                  # 异常在编排层收口，变成状态
            return Run(Stop.STAGE_FAILED, outputs, name, repr(e))
        problems = validate(result)
        if problems:
            return Run(Stop.STAGE_FAILED, outputs, name, "; ".join(problems))
        outputs[name] = current = result
    return Run(Stop.COMPLETED, outputs)
```

`outputs` 保留了失败之前每一阶段的产出，配合检查点（Day40），修好问题后可以从失败的那一阶段重跑。

**并发：汇总规则和缺席规则要先定**

每个分支拿到同一份只读快照，分支之间不共享可变状态。代码事先定好三件事：分给哪些 agent、每个分支等多久、至少要几份结果才能汇总。汇总方式按任务选：分类用投票，打分用加权，需要连贯叙述时才让模型综合。

```python
from concurrent.futures import ThreadPoolExecutor, wait

def run_concurrent(branches: dict[str, Callable], snapshot: Any,
                   timeout_s: float, quorum: int) -> Run:
    pool = ThreadPoolExecutor(max_workers=len(branches))
    futures = {pool.submit(fn, snapshot): name for name, fn in branches.items()}
    done, not_done = wait(futures, timeout=timeout_s)
    pool.shutdown(wait=False, cancel_futures=True)   # 已在运行的线程不会被强行终止，分支自身也要有超时
    outputs, missing = {}, [futures[f] for f in not_done]
    for f in done:
        if f.exception() is None:
            outputs[futures[f]] = f.result()
        else:
            missing.append(futures[f])
    if len(outputs) < quorum:
        return Run(Stop.STAGE_FAILED, outputs, "fan_in", f"缺少：{missing}")
    if missing:
        return Run(Stop.PARTIAL, outputs, detail=f"缺少：{missing}")
    return Run(Stop.COMPLETED, outputs)
```

返回 `PARTIAL` 时，汇总结果和界面都要写明少了哪几个视角，不能当作完整结论展示。

**交接：agent 提议去向，代码把关**

交接时只有一个 agent 在工作。当前 agent 判断自己处理不了，提出“交给谁、为什么”，代码检查三件事：目标在当前 agent 的允许名单里；这次运行没有转回已经经过的 agent；总跳数没超上限。任一项不满足就停下交给人，避免任务在几个 agent 之间来回踢。交接单只带后面需要的东西：任务摘要、已确认的事实、已经排除的可能、转交原因。如果从初始输入就能判断该由谁处理，用一个确定性的分发器即可，不必用交接。
