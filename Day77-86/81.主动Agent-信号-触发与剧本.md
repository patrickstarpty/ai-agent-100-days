## Day81 - 主动 Agent：信号、触发与剧本

> 多 Agent 与主动 Agent ｜ 建议用时 1 小时

> **一句话**：主动 agent 不等人提问，它监听系统里已经发生的事件，条件成立时运行一个受限的剧本，产出一条提议。
>
> **放在全局看**：前面的 agent 都由用户请求驱动，从这一课起，触发者换成事件。Day82 讲提议怎样被采纳，Day83 讲怎样不打扰人，Day85 讲怎样评估，Day86 把它们串成一个完整的剧本。

### 学习目标

- 能列出主线项目里可以作为信号的事件，并设计事件信封。
- 会用幂等键去重、按对象合并信号。
- 能写出一个剧本的定义：触发条件、可用工具、上限。

### 核心概念

**打个比方**：像图书馆的管理员：不等读者投诉，翻借阅登记时发现同一本书总是“无可借”，就写一张加购建议单交给采购员。他看得到登记簿，能写建议单，但不能自己去下单。

**从“被问才答”到“主动发现”**

被动的 agent 有人在场：有人提问、有人看结果、答错了当场有人纠正。主动 agent 被事件唤醒，运行时没有人在线等，产出也没人立刻检查。所以它的边界要比被动 agent 更紧：只能读、只能提议、每次运行都有上限。《12-Factor Agents》第 11 条讲的“从任何地方触发”，在这里的落点是：触发可以来自任何事件，能做的事却要收得很窄。

**信号来自系统已经产生的事件**

| 事件 | 来自 | 可能的剧本 |
| --- | --- | --- |
| 知识发布或更新 | 知识库的入库流程 | 文档变更影响分析：哪些测试用例引用了旧版本 |
| 回答资料不足 | 问答链路的弃答结果（Day17） | 知识缺口提醒：向知识管理员提议补充资料 |
| 用户反馈或纠正 | 反馈接口（Day31） | 复核被纠正的回答所依据的资料 |
| 测试运行失败 | CI | 失败归因草稿 |

这些事件是系统本来就会产生的，并且已经落在现有的权限边界内。主动 agent 不为了“发现问题”额外去抓取数据，也不监视用户的行为。

**事件信封只带标识符和摘要**

```python
from dataclasses import dataclass
from datetime import datetime

@dataclass(frozen=True)
class Event:
    event_id: str            # 与 source 一起唯一标识一个事件
    source: str              # 例如 "qa"、"kb"、"ci"
    type: str                # 例如 "answer.insufficient"
    subject: str             # 事件关于哪个对象，例如 "topic:退订规则"
    occurred_at: datetime
    summary: str             # 一两句话，不含原文
    refs: tuple[str, ...]    # 相关对象的 ID：trace、文档、测试用例

    @property
    def idempotency_key(self) -> str:
        return f"{self.source}:{self.event_id}"
```

信封里不放文档全文、回答全文或用户原话。信封会经过队列、日志和追踪，被复制到很多地方；全文放进去，能看到这些地方的人就都能看到内容。只放 ID，剧本运行时用只读工具按权限去取，谁能看什么仍由源系统说了算（Day21）。`summary` 也只写去标识化的一两句话，不带人名和联系方式（Day63）。CloudEvents 规范也建议事件保持精简、用链接指向数据，理由之一正是这样能对细节做差异化的访问控制。

**用幂等键去重**

队列按“至少投递一次”工作（Day40、Day72），同一个事件可能到两次。`source` 加 `event_id` 唯一标识一个事件，处理过的键记下来，再来就丢弃。

**同一对象的多个信号合并成一次运行**

一个主题一小时内出现五次资料不足，应当运行一次剧本、看到五个信号，而不是运行五次。做法是按（剧本，对象）开一个窗口：第一个信号打开窗口，之后的信号追加进去，窗口到期时把整批交给剧本。

```python
from datetime import timedelta

class Coalescer:
    def __init__(self, window: timedelta):
        self.window = window
        self.seen: set[tuple[str, str]] = set()   # (剧本, 幂等键)；生产中放持久化存储并设保留期
        self.batches: dict[tuple[str, str], list[Event]] = {}
        self.opened_at: dict[tuple[str, str], datetime] = {}

    def add(self, playbook: str, e: Event, now: datetime) -> None:
        if (playbook, e.idempotency_key) in self.seen:
            return                                  # 重复投递
        self.seen.add((playbook, e.idempotency_key))
        key = (playbook, e.subject)
        self.batches.setdefault(key, []).append(e)
        self.opened_at.setdefault(key, now)

    def due(self, now: datetime) -> list[tuple[tuple[str, str], list[Event]]]:
        ready = []
        for key, t in list(self.opened_at.items()):
            if now - t >= self.window:
                del self.opened_at[key]
                ready.append((key, self.batches.pop(key)))
        return ready
```

`now` 由调用方传入，测试时可以随意拨动时间。窗口长度是配置项，按信号的频率和提议的时效来定。

**剧本的定义**

剧本是一个系统 agent（Day55），它的定义包括：

```python
from typing import Callable

@dataclass(frozen=True)
class Playbook:
    name: str
    version: str
    event_types: frozenset[str]
    should_run: Callable[[list[Event]], bool]   # 确定性的触发条件，由代码判断
    tools: frozenset[str]                       # 只读工具，加上 "propose"
    max_steps: int
    token_budget: int
    enabled: bool = True

def check_tools(pb: Playbook, registry: dict) -> None:
    for t in pb.tools:
        if t != "propose" and not registry[t].read_only:
            raise ValueError(f"剧本 {pb.name} 不能使用写工具 {t}")
```

几点约定：

- 触发条件用代码判断。“窗口内同一主题资料不足达到若干次”是确定性规则，不交给模型。模型只做需要判断的部分：归纳问题、查现有资料、写提议的说明。
- 工具只有两类：只读工具，以及 `propose`。`propose` 只把提议写进提议收件箱，不碰目标系统（Day82）。注册剧本时用 `check_tools` 拒绝任何写工具。
- 步数上限和 token 预算按 Day45 设置，达到上限就停，带停止原因结束，不产出半成品提议。
