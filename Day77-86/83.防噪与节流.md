## Day83 - 防噪与节流

> 多 Agent 与主动 Agent ｜ 建议用时 1 小时

> **一句话**：一条提议能不能、什么时候送到人面前，由几条写在代码里、有单元测试的普通规则决定，不交给模型。
>
> **放在全局看**：Day85 说主动 agent 最常见的失败是不该出声的时候出声，这一课给出防住它的规则。它们分布在剧本运行前、剧本产出后和投递时三个位置，预算部分沿用 Day45 和 Day64。

### 学习目标

- 能列出六条防噪与节流规则，说清每条在流水线的哪个位置执行。
- 会把这些规则写成纯函数，用注入的时间写单元测试。

### 核心概念

**打个比方**：像一位懂分寸的秘书：同一件事不重复提；你说“先放着”，他隔一段时间才再提；一天只拿最要紧的几件来找你；事情已经过去了，就把便条撤掉。

**六条规则**

| 规则 | 做法 | 在哪里执行 |
| --- | --- | --- |
| 每个对象一条未处理提议 | 同一剧本、同一对象已有 `open` 提议时，更新它的依据和时间，不新建；建议的内容本身变了，旧的标 `superseded`，新的接替 | 剧本产出后 |
| 忽略后的静默期 | 被 `dismissed` 后，同一剧本、同一对象在一段时间内不再提议，新信号只累积；静默期长短可随忽略原因不同 | 剧本运行前 |
| 每个接收人每天的上限 | 候选提议按优先级排序，每人每天只投递前若干条，其余留到之后，可能先到期失效 | 投递时 |
| 依据变化或超时后自动过期 | 依据的来源版本变了，或到了 `expires_at`，转为 `expired` | 投递时和采纳时 |
| 开关与静音 | 每个剧本有总开关，由负责人控制；每个用户可以静音某个剧本或某个对象 | 运行前查开关，投递时查静音 |
| 每天的 token 预算 | 每个剧本有每日预算，用完后新的运行排队到下一个周期，不丢弃 | 剧本运行前 |

数量关系只需要定性地把握：上限越低，每条提议越“值钱”，但重要的提议更容易被挤到后面；静默期越长越安静，但真问题会被压得越久。具体数值从 Day85 的采纳率、忽略率和过期率里调出来。

**为什么超预算的运行要排队**

信号本身就是数据。一个主题今天的资料不足信号因为预算用完被丢掉，明天就没人知道这个缺口存在过。排队时仍按（剧本，对象）合并（Day81），积压不会成倍增长；排了太久的批次按过期处理，并记录下来。

**三个位置的顺序**

1. 剧本运行前：开关关了、处于静默期、预算用完，就不运行。这里拦住的运行一个 token 都不花。
2. 剧本产出后：按“每个对象一条”更新或新建提议。
3. 投递时：查过期、查静音、按优先级取每日上限内的部分。

**规则是普通代码，配单元测试**

```python
from dataclasses import dataclass
from datetime import datetime, timedelta

@dataclass(frozen=True)
class NoiseSettings:                     # 以下数值均为示例设置
    cooldown_after_dismiss: timedelta = timedelta(days=14)
    daily_cap_per_recipient: int = 3

@dataclass(frozen=True)
class Candidate:
    id: str
    playbook: str
    subject: str
    recipient: str
    priority: int                        # 越大越优先
    created_at: datetime
    expires_at: datetime

def in_cooldown(last_dismissed_at: datetime | None, now: datetime, s: NoiseSettings) -> bool:
    return last_dismissed_at is not None and now - last_dismissed_at < s.cooldown_after_dismiss

def pick_for_delivery(cands: list[Candidate], recipient: str, delivered_today: int,
                      muted: set[str], now: datetime, s: NoiseSettings) -> list[Candidate]:
    ok = [c for c in cands
          if c.recipient == recipient and c.playbook not in muted
          and c.subject not in muted and c.expires_at > now]
    ok.sort(key=lambda c: (-c.priority, c.created_at))
    return ok[: max(0, s.daily_cap_per_recipient - delivered_today)]
```

时间由参数 `now` 传入，函数里不调用 `datetime.now()`，测试才能精确卡在边界上：

```python
T0 = datetime(2026, 1, 1, 9, 0)
S = NoiseSettings()

def cand(id, priority, **kw):
    base = dict(playbook="gap", subject=f"topic:{id}", recipient="u1", priority=priority,
                created_at=T0, expires_at=T0 + timedelta(days=7))
    return Candidate(id=id, **(base | kw))

def test_cooldown_ends_exactly_at_boundary():
    assert in_cooldown(T0, T0 + S.cooldown_after_dismiss - timedelta(seconds=1), S)
    assert not in_cooldown(T0, T0 + S.cooldown_after_dismiss, S)

def test_cap_keeps_highest_priority_and_skips_expired_and_muted():
    cands = [cand("a", 1), cand("b", 5), cand("c", 9, expires_at=T0),
             cand("d", 7, playbook="muted-one"), cand("e", 3), cand("f", 4)]
    picked = pick_for_delivery(cands, "u1", delivered_today=0,
                               muted={"muted-one"}, now=T0, s=S)
    assert [c.id for c in picked] == ["b", "f", "e"]
```

除了这两个，每条规则至少再有一个测试：同一对象第二次产出时提议数量不变；预算用完后运行进入队列而不是消失；剧本开关关闭时不运行。这些测试和 Day85 的评估场景互补：评估场景检查剧本判断得对不对，单元测试检查规则执行得对不对。
