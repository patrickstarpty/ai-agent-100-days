## Day80 - Agent 之间的契约

> 多 Agent 与主动 Agent ｜ 建议用时 1 小时

> **一句话**：agent 和组件之间只交换类型化的输入和带状态的结果，失败也是一种结果，下一步由调用方决定。
>
> **放在全局看**：Day37 提出“契约式组件”，Day77 要求“契约优先”，这一课把契约写成代码。Day78 的编排、Day79 的委派、Day81~83 的主动剧本，都靠这套契约把检索、聚合、生成提议这些组件拼起来。

### 学习目标

- 能为一个组件写出类型化的输入、输出和状态枚举。
- 说清为什么组件返回状态而不抛异常，以及证据为什么要原样传递。

### 核心概念

**打个比方**：像快递的标准面单和签收状态：寄什么、寄给谁写在固定的栏位里；回执也用固定状态：“已签收”“暂不可派送”“地址已变更”“查无此人”“破损”，寄件人照着状态决定重寄、改地址还是联系收件人，用不着去猜一句含糊的“出问题了”。

**类型化的输入输出**

组件之间传的是有固定字段的对象，不传一段让下游去理解的自由文本。字段固定，交接的内容才能被记录、回放和评估，也才能在改动时用类型检查和测试发现不兼容。

**带状态的结果**

```python
from dataclasses import dataclass
from enum import Enum
from typing import Generic, Protocol, TypeVar

class Status(Enum):
    APPLIED = "applied"      # 正常产出
    NOT_READY = "not_ready"  # 依赖还没准备好，例如索引正在重建
    STALE = "stale"          # 依据的版本已经过期
    EMPTY = "empty"          # 正常执行完，没有结果
    FAILED = "failed"        # 执行出错

@dataclass(frozen=True)
class Evidence:
    source_id: str
    source_version: str
    chunk_id: str
    text: str                # 原文，从取回到展示一字不改

T = TypeVar("T")

@dataclass(frozen=True)
class Result(Generic[T]):
    status: Status
    value: T | None = None
    evidence: tuple[Evidence, ...] = ()
    reason: str = ""         # 简短的原因码，给调用方和追踪看

class Component(Protocol):
    name: str
    version: str
    read_only: bool
    def run(self, inp) -> Result: ...
```

| 状态 | 调用方的典型处理 |
| --- | --- |
| `APPLIED` | 用 `value` 和 `evidence` 继续 |
| `NOT_READY` | 稍后重试，或退化到不依赖它的路径（例如只用切片回答） |
| `STALE` | 重新取依据，或把结果标成“可能过期” |
| `EMPTY` | 按“没有结果”处理，例如弃答（Day17） |
| `FAILED` | 记录原因，按 Day45 的停止原因收场 |

不抛异常的理由：这五种情况里有四种是预期之内的，它们应当出现在类型里，调用方写 `match` 时每一种都得面对。异常适合表示程序错误，混用之后，调用方很容易只捕获一部分，或者一个 `except` 把“没有结果”和“程序崩了”当成同一件事。组件内部仍会遇到意外异常，在组件边界统一收口成 `FAILED`：

```python
import logging, time

log = logging.getLogger("components")

def call(c: Component, inp) -> Result:
    start = time.monotonic()
    try:
        result = c.run(inp)
    except Exception as e:                           # 意外错误在边界收口
        result = Result(Status.FAILED, reason=f"unexpected:{type(e).__name__}")
    log.info("component=%s version=%s status=%s reason=%s ms=%d",
             c.name, c.version, result.status.value, result.reason,
             (time.monotonic() - start) * 1000)
    return result

def answer(query: str) -> str:
    r = call(REGISTRY["retrieve"], query)
    match r.status:
        case Status.APPLIED:
            return generate_with_citations(query, r.evidence)
        case Status.EMPTY:
            return abstain("资料里没有找到相关内容")
        case Status.NOT_READY | Status.STALE:
            return retry_later(query, r.reason)
        case Status.FAILED:
            return report_failure(r.reason)
```

**每个组件在自己的 span 里运行**

上面的日志行就是一个 span 该有的字段：组件名、版本、状态、原因码、耗时。接入追踪后（Day67、Day68），`call` 为每次调用开一个 span，把这些字段记成属性。一条 trace 里哪个组件返回了 `NOT_READY`、哪个慢，一眼就能看到。

**证据对象原样传递**

`Evidence` 从检索组件产出，一路传到回答、提议和界面，字段不变。模型可以读证据的文字，但它在输出里只能用 `chunk_id` 指向证据，不能把证据改写后再往下传。下游拿到的是检索组件给的那个对象，代码可以校验引用是否存在、版本是否仍有效（Day16）。经模型转述一次，原文就可能被改动，来源版本也会丢失，后面的校验就无从做起。

**组件要注册**

编排层按名字找组件，不直接导入实现。注册时把元数据一起登记，编排层据此决定谁能用哪个组件，例如主动剧本只能用 `read_only` 的组件（Day81）。

```python
REGISTRY: dict[str, Component] = {}

def register(c: Component) -> None:
    if c.name in REGISTRY:
        raise ValueError(f"重复注册：{c.name}")
    REGISTRY[c.name] = c
```

这和 Day48 的工具注册表是同一个思路：工具是给模型用的接口，组件是给编排代码用的接口。
