## Day79 - 子 Agent 与委派

> 多 Agent 与主动 Agent ｜ 建议用时 1 小时，回看 Day43

> **一句话**：把一段要读很多、只要结论的探索交给子 agent，它在一个干净的上下文里做完，只交回一份浓缩的结果。
>
> **放在全局看**：Day43 把子 agent 列为管理上下文的四种手段之一，Day77 把“上下文装不下”列为值得拆的信号。这一课讲委派本身：委派消息写什么、结果怎样交回、要付出什么代价、什么时候不该委派。

### 学习目标

- 能写出一条合格的委派消息：目标、背景、约束、期望的输出格式。
- 能说清委派的两项代价，并据此判断一个步骤该不该委派。

### 核心概念

**打个比方**：像请助理去档案室查一件事：交代清楚查什么、哪些柜子不用翻、回来用一页纸汇报。他翻了一下午卷宗，你只读那一页；那一页没写到的细节，你也就不知道了。

**子 agent 是什么**

子 agent 是一次独立的 agent 运行：自己的消息列表、自己的工具白名单、自己的步数和 token 上限。主 agent 通过一个工具调用（例如 `delegate`）启动它。子 agent 看不到主 agent 的对话历史，主 agent 也看不到子 agent 的中间过程，双方只通过委派消息和返回结果联系。子 agent 读了几十个文件、跑了十几次检索，这些都留在它自己的上下文里，主 agent 的上下文只多出一份结果。

**委派消息写什么**

子 agent 从空白开始，委派消息就是它知道的全部。缺了哪一项，它就只能猜。

| 项目 | 写什么 | 缺了会怎样 |
| --- | --- | --- |
| 目标 | 要回答的具体问题，以及答案拿去做什么 | 范围漂移，查了一堆不相关的内容 |
| 背景 | 主 agent 已经确认的事实、已经排除的方向 | 重复主 agent 做过的工作 |
| 约束 | 查哪些来源、不碰哪些范围、可用工具、步数和 token 上限 | 几个子 agent 查到同一处，或越出边界 |
| 输出格式 | 结构、长度上限、每条结论附证据引用、找不到时怎样说明 | 交回一大段散文，主 agent 还得再读一遍 |

```python
from dataclasses import dataclass, field
from enum import Enum

@dataclass(frozen=True)
class Delegation:
    goal: str                      # 要回答的问题和用途
    known_facts: tuple[str, ...]   # 已确认的事实、已排除的方向
    scope: str                     # 查哪些来源，不碰哪些
    tools: frozenset[str]          # 只读工具白名单
    max_steps: int
    token_budget: int
    output_schema: str             # 期望的输出结构说明

class SubStatus(Enum):
    DONE = "done"
    NOT_FOUND = "not_found"        # 查完了，没有找到
    LIMIT_REACHED = "limit_reached"

@dataclass
class SubResult:
    status: SubStatus
    findings: list[str]                                   # 浓缩后的结论
    evidence_refs: list[str]                              # 证据的 ID 或路径，不放原文
    open_questions: list[str] = field(default_factory=list)  # 没查清、与预期不符的地方
```

**交回浓缩的结果**

结果里有三样东西：结论、证据引用、没查清的地方。证据用 ID 或路径引用，原文留在存储里，主 agent 需要时再取（Day43 的即时检索）。产出较大时，子 agent 把它写到外部存储，只交回引用。`open_questions` 是专门留给“意外”的位置：子 agent 发现的反常情况，如果没有固定位置写，往往在浓缩时第一个被删掉。`status` 让主 agent 区分“查到了”“查完了没有”“没查完”，后两种不能当成同一回事处理。

**两项代价**

- 更多的模型调用。每个子 agent 都要重新读委派消息、重新检索、重新推理。Anthropic 在介绍他们的多 agent 研究系统时报告，多 agent 系统消耗的 token 约为普通聊天的 15 倍。这个倍数来自他们的场景，你的任务会不同，但委派通常更贵，也更慢。
- 丢失的细节。主 agent 只看到浓缩结果，子 agent 认为不重要而省掉的东西，主 agent 永远不知道。应对办法是在输出格式里强制要求证据引用和未解决的问题，让主 agent 能顺着引用回到原文。

追踪时把子 agent 的运行挂在主 agent 的 span 下面（Day67），否则出了问题找不到是哪次委派交回了错误的结论。

**什么时候不该委派**

- 任务小，几次工具调用就能完成。启动子 agent 和写委派消息的成本比自己做还高。
- 子任务需要主对话里的大量细节。把背景写全的成本接近自己做，写不全又会出错。
- 几个子任务之间依赖很多，需要频繁对齐中间结果。
- 步骤涉及写操作。子 agent 只做只读的探索，写入回到主流程，经过确认关卡（Day41）。

委派是否值得，最终用评估说话：在同一批用例上比较委派和不委派的通过率、token 和延迟（Day32）。
