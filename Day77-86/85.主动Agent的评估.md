## Day85 - 主动 Agent 的评估

> 多 Agent 与主动 Agent ｜ 建议用时 1 小时，回看 Day23

> **一句话**：主动 agent 既要说得对，也要在不该出声的时候保持安静。
>
> **放在全局看**：它把 Day23 的评估方法用在一种新的产出上：没人提问时给出的提议。依据检查沿用 Day27，线上指标接 Day31 的用户反馈；评估对象是 Day81～Day83 搭起来的剧本，Day86 用这里的场景验收。

### 学习目标

- 为“没人提问、自己发起”的 agent 设计评估。
- 定出衡量它是否有用的线上指标。

### 核心概念

**打个比方**：像一位助理：提醒得准是本分，没事总来敲门，很快就会被请出去。

**主动 agent 的特殊之处**

问答系统的评估问“答得对不对”。主动 agent 由事件触发，产出的是提议（提醒、草稿、建议的操作）。它多了一类更常见的失败：不该出声的时候出声了。用户被打扰几次之后会直接关掉它，所以“保持安静”和“说得对”同样重要。

**评估集要有两类场景**

每个主动能力（下面称“剧本”）至少准备：

| 场景 | 给定 | 期望 |
| --- | --- | --- |
| 应当提议 | 一组事件和当时的知识库状态 | 产生提议，且依据引用正确 |
| 不应当提议 | 看起来相似但不满足条件的事件 | 不产生提议 |

“不应当提议”的场景更难写，也更有价值：阈值边缘的情况、依据已经失效的情况、同一对象已有未处理提议的情况。

**提议必须带依据**

每条提议附上依据的引用和来源版本，没有依据就不产出。原因类的结论要区分事实和推断。评估时用 Day27 的方法检查“提议的结论能否从依据推出”。

**线上指标**

| 指标 | 含义 | 偏低或偏高说明什么 |
| --- | --- | --- |
| 采纳率 | 被用户接受的提议占比 | 偏低：提议质量差或时机不对 |
| 忽略率与原因 | 被明确忽略的占比及用户给的原因 | 某个原因集中出现时，直接指向要改的地方 |
| 过期率 | 没人处理就失效的占比 | 偏高：送达的人不对，或数量太多 |
| 每次运行的成本 | token 和时间 | 结合采纳率看是否值得 |

采纳率长期偏低的剧本应当默认关闭。

**防噪也要测**

防噪规则的单元测试见 Day83，提议状态迁移和采纳的测试见 Day82。评估集负责判断剧本该不该出声、说得对不对，规则执行得对不对交给那些单元测试。

### 动手练习

**20 分钟必做**

1. 为一个主动能力（例如“同一主题多次回答资料不足时，提醒知识管理员补充资料”）各写三个“应当提议”和三个“不应当提议”的场景，写明给定的事件和期望。

**课后选做**

1. 给每个场景补上期望的依据引用（文档 ID 和版本），写成 Day86 可以直接读取的 `eval/scenarios.yaml` 草稿。
