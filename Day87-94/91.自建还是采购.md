## Day91 - 自建还是采购

> 案例：编码 Agent 与研发流程 ｜ 建议用时 1 小时

> **一句话**：先弄清现成产品能做到哪一步，再决定自己只建它做不到的部分。
>
> **放在全局看**：Day88 画出了从工单到合并请求的整条流程，这一课决定其中哪几格用现成产品、哪几格自己建；自建部分要面对 Day57 的安全问题和 Day84 的长时运行问题，结论写成 Day94 设计文档里的一份决策记录。架构师的一项重要工作，就是决定哪些东西不自己建。

### 学习目标

- 了解现成的编码 agent 产品做到了哪一步。
- 能为“从需求工单到合并请求”这一段写一张自建与采购的对比表。

### 核心概念

**打个比方**：像装修：水电这种专业、出错代价高的活交给专业队伍，布局和风格自己定。

**先看现成方案能做什么**

“在工单系统里描述需求，agent 写代码并提交”已经有成型的产品。以 GitHub 在 2026 年 3 月发布的 Copilot coding agent for Jira（公开预览）为例，撰写时（2026 年 10 月）GitHub 的更新日志和文档说明如下，以官方文档为准。GitHub 文档现在把底层的编码 agent 称为 Copilot cloud agent，本课和 Day92、Day93 统一叫它 Copilot coding agent。

- 把 Jira 工单指派给 Copilot，或在评论里 @ 它。
- 它读取工单的描述和评论，在后台实现改动，开一个草稿合并请求。
- 需要更多信息时在 Jira 里提问，并在工单里更新进展。
- 它开的合并请求遵守仓库现有的评审和审批规则。
- 前提条件包括 Jira Cloud 且启用了 Rovo。

GitHub 文档列出的 Copilot coding agent 限制也值得记下来，它们勾勒了现成方案的边界：

| 限制 | 内容 |
| --- | --- |
| 范围 | 每个任务只能改一个仓库 |
| 分支与合并请求 | 每个任务一个分支、一个合并请求 |
| 时长 | 单次会话有固定上限（撰写时为 59 分钟） |
| 托管 | 仅支持托管在 GitHub 上的仓库 |
| 上下文 | 默认只能访问任务所在的仓库 |

预览版的功能和限制变化快，做决定前以官方文档为准。

**对比的维度**

| 维度 | 采购现成方案 | 自建（例如基于 LangGraph） |
| --- | --- | --- |
| 上线速度 | 快 | 慢 |
| 流程定制 | 受产品限制 | 完全可控，例如自定义的需求优化和多级审批 |
| 跨仓库、长任务 | 受上表限制 | 可以做，但要自己解决 Day84 的问题 |
| 接入企业知识 | 通过产品提供的扩展点（如 MCP） | 直接调用自己的知识库 |
| 安全责任 | 沙箱、权限由厂商提供并承担一部分 | Day57 的全部问题都要自己解决 |
| 评估 | 只能评最终结果 | 每一步都能评 |
| 维护成本 | 订阅费用 | 持续的工程投入，模型升级后要重新评估 |

**常见的折中**

编码这一步用现成的编码 agent；自己建的是它前后的部分：需求优化、审批关卡、与构建和发布流水线的衔接、接入企业知识库。这样自建的范围落在流程编排上，沙箱和代码执行这些最难做好的部分交给成熟产品。
