## Day93 - 研发流程里的安全

> 案例：编码 Agent 与研发流程 ｜ 建议用时 1 小时

> **一句话**：找出流程里每一处会读到不可信文本、每一处放着密钥、每一处能往外发东西的地方，再用权限、网络和隔离把它们分开。
>
> **放在全局看**：这是 Day57~60 在案例 B 上的完整应用。Day92 管“谁能放行”，这一课管“agent 在放行之前能碰到什么”；Day94 的设计文档要把这里的结论写进威胁模型。

### 学习目标

- 列出研发流程中所有不可信文本的来源，以及读它们的是哪个 agent。
- 为编码和构建环境设计密钥、推送权限和网络的边界。
- 用三要素检查每个 agent，写出去掉或收窄了哪一项、剩余风险是什么。

### 核心概念

**打个比方**：像施工工地：外来的图纸和材料进场前都要验收，工人只能进自己负责的施工区，配电房的钥匙放在工地以外的值班室。

**不可信文本从哪来**

| 来源 | 谁能写 | 谁会读到 |
| --- | --- | --- |
| 工单的描述和评论 | 任何能提工单或评论的人 | 澄清 agent |
| 仓库里的代码、注释、文档 | 所有有提交权限的人，包括外部贡献者 | 编码 agent |
| 依赖包的代码、说明文档、安装脚本 | 依赖的维护者，以及能篡改依赖的人 | 编码 agent、构建环境 |
| 拉取的网页和外部文档 | 网站的作者 | 编码 agent |
| 构建日志和测试输出 | 任何能影响被测代码或依赖的人 | 编码 agent（读失败信息时） |
| 外部 MCP server 的工具描述和返回值 | server 的提供方 | 接入它的 agent（Day50、Day58） |

依赖包的文档常被忽略。agent 为了弄懂一个库会去读它的说明，这些文字和工单一样进入上下文，里面像指令的话模型同样可能照做（Day58）。

**工单：读它的 agent 和写代码的 agent 分开**

澄清 agent 没有代码写权限；编码 agent 只读已批准的结构化需求，读不到原始评论（Day88、Day89）。两者之间隔着一次人工审批，混在评论里的奇怪要求会以一条明面上的需求出现在审批人面前。进入 agent 之前还可以去掉隐藏内容，例如撰写时（2026 年 10 月）GitHub 文档说明，Copilot coding agent（Day91）不会收到写在 HTML 注释里的文字；这一点和本课下面提到的该产品的其他行为都以官方文档为准。过滤只能降低风险，替代不了权限上的隔离。

**构建环境和密钥**

- 编码工作区和合并前的构建里不放任何生产凭据。集成测试需要的外部服务用测试替身或专门的测试账号。
- 部署凭据只放在发布环境里，只有发布作业在审批通过之后才能拿到（Day92 讲的环境密钥机制）。
- 构建用的令牌默认只读，个别作业需要写权限时单独放开。GitHub 的 Actions 安全指南就建议把 `GITHUB_TOKEN` 的默认权限设为只读仓库内容，再按作业提升。
- 凭据尽量短期有效、按任务签发，任务结束即失效。

**agent 的推送权限**

- 只能推送到自己的分支，例如按任务生成的固定前缀分支；不能推送主分支和其他人的分支。Copilot coding agent 也是这样设计的：除非在已有的合并请求上被唤起，它只能推送到为它新建的那一个分支。
- 修改 CI 配置、部署脚本、保护规则所在的文件属于高风险改动，要求代码所有者审批（Day92）。
- agent 推送的代码不自动触发会接触密钥的工作流，先由人看过再运行。原因很直接：工作流文件本身就是代码，agent 能改它，就可能让工作流替它把密钥送出去。Copilot coding agent 默认也是如此：它推送的代码要等有写权限的人点了批准，工作流才会运行。

**网络白名单**

编码和构建期间，默认拒绝所有出站连接，只放行明确需要的目的地：代码托管服务、内部的依赖包镜像或代理、必要的文档站点。被拒绝的请求记入日志并定期查看。这一步把三要素中的“对外途径”收窄到白名单（Day60）。Copilot coding agent 同样限制了它对互联网的访问。

**依赖：另一条进入的路**

- 新增或升级依赖是一类单独标记的改动，进入评审人的重点清单。
- 依赖只从内部镜像获取，用锁文件固定版本。
- 构建里引用的第三方组件钉到不可变的版本。以 GitHub Actions 为例，撰写时 GitHub 的安全指南指出，把 action 钉到完整的提交 SHA 是目前唯一能把它当作不可变版本使用的方式。

**逐个 agent 数三要素**

| agent | 私有数据 | 不可信内容 | 对外途径 | 去掉了哪一项 | 收窄了哪一项、剩余风险是什么 |
| --- | --- | --- | --- | --- | --- |
| 澄清 agent | 工单、只读的代码搜索 | 工单文本 | 只能在当前工单留言 | 无，三项都在 | 收窄对外途径：留言只发到当前工单，只有原本能看到工单的人看得见；代码搜索的范围不超过这些人的权限。剩余风险：注入的文字诱导它在留言里写误导性的内容，靠需求审批把关 |
| 编码 agent | 代码仓库 | 代码、依赖文档、测试输出 | 网络白名单；只能推自己的分支 | 无，三项都在 | 收窄对外途径：出站只到白名单，推送只到自己的分支。剩余风险：白名单内的目的地仍可能被用来夹带数据（例如请求文档站点时把代码片段放进网址），靠工作区里不放密钥、出站日志复查和合并前评审兜底 |
| 发布流水线 | 部署凭据 | 无模型参与 | 部署目标 | 不可信内容（不让模型进入这一步） | 剩余风险：合并进来的代码本身有问题，靠 Day92 的门禁和评审拦截 |

“去掉”只写真正不存在的那一项。只是收窄的，写进最后一列，并在威胁模型里为剩余风险找到接受人。

2. 写出编码期间的网络白名单，每个目的地写明为什么需要。

2. 为什么依赖包的说明文档也要当作不可信文本？
