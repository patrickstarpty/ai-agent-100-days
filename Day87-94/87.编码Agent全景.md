## Day87 - 编码 Agent 全景

> 案例：编码 Agent 与研发流程 ｜ 建议用时 1 小时

> **一句话**：编码 agent 在一个隔离的代码工作区里反复“读代码、改代码、跑测试、看失败、再改”，测试结果给了它客观的反馈。
>
> **放在全局看**：它是案例 B 中间的那一段，前面是需求澄清（Day89），后面是评审、合并和发布（Day92）。Day06 的循环、Day39 带外部反馈的反思、Day44 的规划和 Day84 的运行框架，在这里第一次合在同一个场景里。

### 学习目标

- 说清编码 agent 在一次任务里依次做哪些事，每件事靠什么工具完成。
- 解释编码为什么特别适合交给 agent，以及这个优势依赖什么前提。
- 划清人和 agent 的分工。

### 核心概念

**打个比方**：像一位在独立工位上接活的实习工程师：查代码、改代码、跑测试都自己来；做哪件事由组长定，代码由同事评审，上不上线由负责人拍板。

**循环里的六个动作**

| 动作 | 做什么 | 用到的工具 | 产出 |
| --- | --- | --- | --- |
| 读 | 找到和需求相关的文件、函数、调用方 | 搜索、读文件、符号地图（Day20） | 相关代码的笔记 |
| 计划 | 列出要改哪些地方、按什么顺序、怎样验证 | 结构化输出（Day44） | 一份可以校验的计划 |
| 改 | 按计划修改代码，补充或调整测试 | 写文件（通常以补丁形式） | 工作区里的改动 |
| 跑 | 运行相关测试、类型检查、静态检查 | 测试运行器、命令执行 | 通过或失败的结果 |
| 读失败 | 从报错和失败的断言里定位原因 | 读测试输出、再读代码 | 下一步修复的方向 |
| 修 | 针对失败原因修改，回到“跑” | 写文件 | 新一版改动 |

“跑 → 读失败 → 修”就是 Day39 讲的带外部反馈的反思：报错是事实，模型据此修改，方向明确。这一圈必须有步数和时间上限（Day45），达到上限时如实报告“未通过”。

```python
def fix_until_green(workspace, plan, agent_step, run_tests, max_rounds: int):
    if max_rounds < 1:                           # 至少跑一轮，否则下面的 result 没有值
        raise ValueError("max_rounds 至少为 1")
    for round_no in range(max_rounds):           # 上限由代码决定，数值按自己的追踪数据定
        agent_step(workspace, plan)              # 模型读代码、改代码
        result = run_tests(workspace)            # 确定性的反馈
        if result.passed:
            return {"stop_reason": "completed", "rounds": round_no + 1}
        plan = plan.with_feedback(result.failures)  # 把具体的失败信息喂回去
    # 停止原因沿用 Day45 的标准枚举
    return {"stop_reason": "max_steps", "last_failures": result.failures}
```

**它依赖的环境**

- **隔离的工作区。** 每个任务一份干净的仓库副本，跑在容器或沙箱里（Day60）。agent 运行的测试和命令都是代码执行，不能碰开发者的机器或共享环境。
- **能跑通的测试和构建。** 工作区里要能一条命令装好依赖、跑完测试。环境本身不稳定，agent 会把时间花在和环境较劲上。
- **好用的工具。** 搜索结果要短而准，报错要能看懂（Day47）。测试输出动辄几千行时，工具应先截取失败部分再交给模型。
- **受限的版本控制权限。** agent 只能在自己的分支上提交，详见 Day93。

**为什么编码适合 agent**

Anthropic 在《Building effective agents》的附录里给了几条理由：代码可以用自动化测试验证；agent 能把测试结果当作反馈来迭代；问题空间结构清楚；产出质量可以客观衡量。再加一条：所有改动都在版本控制里，出了错可以整体丢弃重来。

这些优势有前提。测试覆盖不到的地方，“测试通过”就说明不了什么；需求本身含糊，agent 会准确地实现一个错误的理解。所以同一篇文章也强调，自动化测试之外，人工评审仍然必不可少。Day89 解决需求的问题，Day90 解决“什么算完成”的问题。

**人负责什么**

| 事情 | 负责人 | 原因 |
| --- | --- | --- |
| 做什么、先做哪个 | 提出人和产品负责人 | 这是业务判断，agent 没有依据 |
| 需求是否说清楚 | 需求审批人 | 后面所有步骤都以它为准 |
| 代码评审 | 作者以外的工程师 | 检查测试覆盖不到的设计和可维护性 |
| 合并与发布 | 门禁规则加审批人 | 不可逆、影响他人的动作（Day41、Day65） |

agent 的产出一律从草稿开始：一个分支、一个草稿合并请求、一份构建结果。成为权威内容要经过人和规则。
