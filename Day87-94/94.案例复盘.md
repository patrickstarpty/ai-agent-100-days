## Day94 - 案例复盘

> 案例：编码 Agent 与研发流程 ｜ 建议用时 1 小时，无新材料

> **一句话**：把“工单到发布”的整条流程写成一份设计文档，再拿评审清单从头到尾过一遍。
>
> **放在全局看**：这是本阶段的文档产出，也是评审清单第一次被完整用在一个系统上。Day99 会换一份别人的设计，用同样的清单练习评审。

### 学习目标

把 Day87~93 的决定收成一份可评审的研发流程设计文档，并用 [设计评审清单](../模板/设计评审清单.md) 的七节逐一检查它。

### 产出一：研发流程设计文档

至少包含：

- **流程图与步骤表。** 每一步标为确定性、agent 或人，写明输入和交出的产物。来自 Day88。
- **状态枚举。** 每个状态的含义、由谁推进、终止状态及停止原因。来自 Day88、Day45。
- **需求格式。** 结构化需求的字段，提交审批前的确定性检查，提问和等待的上限。来自 Day89。
- **编码 agent 的工具与运行框架。** 工具清单及读写范围、隔离工作区、进度记录、四个上限的数值。来自 Day87、Day84、Day45。
- **“完成”的定义与历史任务集。** 三层验收各在哪一步检查；任务集的来源、数量、运行次数和比较方法；失败归因的分类。来自 Day90。
- **门禁与审批。** 合并和发布的规则，每条标“代码判”或“人判”；身份与职责分离表；审批人看到的内容；紧急通道。来自 Day92。
- **威胁模型。** 每个 agent 的三要素表，不可信文本来源，密钥位置，推送权限，网络白名单，依赖策略。来自 Day93，用 [威胁模型模板](../模板/威胁模型模板.md) 填写。
- **自建与采购。** 哪些部分用现成产品、哪些自建，写成一份 [决策记录](../模板/决策记录模板.md)。来自 Day91。

### 产出二：用评审清单过一遍

打开 [设计评审清单](../模板/设计评审清单.md)，对七节里的每个问题写一句结论和对应的证据位置（文档章节、测试名、追踪链接）。回答不出或只能回答“有”的问题，记为待办。编码类系统要特别回答这几个问题：

- 验收标准是测试通过、构建通过，还是人工评审通过，各在哪一步判定？
- 有没有一组固定的历史任务可以重复运行，上一次运行是什么时候？
- 读工单的 agent 能不能推送代码，能推送代码的 agent 能不能读原始工单？
- 构建环境里有哪些凭据，合并前的构建能拿到生产凭据吗？
- 写代码的身份、批准合并的身份、批准发布的身份是否两两不同？

### 阶段验收

**必做**

- [ ] 设计文档交给一位没参与的同事，对方能据此说出一条需求从接收到发布会经过哪些状态、在哪三处等人。
- [ ] 每个 agent 都有一份威胁模型；三要素表里每个 agent 至少去掉一项，或把剩余风险写明并有接受人。
- [ ] 评审清单七节都有结论，待办项各有负责人。

**进阶**

下面两项需要一个能跑起来的环境。没有自建的编码 agent 时，可以用 Day91 的现成产品，或在一个带测试的开源小仓库上完成。

- [ ] 合并门禁里有一条测试，证明 agent 的身份无法合并自己的合并请求。用现成产品时，改为在仓库设置里确认这条规则生效，并写下设置的位置和确认方法。
- [ ] 历史任务集至少跑过一次基线，结果按任务列出。
