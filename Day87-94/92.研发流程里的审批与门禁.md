## Day92 - 研发流程里的审批与门禁

> 案例：编码 Agent 与研发流程 ｜ 建议用时 1 小时

> **一句话**：合并和发布由确定性门禁加人工审批放行，写代码的身份不能同时批准或发布自己的改动。
>
> **放在全局看**：这是 Day65（确定性门禁）和 Day41（人工确认）在案例 B 上的落地。Day90 定义了“完成”，这一课决定“完成”之后谁能放行；Day93 讲同一条流程的安全面。

### 学习目标

- 为合并和发布分别写出门禁规则和审批要求。
- 按职责分离原则分配流程里的各个身份。
- 设计一条不拆门禁的紧急变更通道。

### 核心概念

**打个比方**：像医院的处方流程：医生开处方，药师审方，药房发药。开方的人不能自己审、自己发，再急的病人也要走完这三步，只是每一步有人加急处理。

**门禁加审批，两样都要**

| 放行点 | 确定性门禁（代码判） | 人工审批（人判） |
| --- | --- | --- |
| 合并 | 必需的检查全部通过：构建、测试、静态检查、Day90 的削弱测试检查；分支与主分支同步；改动范围没有越出计划 | 至少一位作者以外的评审人批准；改到测试目录、CI 配置等受保护路径时，需要对应的代码所有者批准 |
| 发布 | 发布的制品来自主分支上已合并的提交，并且与测试过的是同一个制品；发布窗口和依赖检查通过 | 发布审批人确认变更清单和回滚方案 |

门禁拦住能机械判断的错误，审批拦住需要理解才能发现的错误。门禁本身是代码，其中一条测试必须证明“agent 的身份无法合并自己的合并请求”（Day65）。

**用公开产品对照一下**

GitHub 的文档里能找到这些机制的现成形态。下面是撰写时（2026 年 10 月）GitHub 文档的说明，以官方文档为准：

- 受保护分支可以要求合并前有指定数量的批准、要求最近一次推送由推送者以外的人批准、要求必需的状态检查通过。默认情况下这些限制不约束仓库管理员，需要显式打开才对管理员生效。
- 部署环境可以设置必需的审批人，并勾选“防止自审”，让触发部署的人不能批准自己的部署；环境里的密钥只有在审批等规则通过后才对作业可用；还可以禁止管理员绕过这些规则。
- 它的 Copilot coding agent（Day91）也遵循同样的思路：请 agent 开合并请求的人不能批准这个合并请求；agent 不能把草稿标为可评审，也不能批准或合并；agent 提交的代码默认要等有写权限的人点击批准后才触发工作流。

**职责分离**

| 身份 | 能做 | 不能做 |
| --- | --- | --- |
| 编码 agent | 推送到自己的分支、开草稿合并请求 | 批准、合并、发布、修改保护规则 |
| 委派人（让 agent 做这件事的人） | 查看进度、补充说明 | 批准这个合并请求 |
| 评审人 | 批准或要求修改 | 批准自己推送过的改动 |
| 发布审批人 | 批准发布 | 批准自己触发的发布 |

agent 替委派人干活，委派人因此算作者一方。agent 的提交要能追溯到委派人，审计记录（Day62）才对得上人。

**审批人必须看到什么**

合并审批时：

- 已批准需求的链接和版本号，每条验收标准对应哪些测试。
- 完整的改动，以及超出计划范围的文件。
- 构建结果和削弱测试检查的标记。
- agent 运行记录的摘要和 trace 链接：跑了多少轮、在哪里失败过、改过哪些测试。

发布审批时：要发布的变更清单、制品版本、影响范围、回滚步骤，以及发布后看哪些指标判断是否正常。只看到“同意/拒绝”两个按钮的审批，很快会变成走过场（Day41）。

**紧急变更不拆门禁**

线上出问题时，最常见的冲动是“先绕过检查发上去”。事先定好紧急通道，比临时绕过安全得多：

1. **首选回滚。** 回到上一个已发布的制品，不需要新代码，也不需要编码 agent（Day75）。
2. **缩短等待，不减少环节。** 紧急通道由值班评审人和值班发布审批人处理，必需检查照常运行；可以跳过的只有事先列明的非必需检查。
3. **显式标记。** 紧急变更必须由人发起并写明理由，agent 不能自己把任务标为紧急。
4. **事后补齐。** 规定期限内补完整评审，紧急变更全部进入审计记录，定期复查有没有被滥用。
5. **绕过开关能关就关。** 确实要保留的管理员绕过，每次使用都留下记录并通知相关人。
