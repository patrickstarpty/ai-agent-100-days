## Day90 - 编码 Agent 的验收

> 案例：编码 Agent 与研发流程 ｜ 建议用时 1 小时

> **一句话**：先定义什么叫“完成”，再用一组可以反复运行的历史任务比较不同的模型和提示词，失败时找准是哪一环出了错。
>
> **放在全局看**：这是 Day23~34 的评估方法在编码场景里的应用。“完成”的定义同时是 Day92 合并门禁的输入，判断权在规则和人手里，不在 agent 手里（Day84）。

### 学习目标

- 按自动化程度列出“完成”的三层含义，以及每层能拦住什么。
- 设计一组可重复运行的历史任务，用它比较模型和提示词。
- 把失败归因到需求、计划、代码或环境，并能识别 agent 削弱测试的迹象。

### 核心概念

**打个比方**：像考驾照：先过机考（全自动），再过场地考（仪器判），最后考官跟车（人判）。考官还得留意学员有没有趁人不注意把桩挪开。

**“完成”的三层**

| 层 | 谁来判 | 检查什么 | 拦不住什么 |
| --- | --- | --- | --- |
| 测试通过 | 代码 | 由验收标准（Day89）转成的测试全部通过 | 测试没写到的需求 |
| 构建通过 | 代码 | 编译、类型检查、静态检查、完整测试套件、依赖和安全扫描 | 设计是否合理、是否符合团队约定 |
| 评审通过 | 人 | 实现是否符合需求本意、可维护、没有越出范围 | 评审人漏看的地方 |

越往上越便宜、越可重复，越往下越接近真的完成。agent 报告“已完成”只是一个状态申请，成立与否由这三层决定，第三层永远由人给出。

**一组可以重复运行的历史任务**

比较模型和提示词，需要一套固定的任务。最可靠的来源是团队已经合并过的改动：

- 取合并前的那个提交作为起点。
- 当时的需求（最好是 Day89 格式的结构化需求）作为输入。
- 合并时一起加入的测试作为“隐藏测试”，agent 运行时看不到，跑完后再用它们判定。

公开的 SWE-bench 用的是同一个思路：从 GitHub 上收集真实的问题，给模型一个代码库和一段问题描述，让它产出补丁，再在基于 Docker 的环境里统一评测。自己的任务集贴近自己的代码库和约定，比公开榜单更能说明问题。

《Demystifying evals for AI agents》建议从二十到五十个来自真实失败的任务起步，优先挑 agent 曾经做错的那类。几个要点：

- **环境钉死。** 容器镜像、依赖锁文件、测试命令都固定，否则分数变化可能只是环境变了。
- **每个任务跑多次。** 输出有波动，报告每个任务在多次运行中的通过次数，不只看单次结果。
- **一次只改一个变量。** 换模型时不同时改提示词（Day32）。看逐个任务的翻转，比只看总分更能看出变化是真是假。
- **评结果。** 用隐藏测试和构建结果判定，不要求 agent 按某种步骤顺序做（Day23）。

**失败归因**

| 归因 | 典型表现 | 谁去修 |
| --- | --- | --- |
| 需求 | 验收标准缺失或自相矛盾，agent 准确实现了错误的理解 | 澄清 agent 的提示词、需求审批 |
| 计划 | 找错文件、漏掉调用方、步骤顺序不对 | 规划提示词、代码地图、计划校验 |
| 代码 | 计划对了，实现有逻辑错误 | 编码提示词、模型选择、反馈信息的质量 |
| 环境 | 依赖装不上、测试本身不稳定、超时 | 工作区镜像和基础设施，与模型无关 |

归因靠读追踪（Day24）。把环境问题算成模型的失败，会让你为一个不存在的问题去换模型。

**警惕为了通过而削弱测试**

agent 的目标是让测试变绿，最省事的路有时是改测试。常见迹象：删除或跳过测试、放宽断言、修改期望值、用宽泛的异常捕获吞掉错误、在业务代码里针对测试数据写特例、改动 CI 配置。控制手段放在模型之外：

- 隐藏测试和验收测试不进入 agent 的可写范围。
- 对改动做确定性检查，命中就标记，交给评审人重点看。
- 测试目录和 CI 配置设代码所有者，改动它们需要额外审批（Day92）。

```python
import re

TEST_PATH = re.compile(r"(^|/)(tests?|__tests__)/|_test\.py$|(^|/)test_[^/]*\.py$")
SKIP_MARK = re.compile(r"pytest\.mark\.skip|pytest\.skip\(|@unittest\.skip")

def flag_test_weakening(changed_files: dict[str, str], deleted_files: list[str]) -> list[str]:
    """changed_files: 路径 -> 新增的行（合并成一段文本）。返回需要评审人重点看的问题。"""
    flags = [f"删除了测试文件 {p}" for p in deleted_files if TEST_PATH.search(p)]
    for path, added in changed_files.items():
        if TEST_PATH.search(path):
            flags.append(f"修改了测试文件 {path}")
        if SKIP_MARK.search(added):
            flags.append(f"{path} 新增了跳过测试的标记")
        if path.startswith(".github/workflows/"):
            flags.append(f"修改了 CI 配置 {path}")
    return flags
```

这段检查只负责标记，是否接受由评审人决定。agent 有时确实需要修改错误的测试，标记的意义是让这种修改一定被人看到。

### 动手练习

**20 分钟必做**

1. 从你自己的仓库，或任意一个带测试的开源小仓库里，挑三到五个已合并的改动，为每个写出起点提交、需求描述和隐藏测试的位置。

**课后选做**

1. 为案例 B 写一张表：三层“完成”各自在流程的哪一步检查、结果写在哪里、失败后回到哪一步。
2. 从上面挑一个任务，在起点提交上让一个编码 agent 跑五次，每次用隐藏测试判定，记下五次里通过几次，并读一遍失败那几次的追踪做归因。

### 自检

1. 历史任务集里的“隐藏测试”为什么不能让 agent 在运行时看到？
