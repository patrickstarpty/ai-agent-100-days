## Day89 - 需求澄清 Agent

> 案例：编码 Agent 与研发流程 ｜ 建议用时 1 小时

> **一句话**：把一张写得含糊的工单，变成一份带正例、反例和边界、能用测试检验的结构化需求；缺的信息去问提出人，最后交给人审批。
>
> **放在全局看**：这是流程里第一个 agent 步骤（Day88），它的产物是编码和验收（Day90）的依据。它读的是任何人都能写的工单文本，按 Day57 的分析，它手里没有任何代码写权限。

### 学习目标

- 能把一条模糊的需求改写成带正例、反例和边界的验收标准。
- 设计“提问而不猜”的机制，以及等待回答时流程的状态。
- 定义澄清 agent 的输出结构和它的权限范围。

### 核心概念

**打个比方**：像装修前的量房确认：业主说“客厅亮堂一点”，设计师把它变成“加两盏筒灯，开关装在进门左手边”；拿不准的打电话问业主，最后请业主在确认单上签字再开工。

**模糊在哪里**

一张典型的工单：“订单导出要支持按日期筛选。”编码 agent 拿到它能写出代码，但至少有这些事没说清：按下单日期还是支付日期；起止日期是否包含当天；用哪个时区；只传开始日期时怎么办；结束早于开始时报错还是返回空。每一个没说清的地方，agent 都会替你选一个答案，而且不会告诉你它选了。

**验收标准的三类例子**

| 类型 | 例子 | 作用 |
| --- | --- | --- |
| 正例 | 筛选 3 月 1 日到 3 月 31 日，返回下单日期落在这段时间内的订单 | 说明要做到什么 |
| 反例 | 2 月 28 日 23:59 下单的订单不出现在结果中 | 说明不该出现什么，常常最能暴露理解偏差 |
| 边界 | 起止为同一天时返回当天的订单；结束早于开始时返回参数错误 | 说明边缘情况的约定 |

每条标准写成“给定……，当……，则……”的形式，Day90 可以把它们直接变成测试。写不成这种形式的标准，通常说明它还不够具体。

**提问，不靠猜**

缺失的信息分两类处理：

- **必须问的。** 影响行为、会被用户看到的选择，例如用哪个日期字段。agent 通过一个“提问”工具在工单下留言问提出人，流程进入 `awaiting_requester`，状态经检查点保存（Day40），收到回答后从这里继续。这正是《12-Factor Agents》里“用工具调用联系人”的做法。
- **可以先假设的。** 惯例明确、影响小的选择，例如沿用现有接口的日期格式。写进 `assumptions` 列表，让审批人一眼看到并确认。

提问要合在一起问，一次列清所有问题，免得来回打扰提出人。提问的轮数和等待时长都设上限，超时就把任务标为等待人工处理，不能自行决定一个答案继续往下走。

**输出：一份交给人审批的结构化需求**

```json
{
  "ticketId": "ORD-1024",
  "ticketRevision": 3,
  "summary": "订单导出接口支持按下单日期筛选",
  "inScope": ["导出接口增加 start_date、end_date 参数"],
  "outOfScope": ["导出页面的界面改动"],
  "acceptanceCriteria": [
    {"id": "AC-1", "type": "positive", "given": "存在 3 月内下单的订单", "when": "筛选 3/1 至 3/31", "then": "全部返回"},
    {"id": "AC-2", "type": "negative", "given": "存在 2/28 23:59 下单的订单", "when": "筛选 3/1 至 3/31", "then": "不返回该订单"},
    {"id": "AC-3", "type": "boundary", "given": "任意数据", "when": "结束日期早于开始日期", "then": "返回参数错误"}
  ],
  "assumptions": ["日期按系统配置的业务时区解释"],
  "openQuestions": [],
  "status": "draft"
}
```

提交审批之前，代码先做确定性检查：每条标准有 ID；至少有一条反例和一条边界；`openQuestions` 为空；`ticketRevision` 与工单当前版本一致。检查不通过就退回给 agent 补充。审批人是提出人或产品负责人，批准后 `status` 才变为 `approved`，后面的步骤只认这个版本。

**权限：只读，再加两个受限的写动作**

工单的描述和评论是不可信内容（Day57、Day58），里面可能混着看起来像指令的文字。所以澄清 agent 的工具很少：

| 工具 | 范围 |
| --- | --- |
| 读工单 | 只读当前这张工单 |
| 搜索代码（可选） | 只读，用来理解现有行为；可读范围不超过能看到这张工单的人的权限 |
| 提问 | 只能在当前工单下留言 |
| 提交需求草稿 | 只能写自己的草稿，状态固定为 `draft` |

它不能推送代码、不能改工单状态、不能访问外部网络。即使工单里有人写了“顺便把某项检查关掉”，这也只会作为一条需求出现在草稿里，由审批人看到并决定。提问工具是一个对外通道，留言只发到当前工单，也就只有本来就能看到这张工单的人看得见。

### 动手练习

1. 从你的工单系统里挑一张写得最短的需求，按上面的格式改写，至少写出一条正例、一条反例、一条边界，并列出需要问提出人的问题。
2. 写出提交审批前的确定性检查函数会检查哪几项，每项不通过时退回什么信息。

### 自检

1. 为什么反例常常比正例更能暴露对需求的误解？
2. 澄清 agent 等了很久没收到提出人的回答，系统应该怎样处理？
