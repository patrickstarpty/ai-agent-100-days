## Day59 - 最小权限与 Agent 身份

> 安全与治理 ｜ 建议用时 1 小时

> **一句话**：每个 agent 有自己的身份和刚好够用的权限，需要写东西时借用批准它的那个人的身份，而且只在这一次任务里有效。
>
> **放在全局看**：Day21 让检索带上提问人的身份，Day41 让审批后的写操作以审批人身份执行，这一课把这些做法收成一套身份与权限设计。它是 Day58 里“限制后果”最主要的手段，MCP 的身份透传（Day52）和提议与采纳（Day82）都建立在它之上。

### 学习目标

- 为系统里的每个 agent 定出身份、自身权限和执行写操作时使用的身份。
- 会计算一次运行的有效权限，并让它随任务收窄。
- 为无人值守的 agent 和暂停后恢复的任务设计授权检查。

### 核心概念

**打个比方**：像小区的物业维修工：他有自己的工牌，凭工牌只能进工具间；要进业主家修水管，得业主开门；物业为这张维修单发一张临时门卡，只开这一户，修完收回。

**三种身份**

| 身份 | 代表谁 | 用来做什么 |
| --- | --- | --- |
| 用户身份 | 提问人、发起人或审批人 | 检索时过滤权限；执行经过批准的写操作 |
| agent 身份 | 某个 agent（及其定义修订） | 标明“是哪个 agent 在做”；承载它自身很小的权限 |
| 限定范围的服务身份 | 一个无人值守的任务 | 没有在线用户时，代表一个写清了范围和负责人的用途 |

一条写操作的记录里，应当同时出现“代表谁”和“由哪个 agent 执行”，审计（Day62）才能完整。

**每个 agent 一个身份**

多个 agent 共用一个大服务账号，是一种常见的反模式：出了问题分不清是谁做的，也没法只吊销其中一个，权限只能按最宽的那个 agent 来给。每个 agent 一个身份，就能分别授权、分别审计、分别停用。OWASP 的 agent 风险清单也指出，agent 没有自己的、受管理的身份时，就无法真正落实最小权限。

**写操作以用户身份执行**

agent 自己的身份不持有写权限。它能做的是生成提议；用户批准后，系统用这位用户委托的、只覆盖这一次操作的凭据去执行。这样即便 agent 被注入（Day58），它最多只能提出一个奇怪的提议，而提议要经过人和门禁（Day65）。

**权限随任务收窄**

一次运行的有效权限取三者的交集：平台为该 agent 身份登记的权限上限（由工具白名单推出，Day48）、用户本人的权限、这次任务实际需要的权限。权限上限由平台登记，不写在 agent 定义里，这和 Day55 “定义里不放权限”是一致的。

```python
def effective_scopes(agent_ceiling: set[str], user: set[str], task_needs: set[str]) -> set[str]:
    return agent_ceiling & user & task_needs

# 一次只读分析：即便用户本人有写权限，这次运行也拿不到
scopes = effective_scopes(
    agent_ceiling={"ticket:read", "repo:read", "ticket:comment"},   # 平台登记的上限
    user={"ticket:read", "ticket:comment", "repo:read", "repo:write"},
    task_needs={"ticket:read", "repo:read"},
)
assert scopes == {"ticket:read", "repo:read"}
```

工具注册表（Day48）按有效权限决定这次运行能看到哪些工具；分发层在执行前再查一遍。模型提出了权限之外的调用，直接拒绝并返回错误，不靠模型自觉。

**无人值守的 agent**

由事件或定时任务触发的 agent（Day81）没有在线用户，必须明确它代表谁。可选的有：触发事件的人、预先指定的审批人、一个专用的服务身份。用服务身份时，写清四件事：能访问哪些项目和数据、是只读还是只能提议、负责人是谁、什么时候到期。它的写操作仍走“提议、采纳、以采纳人身份执行”（Day82）。

**恢复时重新检查授权**

任务可能在等待审批时暂停很久（Day40）。这期间发起人可能被移出项目，审批人可能换岗，源系统的权限可能变了。恢复时要重新计算有效权限，不能沿用暂停前缓存的令牌或权限集合。权限已经不够时，以 `permission_changed`（权限变更，Day45 停止原因枚举里的值）结束，并通知发起人。
