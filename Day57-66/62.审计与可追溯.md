## Day62 - 审计与可追溯

> 安全与治理 ｜ 建议用时 1 小时

> **一句话**：每一次写操作都留下一条记录，说清谁要求的、谁批准的、哪个 agent 的哪个版本做的、依据是什么、结果如何，并且能从结果一路追回依据。
>
> **放在全局看**：Day41 的审批和 Day59 的身份提供了“谁”，Day69 会讲的追踪提供“过程”。审计记录是业务记录，和追踪分开保存，用 ID 关联；它也是 Day63 保留期和 Day82 提议生命周期的落脚点。

### 学习目标

- 为 agent 的每类写操作设计审计记录的字段。
- 能从一个线上结果沿着 ID 追溯到它的依据。
- 说清审计记录和追踪为什么分开保存、怎样关联。

### 核心概念

**打个比方**：像仓库的出入库单：每张单写明申请人、批准人、经手人、依据的采购单号和实际出库的数量，单据长期归档；仓库的监控录像另外保存，只留一段时间，需要时按单号和时间去调。

**一条审计记录写什么**

| 字段 | 说明 |
| --- | --- |
| 事件 ID 与时间 | 唯一标识，按时间可排序 |
| 发起人 | 谁提出了这个需求（用户 ID） |
| 批准人与批准时间 | 谁点了同意；批准时看到的内容版本（例如内容的哈希） |
| 执行者 | 哪个 agent、哪个定义修订（Day55、Day74），实际使用的模型（Day70） |
| 执行身份 | 这次写操作以谁的身份执行（Day59） |
| 动作与对象 | 工具名、目标系统里的对象、参数摘要 |
| 依据 | 引用的文档片段 ID、工单号、提议 ID |
| 结果 | 成功、失败或部分成功；目标系统返回的对象 ID（提交号、评论 ID） |
| 关联 ID | trace ID、幂等键（Day40） |

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class AuditRecord:
    event_id: str
    at: str                      # ISO 8601 时间
    requested_by: str
    approved_by: str | None      # 不需要审批的动作写 None，并在策略里说明原因
    approved_content_hash: str | None
    agent_id: str
    agent_revision: str          # agent 定义的修订号（Day55）
    model: str                   # 实际命中的模型
    acting_as: str
    action: str
    target: str
    evidence: tuple[str, ...]    # 片段 ID、工单号、提议 ID
    outcome: str                 # "succeeded" / "failed" / "partial"
    result_ref: str | None
    trace_id: str
    idempotency_key: str
```

**先记后做**

动作执行之前先写一条“待执行”的记录，执行后补上结果，这和 Day40 的“先记后做”是同一个做法。进程在两者之间崩溃时，审计里留着一条没有结果的记录，正好提示需要核对目标系统。

**从结果追溯到依据**

以案例 B 为例，一条可追溯的链是：发布记录 → 合并请求 → 合并审批 → 编码 agent 的提议 → 需求工单与澄清后的需求 → 具体过程的 trace。每一跳都靠记录里的 ID 连起来。检验方法很简单：随手挑一次线上写操作，看能不能只凭记录里的 ID 走回最初的依据。走不通的那一跳就是要补的字段。

**审计记录与追踪分开**

| 维度 | 审计记录 | 追踪（Day69） |
| --- | --- | --- |
| 用途 | 业务与合规：谁做了什么、凭什么 | 调试与评估：过程怎样走的 |
| 读者 | 业务负责人、审计和安全人员 | 开发和运维人员 |
| 内容 | 结构化字段，原文只存 ID 和摘要 | 完整的输入输出和每个步骤 |
| 保留期 | 按业务和合规要求，通常更长 | 较短，按 Day63 的策略清理 |
| 可变性 | 只追加，不修改、不删除 | 可以抽样，到期清理 |

两者互存对方的 ID：审计记录里有 trace ID，追踪里有审计事件 ID。追踪会先被清理，所以依据必须以 ID 和摘要的形式写进审计记录本身，不能只写一句“详见 trace”。

**谁能写审计记录**

审计记录由执行写操作的那段确定性代码写入，agent 的身份对审计存储既不能改也不能删。审计记录本身也受权限控制：里面的摘要和对象 ID 同样可能涉及敏感内容。

### 动手练习

**20 分钟必做**

1. 列出案例 B 从需求工单到发布的所有写操作，为每一类写出审计记录里“依据”和“结果”两个字段具体存什么。

**课后选做**

2. 做一次倒查演练：假设线上出现了一个有问题的发布，写出你会依次查哪几条记录、靠哪个 ID 从一条跳到下一条。
