## Day57 - Agent 的威胁模型

> 安全与治理 ｜ 建议用时 1 小时

> **一句话**：一个 agent 既能读私有数据、又会读到外来内容、还能往外发东西，就可能被人利用来泄密。
>
> **放在全局看**：安全设计的起点，是画清每个 agent 能接触什么、能做什么。

### 学习目标

- 用“三要素”快速判断一个 agent 设计有没有数据外泄风险。
- 为自己的系统画一张威胁模型草图。

### 核心概念

**打个比方**：设想一位能进档案室的新员工：他会认真照办收到的每一张纸条，手里还有寄信的权限。只要有人能把纸条塞给他，档案就可能被寄出去。

**模型分不清指令和数据**

模型读到的所有文本都在同一个上下文里。网页、邮件、工单、文档、工具返回值里只要出现一句像指令的话，模型就可能照做。这叫提示注入；当恶意文本藏在 agent 自己去读取的内容里时，叫间接提示注入。目前没有办法在模型层面彻底杜绝它，所以防护要靠系统设计。

**致命三要素**

Simon Willison 在 2025 年提出一个简单的判断方法。一个 agent 同时具备下面三项时，攻击者就可能让它把私有数据送出去：

1. 能访问私有数据。
2. 会读到不可信的内容（攻击者能控制的文本或图片）。
3. 有对外发送的途径（发请求、发消息、生成带链接的内容等）。

去掉任何一项，这条攻击路径就断了。评审一个设计时，先数它占了几项。

**用案例 B 练一遍**

AI 原生研发流程里，agent 读取需求工单后编码、提交、触发构建和发布：

| 要素 | 在这个流程里是什么 |
| --- | --- |
| 私有数据 | 代码仓库、配置、构建环境里的密钥 |
| 不可信内容 | 工单的描述和评论（任何能提工单的人都能写）、依赖包的文档、拉取到的网页 |
| 对外途径 | 推送代码、构建时的网络访问、在工单里回复、触发发布 |

三项全占。可用的手段包括：

- 审批关卡放在“不可信内容进入”和“对外动作”之间（Day41）。
- 编码环境不放生产密钥，网络访问走白名单。
- agent 只能推送到自己的分支，合并和发布由人或确定性规则放行（Day65）。
- 需求澄清和编码用不同的 agent，前者没有代码写权限。

**把防护放在模型之外**

提示词里写“不要泄露数据”只能降低概率。能真正拦住的是权限、网络、审批这些模型无法绕过的控制。
