## Day64 - 成本与预算治理

> 安全与治理 ｜ 建议用时 1 小时

> **一句话**：把每一次模型调用的花费记到具体的任务、用户和项目上，再用分层的预算管住总量，预算用完就明说排队或拒绝。
>
> **放在全局看**：Day07 讲了单次请求的成本，Day45 给单次运行定了上限，Day70 会讲的模型网关负责记下每一次调用。这一课把这些记录汇总起来做治理；具体的降本手段 Day71 会讲。

### 学习目标

- 设计逐次调用记录里用于成本归因的字段。
- 为系统定出多个层级的预算，以及预算用完时的行为。
- 识别并拦住失控的循环。

### 核心概念

**打个比方**：像单位食堂的饭卡：每刷一次都记下是谁、在哪个窗口、花了多少；每张卡有每天的限额，部门还有每月的总额度。余额不够时刷卡机直接提示，不会悄悄只打半份菜，还当作一整份记账。

**从逐次调用归到任务、用户和项目**

网关（Day70）为每次模型调用写一条记录。要能归因，记录里除了模型、输入输出 token 和成本，还要带上：任务 ID、运行 ID、用户 ID、项目 ID、agent ID 和步骤名。这些 ID 和追踪上下文一样，随调用一路往下传，后台任务和子 agent（Day79）也不能丢。

成本优先用供应商在响应里报告的用量计算，再乘以带版本的价格表。只靠自己数 token 去估算会有偏差，例如撰写时（2026 年 10 月）Langfuse 的文档就提到（以官方文档为准），推理类模型的隐藏推理 token 看不到，无法靠对输入输出分词推算成本。

```python
from collections import defaultdict

def cost_by(records: list[dict], key: str) -> dict[str, float]:
    totals: dict[str, float] = defaultdict(float)
    for r in records:
        totals[r[key]] += r["cost"]
    return dict(totals)

# cost_by(records, "project_id")、cost_by(records, "user_id")、cost_by(records, "task_id")
```

**多个层级的预算**

| 层级 | 管什么 | 来源 |
| --- | --- | --- |
| 单次运行 | 一次任务的步数和 token | Day45 |
| 每个用户每天 | 单个用户的用量 | 防止个别人或个别脚本占满资源 |
| 每个项目每天或每月 | 一个项目的总花费 | 和项目负责人约定 |
| 全局 | 整个系统的上限 | 兜底，防止各层加起来失控 |

每次调用之前，按预估的成本检查所有适用的层级，调用之后按实际用量结算。检查由网关里的代码完成，agent 无法绕过。

```python
def blocking_scope(est: float, scopes: list[tuple[str, str]],
                   spent: dict, limit: dict) -> tuple[str, str] | None:
    for scope in scopes:            # 例如 [("run", rid), ("user", uid), ("project", pid)]
        if spent.get(scope, 0.0) + est > limit[scope]:
            return scope            # 返回是哪一层不够，用于告知用户
    return None
```

**预算用完时公开处理**

可以接受的行为只有两种：排队（后台任务等到下一个预算周期，界面上显示原因）和拒绝（在线请求返回明确的错误，说明是哪一层预算用完、找谁调整）。停止原因记为 `budget_exhausted`（预算耗尽，Day45 停止原因枚举里的值），写进任务记录和追踪。

绝不能做的是悄悄丢弃请求，或把上下文、步数截短后把结果当作完整的交出去。用户以为拿到的是完整答案，问题就被藏起来了。接近上限时提前通知项目负责人，比到点直接拒绝友好得多。

**简单的步骤用便宜的模型**

路由、分类、抽取、改写查询这类步骤，通常不需要最强的模型。每个步骤用哪个档位的模型，在网关里配成逻辑名，由评估（Day32）在同一批用例上比较之后决定，不凭感觉。

**警惕失控的循环**

常见的成本事故来自循环：同一个工具用同样的参数反复调用；重试（Day09）叠加在 agent 循环上，再叠加多 agent 的并发，次数成倍放大；主动 agent（Day81）被自己产生的事件再次触发。对应的控制有：单次运行上限、重复调用检测、按 agent 的调用频率限制、按小时比较花费和平时基线的告警，以及一个能立刻停掉某个 agent 的开关。
