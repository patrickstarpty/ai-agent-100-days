## Day60 - 沙箱与代码执行

> 安全与治理 ｜ 建议用时 1 小时

> **一句话**：模型写出来的代码，要放在一个看不到密钥、出不了网、有时间上限、用完就扔的隔离环境里运行。
>
> **放在全局看**：代码执行让 agent 的能力大增，也让 Day58 的注入从“说错话”升级为“做错事”。沙箱是编码 agent（Day87~93）和任何会运行生成代码的工具的底座，Day93 会把这里的原则用到构建环境上。

### 学习目标

- 说清模型生成的代码为什么必须隔离运行。
- 解释文件系统和网络两条边界为什么缺一不可。
- 为自己的代码执行环境写出一份可检查的沙箱配置。

### 核心概念

**打个比方**：像化学实验室的通风橱：有危险的操作都在橱里做，橱有自己独立的排风，不和办公室的空气相通；贵重的试剂不放进去；每次做完都清理干净再给下一个人用。

**为什么必须隔离**

模型生成的代码，应当按“来历不明的代码”对待。即使没有人攻击，它也可能有缺陷：删错目录、陷入死循环、把磁盘写满。一旦上下文里混进了注入内容，这段代码就可能按攻击者的意图写成。代码是实时生成的，数量也大，逐段人工审核不现实，只能让它在一个出了事也没关系的地方运行。

**两条边界，缺一不可**

| 边界 | 做法 | 只有它会怎样 |
| --- | --- | --- |
| 文件系统 | 只能读写本次任务的工作目录；看不到用户主目录、密钥文件、其他任务的数据 | 没有网络边界时，工作目录里能读到的代码和数据可以被发出去 |
| 网络 | 默认不能联网；需要时经沙箱外的代理，只放行白名单域名 | 没有文件系统边界时，代码能读到沙箱外的密钥，或改写沙箱外的配置和启动脚本，从而跳出隔离 |

Anthropic 在介绍其编码工具的沙箱时，也明确把两者同时具备作为有效隔离的前提，网络访问经由沙箱外的代理按域名放行。

**密钥不进沙箱**

沙箱里不放生产密钥，也不放生产数据。常见的漏洞在于：环境变量里带着部署凭据；挂载了含令牌的配置文件；运行环境的元数据接口能换取云凭据。代码确实需要调用某个外部服务时，让沙箱外的代理替它加上凭据并转发，沙箱里只拿到结果。需要数据时用测试数据或脱敏后的副本。

**资源和时间上限**

CPU、内存、磁盘、进程数、运行时长、输出大小都要有上限。达到上限就终止，并把“超时”“内存超限”这样明确的错误交回给 agent（Day06），让它据此调整，同时计入 Day45 的预算。

**每次从干净状态开始**

每次运行从固定版本的镜像启动，结束后整个销毁，不复用上一次的进程和临时文件。这样一次运行留下的东西影响不到下一次，不同用户的数据也不会在同一个环境里相遇。需要保留的产出（生成的文件、测试报告）要显式导出，并经过检查再进入后续步骤（Day65）。

**把配置写成可检查的数据**

沙箱配置本身就是安全策略，应当能被代码检查、被测试覆盖：

```python
from dataclasses import dataclass, field

@dataclass(frozen=True)
class SandboxSpec:
    image: str                                   # 固定版本的镜像
    network_allowlist: tuple[str, ...] = ()      # 空表示不能联网
    env: dict[str, str] = field(default_factory=dict)
    timeout_s: int | None = None
    fresh_each_run: bool = True

SECRET_HINTS = ("KEY", "TOKEN", "SECRET", "PASSWORD")

def check_spec(spec: SandboxSpec) -> list[str]:
    problems = []
    if any(h in k.upper() for k in spec.env for h in SECRET_HINTS):
        problems.append("环境变量里疑似有密钥")
    if "*" in spec.network_allowlist:
        problems.append("网络白名单不能用通配符放行全部")
    if spec.timeout_s is None:
        problems.append("缺少运行时长上限")
    if not spec.fresh_each_run:
        problems.append("每次运行必须从干净状态开始")
    return problems
```

按名字找密钥只是兜底，主要的保证仍来自“凭据只在沙箱外的代理里”这一设计。

### 动手练习

1. 主线项目在做测试设计时，如果要运行模型生成的测试脚本，为它填一份沙箱配置：文件系统能看到什么、网络白名单有哪些、需要的凭据怎样提供、各项上限、生命周期。
2. 写出三条证明边界生效的测试：读取工作目录以外的文件失败、访问白名单以外的域名失败、超时后进程被终止。

### 自检

1. 一个沙箱禁止了联网，但能读写用户主目录。说出它仍然存在的一种风险。
2. 沙箱环境只清理临时目录就继续给下一次运行使用，会留下哪些隐患？
