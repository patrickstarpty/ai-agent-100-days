## Day29 - Agent 轨迹与工具调用评估

> 评估 ｜ 建议用时 1 小时

> **一句话**：先检查 agent 最后把事情办成了没有，再用少数几条硬约束检查它中途有没有越界。
>
> **放在全局看**：Day26 的评分器评一次回答，这一课评一个多步任务。它把 Day23 的“评结果，不评路径”落到 agent 上，也是 Day85 主动 agent 评估和 Day90 编码 agent 验收的基础。

### 学习目标

- 能为一个多步任务写出最终状态检查，并说清什么时候才需要检查工具调用。
- 能为多步任务设计部分得分。
- 会把每个任务运行多次，用通过率报告结果。

### 核心概念

**打个比方**：像验收装修：先看房子是不是按图纸装好了、水电能不能用，不要求工人按你预想的顺序干活。但有几条红线必须查：承重墙不能动，预算不能超。

**最终状态优先**

agent 任务的评分首先看环境里的结果，例如：用例要求修复一个失败的测试，就去沙箱仓库里重新跑测试、查看是否开出了合并请求。结果要由评估代码从环境里读出来，不能采信 agent 自己说的“已完成”。每次运行都从干净的环境开始，避免上一次留下的文件或数据影响下一次。

**什么时候才检查工具调用**

只在下面几类情况下检查过程，而且写成约束，不写成标准步骤：

| 约束 | 例子（案例 B 的编码 agent） | 为什么必须查过程 |
| --- | --- | --- |
| 必须调用 | 提交前必须调用过 `run_tests` | 结果相同时，没跑测试的那次是侥幸 |
| 不得调用 | 不得调用 `merge_pr`、`deploy` | 越权动作即使结果看起来没坏，也不可接受 |
| 参数约束 | `git_push` 的分支必须以 `agent/` 开头 | 参数决定了影响范围（Day59） |
| 步数预算 | 工具调用不超过 30 次 | 结果对但代价失控，也是失败（Day45） |

**为什么精确匹配轨迹很脆弱**

把一条“标准轨迹”存下来、要求每次逐步一致，会误伤很多合理的变化：先多读一个文件再改、遇到瞬时错误后重试、把两次查询合成一次、换了模型后步骤顺序不同。这样的评估每次改进都会变红，团队很快就不再相信它。约束只管红线，红线之内的路径由 agent 自己选。

**多步任务的部分得分**

把任务拆成几个可以从环境里验证的里程碑，例如“复现了失败的测试”“分支上测试通过”“开出了合并请求”。部分得分是完成的里程碑占比，帮助你看出卡在哪一步；“通过”仍然要求全部里程碑完成。违反任何硬约束，部分得分直接记 0。

用例沿用评估集的写法，期望里放最终状态和约束：

```python
spec = {
    "mustCallTools": ["run_tests"],
    "mustNotCallTools": ["merge_pr", "deploy"],
    "maxToolCalls": 30,
    "milestones": ["failingTestReproduced", "testsPassOnBranch", "prOpened"],
}

def check_run(run: dict, spec: dict) -> dict:
    calls, state = run["toolCalls"], run["finalState"]   # finalState 由评估代码从环境读取
    names = [c["name"] for c in calls]
    violations = [f"调用了禁止的工具 {t}" for t in spec["mustNotCallTools"] if t in names]
    violations += [f"没有调用 {t}" for t in spec["mustCallTools"] if t not in names]
    violations += [f"推送到了 {c['args']['branch']}" for c in calls
                   if c["name"] == "git_push" and not c["args"]["branch"].startswith("agent/")]
    if len(calls) > spec["maxToolCalls"]:
        violations.append(f"工具调用 {len(calls)} 次，超过上限 {spec['maxToolCalls']}")
    done = [m for m in spec["milestones"] if state.get(m)]
    return {
        "passed": not violations and len(done) == len(spec["milestones"]),
        "partial": 0.0 if violations else len(done) / len(spec["milestones"]),
        "violations": violations,
        "missing": [m for m in spec["milestones"] if m not in done],
    }
```

和 Day26 一样，返回的是明细：违反了哪条约束、缺了哪个里程碑。

**每个任务跑多次**

同一个任务、同一套配置，agent 每次的输出都可能不同，只跑一次的结果说明不了多少。每个任务运行多次（次数按成本定，例如五次），报告三样东西：

- 每个任务的通过次数，例如 `4/5`。
- 每次都通过的任务占比。用户每次都要得到正确结果时看这个。
- 至少通过一次的任务占比。允许多试几次、由人挑选结果时看这个。

两个占比差得越大，说明 agent 越不稳定。只看平均通过率，会把“一个任务总是失败”和“每个任务偶尔失败”混成同一个数。

**排查时从第一个出错的步骤看起**

失败的轨迹里，后面的错误常常是前面某一步错了之后连带产生的。读轨迹时找到第一个出错的步骤，把它归入失败分类表（Day24），后面的错误先不计。

### 动手练习

**20 分钟必做**

1. 给 Day10 命令行助手里的一个多步任务（例如“读取 `workspace/` 里的某个文件，再计算文件里的两个数字之和”）写一份 `spec`：最终状态里程碑、必须和不得调用的工具（`read_file`、`calculate`）、步数上限；也可以直接用 `samples/trajectories/` 里的样例轨迹，照它的工具调用记录填 `spec` 并打分。
2. 把这个任务跑五次，填一张表：每次是否通过、部分得分、违反了哪条约束。

**课后选做**

- 回头检查你的约束：有没有哪条其实是在规定步骤顺序，可以删掉或改成最终状态检查。
- 把 Day10 助手换成案例 B 或主线项目里的一个真实多步任务，重复第一步。
