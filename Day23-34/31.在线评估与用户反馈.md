## Day31 - 在线评估与用户反馈

> 评估 ｜ 建议用时 1 小时

> **一句话**：上线以后，从真实请求里抽样打分、收集用户的赞和踩，把确认过的失败补回评估集。
>
> **放在全局看**：离线评估（Day25~30）只能测你想到的问题，在线评估负责发现你没想到的问题。它的原料是 Day67、Day69 的追踪，它的产出流回 Day25 的评估集，形成一个闭环；能存什么、给谁看，受 Day63 的隐私规则约束。

### 学习目标

- 能决定线上哪些检查对全部流量运行、哪些只对样本运行。
- 能设计一条带 trace ID 的用户反馈记录。
- 能写出“线上失败变成评估用例”的流程。

### 核心概念

**打个比方**：像餐厅开业后的两件事：店长每天随机尝几道出锅的菜，顾客也会在点评里打星。店长尝出的问题和顾客的差评都要核实，核实过的写进后厨的操作手册。

**线上没有标准答案**

离线用例带着期望，线上请求没有。所以线上能用的评分器分两类：

| 评分器 | 线上怎么用 | 例子 |
| --- | --- | --- |
| 代码评分器（Day26） | 便宜、确定，可以对全部请求运行 | 引用都在检索结果里、引用的来源当前用户有权访问、输出结构合法、步数没超上限 |
| 模型评审员（Day27） | 每次都要调用模型，只对样本运行 | 结论能否从引用推出、是否答非所问 |

不需要期望答案的检查，才能搬到线上。Day26 里的 `mustContain` 搬不上去，`cited_were_retrieved` 可以。模型评审员在线上用的必须是已经校准过的版本，校准时用的是离线样本，线上流量的分布可能不同，所以要定期从线上样本里再抽一批人工复核。

**抽样**

只看随机样本，少见的失败很难碰到；只看被标记的请求，又会漏掉没人发现的问题。每一批待复核的样本由两部分组成：

- 被标记的请求：用户点了踩、代码评分器判为 `wrong`、弃答、出错或超出步数上限。
- 一部分纯随机抽取的请求，用来发现还没有被任何信号覆盖的失败类型。

评估平台通常可以按规则（过滤条件加抽样比例）自动对新进入的追踪运行评分器，Day33 会讲到具体对应。

**用户反馈怎样存**

赞和踩只有和那一次请求连起来才有用。每条反馈至少存这些字段：

```python
from dataclasses import dataclass, field
from datetime import datetime, timezone

REASONS = {"wrong_fact", "wrong_citation", "should_have_answered", "off_topic", "other"}

@dataclass
class Feedback:
    trace_id: str                    # 指向那次请求的完整追踪
    rating: int                      # 1 = 赞，0 = 踩
    reason: str | None = None        # 可选，取自 REASONS
    note: str | None = None          # 可选的自由文本，按 Day63 的规则保留和清理
    app_version: str = ""            # 提示词、模型、检索配置的版本
    at: datetime = field(default_factory=lambda: datetime.now(timezone.utc))
```

反馈表里只存 trace ID，不再复制一份问题和回答原文，原文留在追踪里，统一受保留期和查看权限管理。原因用固定的几个选项加一个可选的备注，选项和 Day24 的失败分类对齐，统计时才能直接按类别看。用 Langfuse 时，反馈可以作为分数挂到同一条追踪上：

```python
from langfuse import get_client

langfuse = get_client()
# fb 是上面的一条 Feedback
langfuse.create_score(name="user_feedback", value=fb.rating, data_type="BOOLEAN",
                      trace_id=fb.trace_id, comment=fb.reason)
```

**反馈要打折扣地读**

大多数用户不会点任何按钮，点了的人也不代表全体。一次踩可能是系统答错了，也可能是资料本身就是那样、用户不满意规则。除了按钮，复制回答、马上换个说法重问这类行为也是信号（隐式反馈），量大，但更需要解读。所以无论哪种反馈，都只是“值得看一眼”的信号，确认它是不是系统失败，仍然靠 Day24 的错误分析。

**从线上失败回流到评估集**

1. 被标记和随机抽取的请求进入复核队列。
2. 复核人按失败分类表标注：通过或不通过，属于哪一类。
3. 确认不通过的，改写成评估用例：去掉个人信息和与问题无关的细节，写上期望（`mustCiteSources`、`mustAbstain` 等），记录真实的标注人和来源 trace ID。
4. 新用例先进能力集，修好并稳定通过后转入回归集（Day23）。

**哪些不能存、不能给人看**

- 密钥、令牌和连接串不进追踪，也不进反馈。
- 用户在问题和备注里写的个人信息，按 Day63 定保留期，转成评估用例前必须去除。
- 复核人只能看到自己有权访问的来源原文，追踪平台里同样执行 Day21 的权限（Day69）。
- 评估用例进入公开或共享的仓库前，再检查一遍是否带有受限文档的原文。

### 动手练习

1. 列出主线项目线上要对全部请求运行的代码检查，和只对样本运行的模型评审，各写出理由。
2. 定义反馈的原因选项，逐项对应到你的失败分类表。
3. 写出一条线上失败从被标记到进入评估集的完整路径：谁复核、在哪里改写、怎样去除个人信息、谁批准合入。
