## Day49 - 工具的错误、超时与重试

> 工具、Skills 与 MCP ｜ 建议用时 1 小时

> **一句话**：模型能改正的错误交给模型，模型改不了也不该碰的错误由代码处理；写工具重试之前，先保证重复执行不会出事。
>
> **放在全局看**：Day09 处理的是模型调用本身的失败，Day06 把工具错误一律交还模型。这一课把工具失败细分开，配合 Day48 注册表里的只读或写、风险级别字段，决定每类失败由谁来处理。

### 学习目标

- 能把工具失败分到“交还模型”和“代码处理”两类，并说出理由。
- 给工具调用加上超时、部分结果标记和有限次重试。
- 说清写工具为什么需要幂等键，以及这个键应该由谁生成。

### 核心概念

**打个比方**：像餐厅后厨接单：单子上菜名写错了，退回给服务员改（交给模型）；燃气突然断了，厨师长去处理，不让服务员想办法（交给代码）；一道菜做到一半没了原料，就如实说“只上了半份”。

**先分清由谁处理**

| 失败 | 例子 | 由谁处理 | 做法 |
| --- | --- | --- | --- |
| 参数错误 | 日期格式不对、缺少必填项、取值超出范围 | 模型 | 返回错误说明，让模型改参数重试 |
| 未找到 | 订单号不存在、检索没有结果 | 模型 | 返回“没找到”和可能的原因，模型决定换条件还是问用户 |
| 业务规则拒绝 | 已发货的订单不能退订 | 模型 | 说明规则，模型向用户解释 |
| 超时、瞬时错误 | 下游接口超时、限流、连接中断 | 代码 | 只读工具有限次重试；写工具先确认状态 |
| 权限拒绝 | 当前用户无权访问这个工单 | 代码 | 不重试，不让模型换别的工具绕过去；记录并告知用户 |
| 代码缺陷 | 工具内部抛出意料之外的异常 | 代码 | 记录完整堆栈，给模型一句简短说明 |

交还模型的那几类，模型拿到说明后通常能自己纠正。交给代码的那几类，模型再怎么努力也改不了，让它处理只会多花几步，甚至诱导它去找别的路径。权限拒绝尤其如此：模型看到“无权访问”后换一个工具去拿同一份数据，正是最小权限要防的情况（Day59）。

MCP 规范也做了类似的区分：未知工具、请求格式不对属于协议错误，用 JSON-RPC 错误返回；接口失败、输入校验失败、业务规则错误属于工具执行错误，放在结果里并标 `isError: true`，规范建议 client 把后者交给模型，让它自行纠正。

**超时与部分结果**

每个工具都要有超时，时长随工具不同，可以作为注册表里的一个字段。超时之后分两种情况：

- 只读工具：可以有限次重试，或者返回已经拿到的部分结果，并在结果里写明“结果不完整”。例如分页检索取到第 3 页时超时，就返回前两页加一句“第 3 页之后未取到”。
- 写工具：超时只说明没等到响应，不说明操作没有生效（Day09）。不能直接重试，要先查状态，或者依靠幂等键。

部分结果必须带标记，并且标记要进入模型能读到的文本。没有标记，模型会把半份结果当作全部，再自信地给出结论。

**写工具的幂等键由代码生成**

在 agent 里，重复执行有两个来源：你的重试逻辑，以及模型看到报错后自己再发一次同样的调用。后者每次的 `tool_call_id` 都不同，所以不能拿它当幂等键。可靠的做法是由代码根据任务 ID、工具名和规范化后的参数算出幂等键，不让模型生成，也不让模型看见。

```python
import hashlib
import json

def idempotency_key(task_id: str, tool: str, args: dict) -> str:
    raw = json.dumps({"task": task_id, "tool": tool, "args": args}, sort_keys=True, ensure_ascii=False)
    return hashlib.sha256(raw.encode()).hexdigest()
```

同一任务里参数完全相同的写调用得到同一个键，下游据此只执行一次。“确实想再发一条一样的通知”这种需求很少见，遇到时应当由用户明确确认，不由模型决定。

**一个按策略执行工具的草图**

```python
class TransientError(Exception): ...      # 超时、限流、连接中断
class PermissionDenied(Exception): ...

def run_with_policy(spec, args: dict, ctx) -> dict:
    """返回 {"content": 给模型的文本, "is_error": bool, "stop": 停止原因或 None}"""
    attempts = 2 if spec.access == "read" else 1          # 写工具不在这里自动重试
    for attempt in range(1, attempts + 1):
        try:
            if spec.access == "write":
                args = {**args, "idempotency_key": idempotency_key(ctx.task_id, spec.name, args)}
            return {"content": spec.func(**args, timeout=spec.timeout), "is_error": False, "stop": None}
        except ValueError as e:                            # 参数错误、未找到、业务规则
            return {"content": str(e), "is_error": True, "stop": None}
        except PermissionDenied:
            ctx.log("permission_denied", tool=spec.name)
            return {"content": f"当前用户无权使用 {spec.name}，不要尝试用其他工具获取同样的数据。",
                    "is_error": True, "stop": "permission_denied"}
        except TransientError as e:
            ctx.log("tool_transient", tool=spec.name, attempt=attempt, error=str(e))
    if spec.access == "write":
        return {"content": f"{spec.name} 未确认是否已执行，已停止，等待人工核实。",
                "is_error": True, "stop": "tool_failed"}
    return {"content": f"{spec.name} 暂时不可用，已重试 {attempts} 次。请基于已有信息作答，并说明缺少这部分数据。",
            "is_error": True, "stop": None}
```

`stop` 不为空时，循环按 Day45 的停止原因结束任务，不再调用模型。草图假设 `ToolSpec` 比 Day48 多一个 `timeout` 字段，`func` 也接受 `timeout` 参数，实际要按工具自己的接口改。意料之外的异常不在这里捕获，交给外层（Day06 的 `run_tool`）记录堆栈，再给模型一句简短说明。

**错误文本是写给模型读的**

| 写法 | 模型下一步 |
| --- | --- |
| `KeyError: 'A9999'` | 猜原因，可能换个格式再试一次 |
| “订单 A9999 不存在。订单号格式为 A 加四位数字。请向用户核对订单号，不要猜测。” | 去问用户 |
| “start_date 应为 YYYY-MM-DD，收到的是 10/09。” | 改格式重试 |

一条好的错误文本说清三件事：出了什么错、正确的格式或条件是什么、下一步该怎么做。堆栈和内部细节写进日志，不进上下文（Day47）。
