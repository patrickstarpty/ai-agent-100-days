## Day53 - Skills：渐进式披露

> 工具、Skills 与 MCP ｜ 建议用时 1 小时

> **一句话**：Skill 是一个装着操作说明的文件夹，平时只让模型看到它的名字和一句简介，用到时再把全文和附件读进来。
>
> **放在全局看**：工具让 agent 能做事，Skill 告诉 agent 某类事该怎么做。渐进式披露是 Day43 上下文工程里“用到再取”的一个具体做法；Day54 讲导入外部 Skill 的风险，Day55 把 Skill 写进 agent 定义。

### 学习目标

- 说清一个 Skill 由哪几部分组成，以及三层加载各自在什么时候发生。
- 区分 Skill、工具和系统提示词，判断一段知识该放在哪里。
- 不依赖特定产品，用纯 Python 实现一个最小的 Skill 加载机制。

### 核心概念

**打个比方**：像公司的操作手册柜：新同事桌上只有一张目录卡，写着每本手册叫什么、什么时候用；遇到对应的活儿，才去柜子里取那一本；手册里提到的附表，翻到那一页才去拿。

**Skill 的结构**

按 Anthropic 的 Agent Skills 文档，一个 Skill 是一个目录，里面必须有一个 `SKILL.md`，开头是 YAML frontmatter，必填 `name` 和 `description`，正文是操作说明；目录里还可以放其他说明文件、参考资料和脚本。

```text
test-case-design/
├── SKILL.md            # frontmatter + 主要说明
├── TEMPLATES.md        # 用例模板，正文里提到时才读
└── examples/
    └── refund-flow.md  # 一个完整示例
```

```markdown
---
name: test-case-design
description: 根据需求描述设计功能测试用例，覆盖正常流程、边界值和异常流程。用户要求为某个需求写测试用例、补充测试点或评审用例覆盖时使用。
---

# 测试用例设计

1. 先从需求里列出输入、输出和业务规则，不确定的地方列成问题，不要自行假设。
2. 每条规则至少一条正常用例、一条边界用例、一条异常用例。
3. 输出格式按 TEMPLATES.md 中的“标准用例表”。
4. 涉及退订、退款这类资金流程时，再参考 examples/refund-flow.md。
```

`description` 要同时写清“做什么”和“什么时候用”，因为模型正是拿用户的请求去和它比对，决定要不要启用这个 Skill。

**三层加载**

| 层级 | 什么时候进上下文 | 内容 |
| --- | --- | --- |
| 元数据 | 一开始就在，放在系统提示词里 | 每个 Skill 的 `name` 和 `description` |
| 说明 | 模型判断任务需要这个 Skill 时 | `SKILL.md` 的正文 |
| 附件 | 正文提到、任务确实用到时 | 其他说明文件、参考资料；脚本只把运行结果放进上下文 |

撰写时（2026 年 10 月）Anthropic 文档给出的量级是：元数据每个 Skill 大约一百 token，正文在五千 token 以内，附件不读就不占上下文（以官方文档为准）。所以可以装很多 Skill 而不撑爆上下文。代价是每多一个 Skill，目录里就多一条要模型去区分的简介，装得太多时模型可能选错，这要靠评估来发现（Day29）。

**Skill、工具、系统提示词的分工**

| | 是什么 | 什么时候在上下文里 | 适合放 |
| --- | --- | --- | --- |
| 系统提示词 | agent 的身份、职责和底线 | 每一轮都在 | 每次任务都要遵守的规则 |
| Skill | 某类任务的做法、步骤、模板 | 用到时才加载 | 只在部分任务里需要、篇幅较长的专业做法 |
| 工具 | 可执行的动作 | 定义每一轮都在，结果在调用后 | 查询、计算、写入等需要代码执行的事 |

判断的办法：每次都要用的内容，放系统提示词；要真正执行一个动作的，做成工具；剩下的、按任务类型才需要的“怎么做”，写成 Skill。Skill 里可以说“用某某工具查一下”，但它不会因此获得那个工具，能用哪些工具仍由 agent 的白名单决定（Day48）。

**在自己的 agent 里实现**

Anthropic 的实现里，模型在一个带文件系统的执行环境里用命令读取 `SKILL.md` 和附件。自己的 agent 没有这样的环境时，可以用系统提示词里的目录加一个只读工具达到同样的效果，下面是本课程的一个草图：

```python
from pathlib import Path

SKILLS_ROOT = Path("skills").resolve()

def parse_frontmatter(text: str) -> dict:
    """只处理 `key: value` 形式的简单 frontmatter。"""
    _, head, _ = text.split("---", 2)
    return dict(line.split(":", 1) for line in head.strip().splitlines())

def skill_catalog() -> str:
    """第一层：拼进系统提示词的目录。"""
    lines = []
    for f in sorted(SKILLS_ROOT.glob("*/SKILL.md")):
        meta = parse_frontmatter(f.read_text(encoding="utf-8"))
        lines.append(f"- {meta['name'].strip()}: {meta['description'].strip()}")
    return "可用的 Skill（需要时用 load_skill 读取全文）：\n" + "\n".join(lines)

def load_skill(name: str, file: str = "SKILL.md") -> str:
    """第二、三层：作为只读工具提供给模型。"""
    base = (SKILLS_ROOT / name).resolve()
    path = (base / file).resolve()
    if base.parent != SKILLS_ROOT or not path.is_relative_to(base) or not path.is_file():
        return f"Skill {name} 中没有文件 {file}。"
    return path.read_text(encoding="utf-8")
```

`load_skill` 做了和 Day10 `read_file` 一样的目录限制。这个草图只读文件，不运行 Skill 里的任何脚本，原因在 Day54。

### 动手练习

**20 分钟必做**

1. 为主线项目写一个 Skill，主题从“带引用回答的格式要求”“需求澄清的提问清单”“测试用例设计”中选一个。写好 `description`，正文控制在一页以内，至少拆出一个附件。

**课后选做**

2. 列出你现在系统提示词里的每一段，逐段判断：留在系统提示词、挪进某个 Skill，还是应当做成工具。
3. 准备五个请求，其中三个应当触发你的 Skill、两个不应当，记下模型实际是否调用了 `load_skill`。

### 自检

1. 为什么 `description` 写得好不好，直接决定一个 Skill 有没有用？
2. 一个 Skill 的正文写着“用 tickets_update 工具把结论写回工单”，而当前 agent 的白名单里没有这个工具，会发生什么？
