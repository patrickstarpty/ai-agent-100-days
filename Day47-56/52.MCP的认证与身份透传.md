## Day52 - MCP 的认证与身份透传

> 工具、Skills 与 MCP ｜ 建议用时 1 小时

> **一句话**：远端 server 先要确认“谁在调我”，更要让下游系统知道“这次是替哪位用户查的”，否则权限就在中间这一跳丢掉了。
>
> **放在全局看**：Day21 要求检索按提问人的权限过滤，Day50 指出知识库以 MCP 接口提供时身份必须传到检索层。这一课讲怎样传。Day59 会把同样的思路推广到所有 agent 的写操作。

### 学习目标

- 区分服务身份和用户身份，说清各自用在哪一跳。
- 设计一条“用户令牌按请求传到下游”的链路，并知道 MCP 规范对令牌转发的限制。
- 说出用一个共享服务账号访问下游会出哪些问题。

### 核心概念

**打个比方**：像去档案馆代人调档：门卫要看你的工作证（服务身份），才放你进门；档案员还要看委托人的授权书（用户身份），才知道能调哪几份。只看工作证就开柜，你就能拿到委托人本来无权查看的档案。

**两跳，两个问题**

一次请求从 agent 到数据，通常经过两跳：

| 一跳 | 要回答的问题 | 典型做法 |
| --- | --- | --- |
| client → MCP server | 调用方是否为可信的应用，带的令牌是否签发给这个 server | HTTP 传输下按 MCP 规范走 OAuth，令牌放在 `Authorization: Bearer` 头里，每个请求都带 |
| MCP server → 下游系统 | 这次查询替哪位最终用户发出，下游应按谁的权限过滤 | 下游收到代表该用户的令牌，在下游应用权限 |

第一跳是认证，撰写时（2026 年 10 月）的规范已经定得很细（以官方文档为准）：server 是 OAuth 资源服务器，必须校验令牌确实是签发给自己的（受众绑定）；令牌不能放进 URL 查询串；令牌无效返回 401，权限范围不够返回 403。stdio 传输不走这套，规范建议从环境里取凭据，也就是说本地 server 以启动它的那个人的身份运行。第二跳才是这一课的难点。

**规范不允许原样转发令牌**

最直接的想法是把 client 发来的令牌原样转给下游。MCP 规范明确禁止：server 不得接受或转递签发给别人的令牌；server 调用上游接口时，可以作为 OAuth client 去拿一个单独的令牌，这个令牌由上游的授权服务器签发。

所以“身份透传”要传的是用户身份，令牌在每一跳各换一张。常见做法是在 server 这一跳，用收到的用户令牌去换一张以下游为受众、仍然代表这位用户的令牌（各家身份平台叫法不同，例如 on-behalf-of），再拿它访问下游。下游据此知道是谁，按谁的权限过滤。

**一个具体的例子**

微软的文档讲了 agent 通过 MCP 连接 Foundry IQ 知识库的做法，两种身份分得很清楚。下面提到的查询时权限过滤和 MCP 连接（撰写时为预览功能，以官方文档为准）：

- agent 到知识库 MCP 端点这一跳，用项目的托管身份建立连接，这是服务身份。
- 知识源里有带权限的内容时，要把已登录用户的令牌放在 `x-ms-query-source-authorization` 头里随请求转发，检索引擎才能按这位用户过滤。文档建议在多用户应用里为每位用户传各自的令牌，例如经由 on-behalf-of 流程取得。
- 不传用户令牌时，带权限的知识源会返回未过滤的结果。

最后一条值得记住：身份缺失时，有的系统会放开结果，并不报错。设计时要让自己的链路在用户令牌缺失时直接拒绝，不依赖下游的默认行为。

**用户令牌不经过模型**

用户令牌是按请求的上下文，由宿主程序从登录会话里取出，放进请求头或调用上下文。它不能是工具参数：参数由模型生成，令牌一旦进了参数，就进了上下文，可能被写进追踪，也可能被注入的文本诱导着发到别处。

```python
def kb_search(query: str, *, ctx) -> str:           # query 来自模型；ctx 来自宿主
    if not ctx.user_token:
        raise PermissionError("缺少用户身份，拒绝检索")   # 缺身份就拒绝，不退回服务账号
    downstream = ctx.exchange_token(ctx.user_token, audience="knowledge-search")
    return search_api(query, token=downstream)        # 下游按这位用户的权限过滤
```

`exchange_token` 和 `search_api` 是示意，具体的换取方式取决于你们用的身份平台。

**共享服务账号会出什么问题**

只用一个服务账号访问下游，看起来省事，代价是：

- 每个用户都拿到服务账号的全部权限，Day21 的按源系统权限检索形同虚设。
- 审计记录里只有服务账号，查不出是谁看了什么（Day62）。
- 某人被移出项目后仍然能查到原来的资料，因为下游从来不知道请求来自他。
- 一旦发生提示注入，攻击者能拿到的范围是服务账号的全部范围（Day57）。

服务身份也有正当用途：建立连接、读公开资料、后台同步索引。规则是写清每一跳用哪种身份，凡是涉及“这个人能不能看”的地方，都用用户身份。没有在线用户的后台 agent 代表谁，要事先定下来（Day21、Day81）。

### 参考说明

- [MCP 规范：Authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)：HTTP 传输下的 OAuth 角色划分，令牌放在 `Authorization: Bearer` 头里且每个请求都带、不得放进查询串，server 必须校验令牌受众，401 与 403 的用法，stdio 传输改为从环境取凭据。
- [MCP 规范：Authorization Security Considerations](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations)：server 调用上游时使用上游授权服务器签发的单独令牌，不得转递从 client 收到的令牌。
- [Connect agents to Foundry IQ knowledge bases](https://learn.microsoft.com/azure/ai-foundry/agents/how-to/tools/knowledge-retrieval)：agent 通过 MCP 连接知识库，连接用项目托管身份，用户令牌放在 `x-ms-query-source-authorization` 头里按请求转发，不传时带权限的知识源返回未过滤结果，多用户场景可经由 on-behalf-of 取得用户令牌；撰写时页面把查询时权限过滤和项目里的 MCP 连接（RemoteTool）标为预览功能。
