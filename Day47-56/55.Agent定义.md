## Day55 - Agent 定义

> 工具、Skills 与 MCP ｜ 建议用时 1 小时

> **一句话**：一个 agent 由四样东西定义：系统提示词、Skills、工具白名单和模型；这份定义每发布一次就是一个不可改的新版本。
>
> **放在全局看**：这一课把本阶段的零件收拢成一个可以发布的对象：Day48 的白名单、Day53 和 Day54 的 Skill 修订都写进定义里。定义怎样发布和回滚，在 Day74、Day75 展开；定义之外的上限和权限，由 Day45 和 Day59 的机制强制执行。

### 学习目标

- 写出一份 agent 定义，说清每个字段的作用。
- 说清定义为什么要作为不可变、带版本的修订保存。
- 区分系统 agent 和用户定义的 agent，以及两者权限不同的原因。

### 核心概念

**打个比方**：像一份岗位说明书：写清这个岗位做什么（系统提示词）、按哪几本手册干活（Skills）、能动用哪些工具（白名单）、配什么级别的人（模型）。工资上限、门禁权限不写在说明书里，由人事和安保统一管。

**四个组成部分**

```yaml
name: course-qa
kind: system                    # system 或 user
model: chat-default             # 模型网关上的别名（Day70），不写具体厂商型号
system_prompt: |
  你是课程与知识库问答助手。回答必须基于检索到的资料并给出引用；
  资料不足时如实说明，不要猜测。
skills:
  - name: cited-answer
    revision: 3f9c2a7e          # Day54 导入时生成的修订号
tools:                          # 白名单，名字必须在注册表里（Day48）
  - kb_search
  - courses_search
```

| 字段 | 作用 | 改动它意味着 |
| --- | --- | --- |
| 系统提示词 | 身份、职责、每次都要遵守的规则 | 行为可能整体变化，要跑评估 |
| Skills | 按任务加载的做法，引用到具体修订 | 只影响触发该 Skill 的任务 |
| 工具白名单 | 这个 agent 能请求哪些工具 | 能力边界变化，要重新评审风险 |
| 模型 | 用哪个模型，经网关的别名 | 质量、成本、延迟都可能变化 |

产品里的 agent 也大体是这个形状。以 Azure Foundry 为例，创建 agent 时提交模型、指令和工具，接入 MCP 工具时可以列出允许使用的工具名；创建用的是“创建版本”的接口，每个版本有自己的版本号。

**作为不可变修订保存**

定义一旦发布，就不在原处修改。改了提示词、换了 Skill 修订、加了一个工具，都是一个新修订。这样做换来三件事：

- 每次任务记录用的是哪个修订，出问题时能还原当时 agent 看到的一切（Day62）。
- 评估结果和修订一一对应，比较两个修订就是比较两次改动的效果（Day30）。
- 回滚就是把“生产”指回上一个修订，不需要临时改文件（Day75）。

Skill 也按修订号引用。只写名字、不写修订号，等于允许别人上传一个新版本就悄悄改变这个 agent。

**系统 agent 与用户定义的 agent**

| | 系统 agent | 用户定义的 agent |
| --- | --- | --- |
| 谁编写 | 平台团队 | 任何有权限的用户 |
| 发布前 | 评审、评估、走发布流程 | 自动校验，可选评审 |
| 可选工具 | 注册表里经过评审的工具，包括写工具 | 只能从“允许用户选用”的工具里选，默认只读 |
| 可用 Skill | 平台自带和已审核的 | 再加上自己导入的（Day54） |
| 访问数据用谁的身份 | 提问人的身份；后台任务用事先限定范围的身份 | 始终是使用者本人的身份 |

两者权限不同，原因在于责任和影响面：系统 agent 的每次改动都有人评审、有评估把关，服务很多人；用户定义的 agent 没有经过这些，所以让它的能力不超过使用者本人能做的事，也不能经由它接触高风险工具。

发布时由代码做校验，下面是一个草图：

```python
def validate(defn: dict, registry, skill_store, user_selectable: set[str]) -> list[str]:
    errors = []
    for name in defn["tools"]:
        if registry.get(name) is None:
            errors.append(f"工具 {name} 未注册")
        elif defn["kind"] == "user" and name not in user_selectable:
            errors.append(f"用户定义的 agent 不能使用 {name}")
    for s in defn["skills"]:
        rev = skill_store.get(s["name"], s["revision"])
        if rev is None:
            errors.append(f"Skill {s['name']} 没有修订 {s['revision']}")
        elif defn["kind"] == "system" and rev.tier not in {"platform", "reviewed"}:
            errors.append(f"系统 agent 不能使用未审核的 Skill {s['name']}")
    return errors
```

**定义里有意不放的东西**

| 不放进定义的 | 由谁决定 | 原因 |
| --- | --- | --- |
| 步数、token、时间上限 | 平台按 agent 类型和任务类型统一设定（Day45） | 能编辑定义的人不能自己给自己放宽预算 |
| 每个工具的调用上限、是否需要确认 | 注册表和审批规则（Day48、Day41） | 跟着工具走，不跟着 agent 走 |
| 运行身份和数据权限 | 平台按使用者身份决定（Day59） | 定义可以被复制和分享，权限不能跟着复制 |
| 密钥和连接凭据 | 平台的凭据管理 | 定义会进版本库、进追踪 |

定义描述“这个 agent 想做什么”，平台决定“它最多能做多少”。即使有人在定义里写了“最多 100 步”，代码也只认平台的上限。
