## Day48 - 工具注册表与白名单

> 工具、Skills 与 MCP ｜ 建议用时 1 小时

> **一句话**：所有工具登记在一张注册表里，每个 agent 只能用名单上的那几个；模型要了名单外的工具，代码直接拒绝。
>
> **放在全局看**：Day06 的分发表 `TOOL_FUNCS` 是写死在代码里的，这一课把它换成带元数据的注册表。之后接 MCP server（Day50、Day51）、定义 agent（Day55）、做最小权限（Day59），都以这张表为准。

### 学习目标

- 定出工具注册表的字段，说清每个字段由谁填、在哪一步用到。
- 写出分发前的检查：白名单、调用上限、所需权限，任何一项不满足就不执行。

### 核心概念

**打个比方**：像公司的设备借用登记簿：每件设备登记了名称、用途、是否危险、谁能借、一次借几件。来借东西的人报出一个名字，管理员先翻登记簿和他的权限，对得上才交出去。

**从写死的列表到注册表**

Day06 里，`TOOLS` 给模型看，`TOOL_FUNCS` 给代码分发，两者靠工具名对应。工具一多、agent 一多，问题就来了：哪个 agent 能用哪些工具没有地方写；工具是只读还是会写入，只有读代码才知道；接进来的 MCP 工具和自己写的工具混在一起，分不清来源。

注册表把这些信息放到一起，每个工具一条记录：

| 字段 | 含义 | 用在哪里 |
| --- | --- | --- |
| 名称 | 全局唯一，带服务前缀，如 `orders_get_status` | 分发、白名单、追踪 |
| 描述 | 写给模型看的说明（Day47） | 发给模型 |
| 参数结构 | JSON Schema | 发给模型；执行前校验参数 |
| 只读或写 | `read` / `write` | 写工具要走确认（Day41）和幂等（Day49） |
| 风险级别 | 低 / 中 / 高 | 决定是否需要人工确认、调用上限多大 |
| 调用上限 | 一次任务里最多调用几次 | 预算（Day45） |
| 所需权限 | 调用人必须具备的权限 | 分发前检查 |
| 版本 | 工具实现或描述的版本 | 评估对比、出问题时回溯 |
| 来源 | 自带、某个 MCP server、某个导入的 Skill | 信任等级（Day54、Day66） |

只读、风险级别和所需权限由你们评审后填写，不照抄工具自己的声明。MCP 规范允许 server 用 annotations 描述工具行为，同时明确要求 client 在 server 不可信时把这些 annotations 当作不可信信息。一个 server 说自己的工具“只读”，不等于它真的只读。

**每个 agent 一份白名单**

agent 的定义里列出它能用的工具名（Day55）。白名单在两处起作用：

1. 发请求时，只把白名单里工具的定义发给模型。模型看不到的工具，一般不会去要。
2. 分发时再查一遍。模型可能编出一个工具名，也可能被注入的文本诱导去要一个它没见过的工具（Day58）。第一道是“不让看见”，第二道才是真正的拦截。

**草图：注册表和分发前检查**

```python
from dataclasses import dataclass
from typing import Callable, Literal

@dataclass(frozen=True)
class ToolSpec:
    name: str
    description: str
    parameters: dict                   # JSON Schema
    func: Callable[..., str]
    access: Literal["read", "write"]
    risk: Literal["low", "medium", "high"]
    max_calls: int                     # 单次任务内的上限
    permission: str                    # 例如 "orders:read"
    version: str
    source: str                        # "builtin" / "mcp:<server>" / "skill:<name>"

    def to_model_schema(self) -> dict:
        return {"type": "function", "function": {
            "name": self.name, "description": self.description, "parameters": self.parameters}}

class Registry:
    def __init__(self) -> None:
        self._tools: dict[str, ToolSpec] = {}

    def register(self, spec: ToolSpec) -> None:
        if spec.name in self._tools:
            raise ValueError(f"工具名重复：{spec.name}")   # 两个来源的同名工具不能互相覆盖
        self._tools[spec.name] = spec

    def get(self, name: str) -> ToolSpec | None:
        return self._tools.get(name)

    def schemas_for(self, allowed: list[str]) -> list[dict]:
        return [self._tools[n].to_model_schema() for n in allowed if n in self._tools]

def check_call(registry: Registry, allowed: set[str], name: str,
               user_perms: set[str], counts: dict[str, int]) -> str | None:
    """返回拒绝原因；返回 None 表示可以执行。"""
    if name not in allowed:
        return f"工具 {name} 不在当前助手的可用范围内，请只使用已提供的工具。"
    spec = registry.get(name)
    if spec is None:
        return f"工具 {name} 未注册。"
    if spec.permission not in user_perms:
        return f"当前用户没有使用 {name} 的权限。"
    if counts.get(name, 0) >= spec.max_calls:
        return f"{name} 在本次任务中已达到调用上限 {spec.max_calls} 次，请基于已有结果作答。"
    return None
```

几点说明：

- `check_call` 在参数校验和执行之前运行，任何一项不满足，都不调用 `func`。
- 拒绝原因作为工具结果交还模型，让它换个办法或如实告诉用户。权限不足是否还要终止任务，Day49 再细分。
- `user_perms` 是提问人的权限，来自登录身份，不来自模型生成的参数。
- 被拒绝的调用也要记进追踪，它常常是注入或描述写得不清的信号。

**注册是一个受控动作**

谁能往注册表里加工具、加进来以后默认进不进任何白名单，要有规则。建议默认不进：新工具注册后处于“可用但未分配”状态，评审填好只读、风险和权限后，再加进具体 agent 的白名单。这和 Day50 写的 MCP server 接入规则是同一件事。
