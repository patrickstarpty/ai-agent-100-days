## Day50 - MCP 架构

> 工具、Skills 与 MCP ｜ 建议用时 1 小时

> **一句话**：MCP 是 AI 应用连接外部工具和数据的统一接口标准。
>
> **放在全局看**：有了统一标准，接入外部能力变容易了，随之而来的是“接什么、信什么”的治理问题。

### 学习目标

- 说清 MCP 的三个角色和三种基本能力。
- 定出“谁能把外部工具接进来”的规则。

### 核心概念

**打个比方**：像 USB 接口：设备厂商按同一个标准做，任何电脑都能插。能插上，不代表每个 U 盘都该信任。

**MCP 解决什么问题**

每个 AI 应用都要接各种外部系统，每接一个就写一套适配。Model Context Protocol（MCP）把“应用怎样从外部获得工具和上下文”定成一个开放协议，一个 MCP server 写好后可以被任何支持 MCP 的应用使用。协议只管上下文怎样交换，不管应用怎样使用模型。

**三个角色**

| 角色 | 是什么 |
| --- | --- |
| Host | AI 应用本身，负责管理一个或多个 client |
| Client | host 内部的组件，每个 client 与一个 server 保持连接 |
| Server | 对外提供工具和上下文的程序，可以在本机，也可以在远端 |

**server 提供的三种能力**

- Tools：可被调用的函数，用来执行动作（查询、调用接口、写入）。
- Resources：只读的数据源，提供上下文（文件内容、数据库结构）。
- Prompts：可复用的提示词模板。

client 先用 `tools/list` 发现有哪些工具，再用 `tools/call` 调用。工具列表可以是动态的。

**两种传输**

- stdio：host 启动一个本地进程，通过标准输入输出通信。适合本机工具。
- Streamable HTTP：通过 HTTP 访问远端 server，支持常规的 HTTP 认证，协议建议用 OAuth 获取令牌。

协议按日期发布版本，撰写时文档对应的版本是 `2026-07-28`，这一版把协议定为无状态：每个请求自带协议版本和能力声明。开始实现前先核对当前版本。

**接入 server 就是引入外部代码和外部文本**

- server 的工具描述会进入模型的上下文，它是不可信输入（Day57、Day58）。
- 远端 server 能看到你发给它的参数，其中可能有用户数据。
- 工具一旦进入白名单，模型就可能在你没预料到的时机调用它。

所以注册 server 应该是一个受控动作：谁能注册、注册后哪些工具进入白名单、每个工具的风险级别，都要有规则。把知识库以 MCP 接口提供给 agent 时，还要解决提问人的身份怎样传到检索层（Day21、Day52）。
