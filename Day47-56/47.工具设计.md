## Day47 - 工具设计

> 工具、Skills 与 MCP ｜ 建议用时 1 小时

> **一句话**：工具是写给模型用的，要让它用最少的调用、最少的文字办成一件事。
>
> **放在全局看**：Day05 讲了工具调用的协议，Day06 把工具接进了循环，这一课讲工具本身怎样设计。工具的好坏直接决定 agent 的成功率和成本，值得像提示词一样反复打磨。设计好的工具交给 Day48 登记进注册表，Day49 再细分它们出错时由谁处理。

### 学习目标

- 掌握为 agent 设计工具的五条原则。
- 能评审一个现有工具的描述和返回值。

### 核心概念

**打个比方**：像给新同事准备工具箱：放几把趁手的，每把贴上清楚的标签，比塞满一百件没标签的强。

**工具是给模型用的接口**

给程序员用的 API 追求完备和正交；给 agent 用的工具追求让模型用最少的调用、最少的 token 完成一件事。把后端每个接口原样包成工具，通常效果很差。

**五条原则**

| 原则 | 说明 | 反例 |
| --- | --- | --- |
| 少而准 | 为高价值的任务设计少数几个工具，把常一起用的步骤合并 | 订单系统的“查订单头”“查订单明细”“查物流”三个接口原样包成工具，模型查一次订单状态要调三次 |
| 命名分组 | 用前缀按服务和资源分组，让模型分得清 | 课程系统和工单系统各有一个 `get_detail`，模型不知道该调哪个；改成 `courses_get`、`tickets_get` 就清楚了 |
| 返回有意义的内容 | 返回人能读懂的名称和摘要，少返回内部 ID 和原始结构 | 查课程只返回 `{"cid": 1042, "tid": 77}`，模型还要再查一次才知道课程名和讲师 |
| 节省 token | 默认分页、过滤、截断；错误信息告诉模型怎样改正 | 查一张工单就把几百条历史评论全部带回来；出错时只返回一个错误码 |
| 描述要写清 | 像给新同事交代工作那样写清做什么、什么时候用、参数的格式和取值范围 | 描述只写“查工单”，唯一的参数叫 `q`，模型不知道该填工单号还是关键词 |

**错误信息是提示词的一部分**

工具报错的文本会原样进入模型的上下文。“日期格式应为 YYYY-MM-DD，你传入的是 10/09”能让模型下一步改对；一个堆栈跟踪只会浪费 token。

**用评估来改工具**

改工具描述和改提示词一样，要靠评估集判断好坏。看追踪里模型在哪里用错了工具、在哪里多调了几次，再回头改描述或合并工具。

### 动手练习

**20 分钟必做**

1. 挑主线项目里现有的两个工具（例如知识检索和带引用回答），按五条原则逐条评审，写下每条的结论和改进点。

**课后选做**

2. 为“工具注册表”定字段：名称、描述、参数结构、是否只读、风险级别、调用上限、所需权限、版本。Day48 会给出一份参考字段，可以拿来对照。

### 自检

1. 为什么“返回内部 ID”对 agent 不友好，而对程序调用方却很合理？
2. 哪些工具应该标为高风险？依据是什么？
