## Day97 - 设计评审清单

> 架构师收口 ｜ 建议用时 1 小时

> **一句话**：清单保证评审时每个方面都被问到，而不只是你熟悉的那些。
>
> **放在全局看**：前面 Day34、Day46、Day66、Day76 的复盘各对照过清单的一节，Day94 第一次用它完整检查了自己的设计。这一课把清单定稿，Day98、Day99 拿它做两次评审演练，Day100 把它和其他产出一起交给团队维护。

### 学习目标

把各阶段积累的清单定稿，并知道怎样用它评审别人的 agent 项目。

### 核心概念

**打个比方**：像飞行员的起飞检查单：再有经验的机长，也照单逐项确认。

**清单的用途**

评审别人的设计时，最大的风险是只评自己熟悉的部分。清单保证每个方面都被问到。它是提问的起点，每个问题都应引出一段讨论，不要把它当作打勾的表格。

**怎样提问**

- 问“怎样做到的”，少问“有没有”。“有评估吗”得到的回答是“有”；“一次提示词改动上线前，怎样知道它没有让别的问题变差”才能看出实际情况。
- 要证据：评估集文件、一条真实的追踪、一次失败的 CI。
- 每一节最后问同一个问题：这里最可能出事的地方是什么，出事时谁会先知道。

**清单的七节**

模板给出的是完整版，前面各阶段复盘时你已经对照过其中几节，按自己的项目增删过问题。各节的出处如下：

| 节 | 来自 |
| --- | --- |
| 该不该用 agent | Day35、Day77 |
| 评估 | Day34 |
| 编排 | Day46 |
| 工具与安全 | Day66 |
| 权限与平台底座 | Day76 |
| 多 agent 与长时运行 | Day77、Day84、Day85 |
| 运行与治理 | Day62–65 |

完整版本见 [设计评审清单](../模板/设计评审清单.md)。

**评审的产出**

一次评审结束时交给项目组的应该是一页纸：三到五条按优先级排序的发现，每条写明问题、可能的后果、建议的下一步。超过五条，对方通常一条也不会处理。

### 动手练习

**20 分钟必做**

1. 找一份一页长的设计：你自己项目的设计说明，或 Day98 的设计摘要。只挑清单里的两节，把其中每个“有没有”式的问题改写成“怎样做到的”问法，并写下你会向对方要的证据（文件、追踪、测试）。

**课后选做**

1. 用定稿的清单完整评审一个真实项目，评审后请对方写一段书面反馈：哪条发现最有用，哪条不符合实际。

### 自检

1. 清单里哪些问题对“知识检索类系统”和“编码类 agent”应该有不同的问法？
2. 一次评审给出十二条发现，问题出在哪？
