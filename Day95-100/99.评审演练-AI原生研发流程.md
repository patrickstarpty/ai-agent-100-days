## Day99 - 评审演练：AI 原生研发流程

> 架构师收口 ｜ 建议用时 1 小时

> **一句话**：用同一份清单评审一份编码 agent 流程的设计，找出那些让 agent 权力过大、停不下来、自己给自己打分的地方。
>
> **放在全局看**：这是 Day98 的姊妹练习，对象换成案例 B。你在 Day87~94 自己设计过这条流程，这次站在评审人的位置看别人的版本。

### 学习目标

- 用 [设计评审清单](../模板/设计评审清单.md) 评审一份编码 agent 流程的设计摘要。
- 区分编码类系统和检索类系统在评审时的不同关注点。
- 写出三到五条按优先级排序的发现。

### 核心概念

**打个比方**：像检查一家新开的自助加油站：油枪好不好用是一回事，更要紧的是有没有自动断流、谁能打开油罐、加完油由谁结账。

**待评审的设计摘要（虚构）**

> **自动开发助手设计摘要**
>
> **目标**：产品经理在 Jira 里写好需求并打上“自动开发”标签后，系统自动完成开发并上线，减少开发人员的重复劳动。
>
> **流程**：一个开发 agent 监听带标签的工单。它读取工单的描述和全部评论，自行规划，在隔离的容器里修改代码、运行测试，然后把代码推送到主分支。agent 认为需求已经实现时，把工单状态改为“开发完成”。
>
> **权限**：agent 使用一个对代码仓库有完整写权限的令牌，这样它可以处理任何仓库的需求。
>
> **构建**：推送到主分支后自动触发构建。为了让集成测试更接近真实情况，构建环境配置了生产数据库的只读账号。
>
> **运行方式**：agent 持续工作直到它判断任务完成为止，复杂需求可以运行很久。
>
> **审批**：发布前由产品经理在工单里点击“确认上线”，流水线随后发布。
>
> **可观测性**：每次运行的全部步骤按开放标准记录追踪，可以回放。
>
> **评估**：上线前用团队过去的二十个需求试跑过，大部分能完成。

**编码类系统的评审重点**

和 Day98 的知识库相比，这类系统的风险集中在“动作”上。评审时多问这几件事：

- 读不可信文本的 agent 和能写代码、能推送的 agent 是不是同一个（Day57、Day89）。
- 循环有没有步数、时间、token 上限，达到上限时停在什么状态（Day45）。
- 审批点放在哪，审批人看到的是什么，审批人和作者是不是同一方（Day41、Day92）。
- 构建和编码环境里有哪些凭据，网络能去哪里（Day93）。
- “完成”由谁判定（Day90）。

**示范一条发现**

> **发现（高）：“完成”由 agent 自己判断**
>
> - **问题**：摘要写明“agent 认为需求已经实现时，把工单状态改为开发完成”，而工单上并没有一份带验收标准的结构化需求，agent 也没有被要求跑哪一组测试才算完成。清单第二节“编码类 agent：验收标准是测试通过、构建通过，还是人工评审通过？”在这里找不到答案，实际的判定标准是 agent 的自我感觉。评估一节提到的“大部分能完成”，同样是按 agent 自己的标准统计的。
> - **可能的后果**：agent 可能在只做完一部分、或者理解错需求时宣布完成；产品经理看到“开发完成”后点击上线，未经验证的改动直接进入生产。长时运行的 agent 本来就容易过早宣布完成（Day84），这里没有任何外部检查能发现。
> - **建议的下一步**：把“完成”改为由外部条件判定：需求先经澄清和审批，形成带验收标准的结构化需求（Day89）；验收测试和构建结果由流水线判定，agent 只能申请状态变更（Day90）；用历史任务集加隐藏测试重新评估，报告每个任务多次运行的通过情况。

**轮到你**

摘要里至少还有四处值得写成发现，其中几处的后果比示范的这一条更严重，排序时要想清楚。提示：对照上面五个重点逐条问，再数一数这个 agent 占了三要素里的几项。

### 动手练习

1. 用清单评审上面的摘要，写出三到五条发现（可以包含示范的这一条），按优先级排序，每条都包含问题、可能的后果、建议的下一步。
2. 找出几条发现背后的共同根因，用一句话写在报告开头。
3. 把你的报告和 Day94 自己的设计文档对照：你自己的设计里，有没有哪一条也没有做到？

### 自检

1. 示范的这条发现为什么排不上第一位？哪一条应该排在它前面？
2. 摘要里“发布前由产品经理确认上线”这一次审批，为什么不足以弥补前面缺失的审批点？
