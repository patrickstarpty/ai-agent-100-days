## Day20 - 代码作为知识

> 知识检索 ｜ 建议用时 1 小时

> **一句话**：代码不能当普通文档来检索，它要按结构切分，而且常常需要精确查找。
>
> **放在全局看**：知识库一旦收录代码，Day12~14 的切法和查法、更新频率和 Day21 的权限模型都要为它单独考虑。Day87~94 的编码 agent 案例会直接用到这里的符号地图和现场搜索。

### 学习目标

- 说清代码和文档在检索上的差别。
- 能比较三种让 agent 获得代码上下文的做法。

### 核心概念

**打个比方**：查文档像在图书馆按主题找书，说个大意就能找到那一排。查代码更像维修小区的水管：先按门牌号一字不差地找到那一户（精确匹配符号），再顺着管道查它接着哪几户、由哪根总管供水（沿调用关系查找），只知道“大概在东边”修不了。

**代码和文档哪里不一样**

| 方面 | 文档 | 代码 |
| --- | --- | --- |
| 结构 | 章节、段落 | 文件、类、函数、调用关系 |
| 查询方式 | 语义相近即可 | 常常需要精确匹配一个符号名 |
| 自然的切片边界 | 段落或小节 | 语法单元（函数、类） |
| 变化速度 | 较慢 | 每天都在变 |
| 回答问题需要的范围 | 通常几个片段 | 常要沿调用链跨多个文件 |

按固定长度切代码会把函数拦腰截断；只靠向量相似度，查 `get_user_by_id` 可能返回一堆“看起来相似”的函数。

**三种做法**

| 做法 | 怎么做 | 优点 | 局限 |
| --- | --- | --- | --- |
| 向量切片 | 按语法单元切片后建向量索引 | 能回答“哪里处理了退款”这类语义问题 | 索引会过期；对精确符号查询不如关键词 |
| 符号地图 | 提取每个文件的关键类、函数和签名，形成一份全仓库的简明地图，按依赖关系挑出与当前任务最相关的部分放进上下文 | 用很少的 token 让模型知道“有什么、在哪” | 只有签名没有实现，细节仍要再读文件 |
| 现场搜索 | 不建索引，给 agent 搜索和读文件的工具，让它自己找 | 永远是最新的；适合沿调用链追踪 | 每次都要花步数和 token；仓库很大时慢 |

aider 的 repository map 是符号地图的一个公开实现：它把仓库表示成文件之间的依赖图，用图排序算法挑选最相关的部分，并受一个 token 预算控制。

**实际常见的组合**

符号地图给全局视野，现场搜索取细节，向量索引只用于跨仓库的语义查找。编码类 agent 多数时候靠前两者；面向“问答”的知识库更依赖向量和关键词索引。

**权限**

代码仓库的可见范围通常按仓库或团队划分。把代码纳入知识库时，Day21 的权限问题同样适用，而且符号地图和摘要这类派生物也要继承仓库权限。

### 动手练习

**20 分钟必做**

1. 为案例 A（企业知识库，同时收录文档和代码）写一张对比表：三种做法各自适合回答哪类问题，各自的更新成本，以及你建议的组合，并给出理由。

**课后选做**

2. 找一个你熟悉的小仓库，用 `grep` 或编辑器的“查找引用”回答“某个函数被哪些地方调用”，再用任意向量检索查同一个问题，比较两者的结果和花费的时间。

### 自检

1. “这个接口被哪些地方调用”适合用哪种做法？为什么向量检索不合适？
2. 仓库每天有上百次提交时，向量索引怎样保持可用？
