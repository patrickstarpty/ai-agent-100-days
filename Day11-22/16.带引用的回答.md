## Day16 - 带引用的回答

> 知识检索 ｜ 建议用时 1 小时

> **一句话**：回答拆成一条条结论，每条都标上证据编号，再由代码检查这些编号是否真实、是否取回过、提问人是否有权看。
>
> **放在全局看**：引用让检索的结果变成用户可以核对的依据。它承接 Day15 选出的证据，引出 Day17 的弃答；引用合法之后，结论是否真的成立由 Day27 的评审员来判。

### 学习目标

- 会把回答设计成“结论 + 证据标签”的结构化输出。
- 能用代码校验每条引用，并处理非法引用。
- 分得清“引用合法”和“结论成立”是两件事。

### 核心概念

**打个比方**：像写报销单：每一笔费用后面贴上对应的发票编号。财务先核对发票是否真实、是否属于这次报销，至于这笔钱该不该花，是另一道审核。

**把证据编号后再交给模型**

送进模型的每个切片，由代码分配一个短标签 E1、E2……，并在服务端保存“标签 → 切片”的对照表。模型只看到标签，看不到内部的切片 ID。

```text
<evidence id="E1" source="退订规则 第 2 节">标准套餐自开通之日起 30 天内可申请退订……</evidence>
<evidence id="E2" source="高级套餐说明 第 4 节">高级套餐退订时按剩余天数折算……</evidence>
```

用短标签有三个好处：模型不容易编造出一个看起来合理的 ID；对照表完全在代码手里；内部 ID 不暴露给用户。证据包在明确的标签里、和指令分开放，模型更容易把它们当作资料对待；这只能减轻注入的影响，真正的防护靠 Day58 讲的设计。

**回答的结构**

用结构化输出（Day04）让模型返回若干结论，每条带一个或多个标签：

```json
{
  "claims": [
    {"text": "标准套餐开通 30 天内可以退订。", "evidence": ["E1"]},
    {"text": "高级套餐退订按剩余天数折算费用。", "evidence": ["E2"]}
  ]
}
```

一条结论只说一件事。结论粒度越细，校验和后面的评审越容易。

**用代码校验引用**

```python
from dataclasses import dataclass

@dataclass
class Evidence:
    label: str      # "E1"
    chunk_id: str
    doc_id: str
    anchor: str     # 页码或节路径，点击后跳转用

@dataclass
class Claim:
    text: str
    evidence: list[str]

def validate(claims: list[Claim], evidence_map: dict[str, Evidence],
             retrieved_ids: set[str], can_read) -> tuple[list[Claim], list[Claim]]:
    """返回 (保留的结论, 丢弃的结论)。can_read(doc_id) 以提问人身份判断权限。"""
    kept, dropped = [], []
    for c in claims:
        valid = [
            label for label in c.evidence
            if label in evidence_map                               # 1. 标签存在于本次对照表
            and evidence_map[label].chunk_id in retrieved_ids      # 2. 切片确实是本次取回的
            and can_read(evidence_map[label].doc_id)               # 3. 提问人现在有权查看
        ]
        if valid:
            kept.append(Claim(c.text, valid))    # 剥掉非法标签，保留合法的
        else:
            dropped.append(c)                    # 一个合法标签都没有，整条丢弃
    return kept, dropped
```

三项检查各防一类问题：

1. **标签存在。** 模型可能写出 E9，而这次只给了 E1~E5；多轮对话里，它还可能引用上一轮的标签。每轮重新编号，对照表只属于这一轮。
2. **切片确实被取回。** 对照表如果被缓存或跨轮复用，标签可能指向这次并没有检索到的切片。
3. **有权限。** 检索时已经按权限过滤（Day21），这里再查一次，防的是缓存、图谱扩展（Day19）等旁路带进来的切片，以及检索之后才生效的权限变更。

**非法引用怎样处理**

- 部分标签非法：剥掉非法的，保留合法的。
- 一条结论没有合法标签：整条丢弃，不能当作“无引用的结论”展示。
- 丢弃之后一条不剩：整次回答转为弃答（Day17）。
- 丢弃的数量记进追踪和指标。比例升高，说明提示词、证据格式或模型出了问题。也可以把失败原因反馈给模型重写一次（Day39 的外部反馈），重写也要有次数上限。

**点击引用打开原文**

界面上每个标签渲染成链接，指向原件中对应的页或节（Day12 的锚点）。打开原文的服务以提问人身份再做一次权限检查，不能因为“回答里出现过”就放行。

**合法不等于成立**

上面的校验只证明：被引用的证据存在、是这次取回的、提问人有权看。它不证明结论能从证据推出来。模型可能引用 E1 却写出 E1 里没有的“15 天”。有一个便宜的补充检查：结论里出现的数字、日期、编号，必须在被引用的切片原文里找得到，找不到就标记出来。完整的判断要交给 Day27 的 LLM 评审员，它的可信度要靠人工标注校准。

### 动手练习

**20 分钟必做**

1. 为主线项目定义证据格式和回答的 JSON schema，写清标签怎样生成、每轮怎样重置。
2. 实现 `validate`，先为三种情况各写一个测试：标签不存在、切片未被取回、提问人无权限。

**课后选做**

3. 补齐另外三种情况的测试：标签来自上一轮、部分标签合法、全部非法。
4. 加上“数字必须出现在被引用切片里”的检查，用一个故意改错数字的回答验证它能发现问题。
